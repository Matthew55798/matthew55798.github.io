## 核心原则

阿里巴巴手册推荐的应用分层思想可以概括为：上层依赖下层，调用方向保持单向；不同层承担不同职责，避免把访问控制、业务编排、通用能力、数据访问混在一起。

典型依赖方向：

```text
开放 API 层 / 终端显示层
          |
        Web 层
          |
      Service 层
          |
      Manager 层
          |
        DAO 层
          |
      数据存储系统
```

旁路依赖：

- 开放 API 层可以直接封装 Service 接口，暴露为 RPC 或 HTTP 接口。
- Manager 层可以封装第三方服务、外部数据接口、中间件能力。
- DAO 层只处理与 MySQL、Oracle、HBase、OceanBase 等存储系统的数据交互。

## Controller 层

在手册中更偏向称为 Web 层，主要职责是访问入口处理。

适合放在 Controller 的逻辑：

- 路由和请求转发。
- 基本参数校验。
- 登录态、权限、幂等标识等访问控制。
- 不需要复用的简单业务处理。
- 将 Service 返回结果转换成前端需要的 VO 或统一响应结构。

不适合放在 Controller 的逻辑：

- 复杂业务规则。
- 事务控制。
- 多个 DAO 的组合访问。
- 第三方平台适配。
- 缓存、中间件等通用处理。

Controller 应该薄，避免变成“流程脚本层”。

## Service 层

Service 层是相对具体的业务逻辑服务层，承载业务用例和业务流程编排。

适合放在 Service 的逻辑：

- 业务用例入口，例如创建订单、审批流程、提交支付、生成报表。
- 事务边界。
- 业务规则校验。
- 调用 Manager 完成通用能力或外部系统适配。
- 输出 DTO、BO 或统一业务结果。

Service 不应该直接承担大量底层细节。若一段逻辑具有通用复用价值，或者需要封装第三方平台、中间件、多个 DAO 组合，优先下沉到 Manager。

## Manager 层

Manager 层是通用业务处理层，介于 Service 和 DAO / 外部服务之间。

手册中给出的 Manager 层典型特征可以整理为三类：

- 第三方平台封装：预处理返回结果，转换异常信息，适配上层接口。
- Service 通用能力下沉：缓存方案、中间件通用处理、分布式锁、限流等。
- DAO 组合复用：将多个 DAO 的访问组合为一个可复用能力。

实践中，Manager 可以理解为“可复用的业务基础能力”，但不能滥用。若只是某个单一业务用例的流程编排，仍应留在 Service。

## Repository / Mapper 层

阿里巴巴手册中使用 DAO 层的说法，常见工程中也会命名为 Repository、Mapper、Gateway 等。

职责边界：

- 只负责数据访问，不写业务流程。
- 只与底层存储或 ORM 框架交互。
- 负责 DO 和数据库表之间的映射。
- 返回 DO 或基础数据结构，不直接返回 VO。
- 不处理 Web 请求语义，不依赖 Controller / Service。

在 MyBatis 工程中，Mapper 接口一般属于 DAO 层；在 DDD 风格工程中，Repository 更强调聚合持久化语义，但底层实现仍属于数据访问边界。

## DTO

DTO 是 Data Transfer Object，即数据传输对象。

使用场景：

- Service 或 Manager 对外传输数据。
- RPC、HTTP API、二方库接口中的入参和出参。
- 跨模块、跨进程传递业务数据。

设计建议：

- 只暴露调用方需要的数据。
- 不直接复用数据库 DO，避免表结构泄漏到接口层。
- 字段命名保持业务语义，不强绑定页面控件或数据库字段。
- 对外接口 DTO 要考虑兼容性，避免随意删除字段或改变字段含义。

## VO

VO 是 View Object，即显示层对象。

使用场景：

- Controller 返回给前端页面或模板渲染的数据。
- 移动端、Web 端、管理后台等展示场景的响应结构。

设计建议：

- 面向展示，而不是面向数据库。
- 可以组合多个 DTO / BO 的字段。
- 可以包含展示状态、文案、按钮权限等前端需要的信息。
- 不要让 VO 反向进入 Service / DAO 作为核心业务入参。

## Entity / DO

阿里巴巴手册中更常用 DO，即 Data Object。DO 与数据库表结构一一对应，通过 DAO 层向上传输数据源对象。

使用边界：

- DO 属于数据访问模型。
- DO 字段类型要与数据库字段类型匹配。
- DO 不应该承担复杂业务行为。
- DO 不应该直接暴露给 Controller 或外部 API。

如果项目使用 JPA，Entity 往往兼具 ORM 实体含义；如果项目使用 MyBatis，DO / PO 更常见。无论命名如何，都要避免把持久化模型直接当作接口模型。

## BO

BO 是 Business Object，即业务对象。

使用场景：

- Service 层输出的、封装业务逻辑或业务状态的对象。
- 聚合多个 DO / DTO 后形成的业务视图。
- 业务计算、规则判断中的中间对象。

BO 与 DTO 的区别：

- DTO 偏传输边界，强调接口稳定和数据传递。
- BO 偏业务内部，强调业务含义和业务行为。

## Query

Query 是查询对象，各层可以用它接收上层的查询请求。

手册中特别提醒：超过 2 个参数的查询应封装为对象，不建议使用 Map 传输。

原因：

- Query 对象有明确字段和类型，调用方更容易理解。
- 编译期可以发现字段变更问题。
- Map 容易隐藏参数含义，导致魔法字符串和运行期错误。

示例：

```java
public class OrderQuery {
    private Long userId;
    private Integer status;
    private LocalDateTime startTime;
    private LocalDateTime endTime;
}
```

## 领域对象

分层领域模型可以按用途区分：

| 对象 | 含义 | 典型位置 | 是否跨层传递 |
|------|------|----------|--------------|
| DO / PO | 数据库表映射对象 | DAO 层 | 尽量只在 DAO / Manager 内使用 |
| Query | 查询请求对象 | Controller / Service / DAO | 可以向下传递 |
| DTO | 数据传输对象 | Service / API | 可以跨模块或跨进程 |
| BO | 业务对象 | Service / Manager | 主要用于业务内部 |
| VO | 展示对象 | Controller / Web | 只向展示层输出 |

常见转换方向：

```text
请求参数 -> Query / Command -> Service
DAO -> DO -> Manager / Service -> BO / DTO -> Controller -> VO
```

## 模块边界

按模块划分时，可以把“层”和“模块”同时考虑。

单体项目常见结构：

```text
example-system
├── example-web          # Controller、VO、Web 配置
├── example-service      # Service 接口和业务用例
├── example-manager      # 通用业务能力、第三方适配
├── example-dao          # Mapper、Repository、DO
├── example-api          # 对外 DTO、API 接口、枚举、常量
└── example-common       # 通用工具、基础异常、公共常量
```

更轻量的 Spring Boot 项目也可以先按包划分：

```text
com.example.order
├── controller
├── service
├── manager
├── repository
├── model
│   ├── dto
│   ├── vo
│   ├── bo
│   ├── query
│   └── dataobject
└── common
```

关键不是目录名字，而是依赖方向和职责边界是否清晰。

## 依赖方向

推荐规则：

- Controller 可以依赖 Service。
- Service 可以依赖 Manager。
- Manager 可以依赖 DAO、第三方 Client、基础组件。
- DAO 不依赖 Service / Controller。
- API 模块只放接口、DTO、必要枚举、常量，不反向依赖实现模块。
- Common 模块不放业务流程，避免变成无边界垃圾桶。

禁止或慎用：

- Controller 直接调用 Mapper。
- DAO 调用 Service。
- VO 进入 DAO。
- DO 直接作为外部 API 返回值。
- Common 依赖业务模块。

## 通用模块

通用模块适合放：

- 基础异常类。
- 统一响应码。
- 通用常量和枚举。
- 日期、金额、字符串等稳定工具类。
- 不含业务语义的基础设施封装。

通用模块不适合放：

- 订单、用户、支付等业务规则。
- 需要频繁改动的业务工具类。
- 对具体业务表、业务流程的依赖。

判断标准：如果离开当前业务系统仍然成立，可以考虑放入通用模块；如果只有当前业务理解它，就放回业务模块。

## 业务模块

业务模块应围绕业务能力划分，而不是只按技术层横切。

例如订单系统可以按以下方式组织：

```text
order
├── controller
├── service
├── manager
├── repository
└── model

payment
├── controller
├── service
├── manager
├── repository
└── model
```

模块划分建议：

- 高内聚：同一业务能力的 Controller、Service、DAO、模型尽量靠近。
- 低耦合：跨模块只通过 API / Service 接口交互，不直接访问对方 DAO。
- 稳定边界：对外暴露 DTO / API，内部 DO / BO 不随意外泄。
- 渐进拆分：先在单体内划清边界，再根据部署、团队、性能需要拆成独立服务。

## 异常处理分层

手册对异常处理也按层给出建议，可整理为：

- DAO 层：捕获底层异常后转换为 DAOException，通常不重复打印日志。
- Manager / Service 层：捕获并记录业务上下文、关键参数和错误日志。
- Web 层：作为顶层入口，不继续向上抛给用户；应转成友好错误页或统一错误响应。
- 开放 API 层：将异常转换成错误码和错误信息。

这样做的目标是避免重复日志、保留关键现场，并让外部调用方得到稳定的错误协议。

## 落地检查清单

- Controller 是否足够薄，没有直接写复杂业务流程？
- Service 是否表达一个明确业务用例？
- Manager 是否承接了可复用能力，而不是变成另一个 Service？
- DAO 是否只负责数据访问？
- DO 是否没有直接暴露到外部接口？
- DTO / VO / BO / Query 是否按用途区分？
- 超过 2 个查询参数时，是否使用 Query 对象承载？
- Common 模块是否没有混入业务逻辑？
- 模块之间是否保持单向依赖？
- 异常是否在合适层级记录和转换？
