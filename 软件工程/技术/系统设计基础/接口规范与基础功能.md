## 分页处理

普通后台管理系统里，分页一般采用“后端分页 + 前端维护查询状态 + 后端返回分页结果”的方式。前端不需要一次性拉取全部数据后再本地分页，而是在页码、每页条数、排序字段、排序方向、筛选条件变化时重新请求后端接口。

典型前端状态：

```js
const query = {
  page: 1,
  pageSize: 20,
  sortField: 'createdAt',
  sortOrder: 'desc'
}
```

典型后端返回：

```json
{
  "list": [],
  "total": 1280,
  "page": 1,
  "pageSize": 20,
  "totalPages": 64,
  "hasNext": true
}
```

字段含义：

| 字段 | 说明 |
|------|------|
| `list` | 当前页数据列表 |
| `total` | 符合查询条件的数据总数 |
| `page` | 当前页码，建议对外从 `1` 开始 |
| `pageSize` | 每页条数 |
| `totalPages` | 总页数，可由 `total` 和 `pageSize` 计算得到 |
| `hasNext` | 是否还有下一页，适合前端控制下一页按钮或加载更多 |

请求参数示例：

```http
GET /api/users?page=1&pageSize=20&sortField=createdAt&sortOrder=desc
```

后端一般使用 MyBatis-Plus 分页插件或 PageHelper 实现物理分页。需要注意的是，分页插件解决的是“统一生成分页 SQL、少写样板代码、封装分页结果”，不是从根上解决深分页问题。

### MyBatis-Plus 分页

MyBatis-Plus 的分页方式是配置分页插件，然后在查询方法里传入 `Page` 对象。插件会拦截 MyBatis 查询，根据数据库类型把普通查询改写成对应数据库的物理分页 SQL。

Spring Boot 常见配置：

```java
@Configuration
@MapperScan("com.example.mapper")
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

        PaginationInnerInterceptor pagination = new PaginationInnerInterceptor(DbType.MYSQL);
        pagination.setMaxLimit(500L);

        interceptor.addInnerInterceptor(pagination);
        return interceptor;
    }
}
```

普通分页查询：

```java
Page<User> page = new Page<>(query.getPage(), query.getPageSize());

LambdaQueryWrapper<User> wrapper = Wrappers.<User>lambdaQuery()
    .eq(User::getStatus, query.getStatus())
    .orderByDesc(User::getCreatedAt)
    .orderByDesc(User::getId);

Page<User> result = userMapper.selectPage(page, wrapper);
```

返回接口时不要直接把 MyBatis-Plus 的 `Page` 对象暴露给前端，可以转换成统一分页响应：

```java
return PageResult.of(
    result.getRecords(),
    result.getTotal(),
    result.getCurrent(),
    result.getSize()
);
```

MyBatis-Plus 分页插件一般会做两件事：

1. 根据原 SQL 生成 `count` SQL，用于查询总数。
2. 根据 `current` 和 `size` 生成分页 SQL，例如 MySQL 下追加 `limit ?, ?`。

对于自定义 XML SQL，也可以把 `IPage` 作为 Mapper 方法参数：

```java
IPage<UserVO> selectUserPage(IPage<?> page, @Param("status") Integer status);
```

```xml
<select id="selectUserPage" resultType="com.example.UserVO">
  select id, username, created_at
  from user
  where status = #{status}
  order by created_at desc, id desc
</select>
```

使用 MyBatis-Plus 分页时，需要注意：

- 分页插件要正确注册，多个插件同时存在时，分页插件通常放在最后。
- 设置 `maxLimit`，避免前端传入过大的 `pageSize`。
- 排序字段要白名单控制，避免直接拼接前端传入字段。
- 复杂 SQL 的 `count` 可能不准确或性能较差，必要时单独写 count 查询。
- 大表分页必须配合合适索引，插件本身不能消除深分页成本。

### PageHelper 分页

PageHelper 是 MyBatis 项目里常见的分页插件。它的典型用法是在 Mapper 查询前调用 `PageHelper.startPage(page, pageSize)`，然后紧跟着执行要分页的 Mapper 方法。

普通分页查询：

```java
PageHelper.startPage(query.getPage(), query.getPageSize());
List<User> list = userMapper.selectByCondition(query);
PageInfo<User> pageInfo = new PageInfo<>(list);
```

返回接口时同样建议转换成统一分页响应：

```java
return PageResult.of(
    pageInfo.getList(),
    pageInfo.getTotal(),
    pageInfo.getPageNum(),
    pageInfo.getPageSize()
);
```

PageHelper 的核心机制是：

1. `PageHelper.startPage(page, pageSize)` 把分页参数保存到当前线程的 `ThreadLocal`。
2. 后续第一个 MyBatis 查询被 `PageInterceptor` 拦截。
3. 插件读取 `ThreadLocal` 中的分页参数。
4. 自动执行总数查询。
5. 自动把原 SQL 改写成物理分页 SQL。
6. 查询结束后清理分页上下文。

因此，`startPage` 必须紧挨着需要分页的 Mapper 查询：

```java
PageHelper.startPage(1, 20);
List<User> list = userMapper.selectUsers();
```

不要把 `startPage` 和真正的 Mapper 查询隔得太远，也不要在中间加入复杂分支：

```java
PageHelper.startPage(1, 20);

if (needQuery) {
    List<User> list = userMapper.selectUsers();
}
```

更安全的写法是：

```java
if (needQuery) {
    PageHelper.startPage(1, 20);
    List<User> list = userMapper.selectUsers();
}
```

使用 PageHelper 分页时，需要注意：

- `startPage` 只对后面紧跟的第一个 MyBatis 查询生效。
- 不要在 `startPage` 和 Mapper 查询之间夹杂其他查询。
- 由于它依赖 `ThreadLocal` 传递分页参数，异常分支和复杂控制流要特别谨慎。
- 复杂 SQL 的 `count` 同样可能有性能问题，必要时要手写优化。
- PageHelper 也是物理分页插件，默认仍然是 `limit offset` 思路，深分页问题依然存在。
