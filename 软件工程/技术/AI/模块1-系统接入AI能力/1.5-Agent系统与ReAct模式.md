# 1.5 Agent 系统与 ReAct 模式

## 本章目标

掌握 Agent 系统的设计原理，能够理解 ReAct 模式，设计自主决策的 AI 系统。

## 核心知识点

### 1. Agent 的本质

**一句话定义：**
Agent 是一个能够感知环境、做出决策、执行行动的自主系统。

**类比：**
Agent 就像一个员工：
- **感知：** 收到任务、查看信息
- **决策：** 思考怎么做
- **行动：** 执行操作、使用工具
- **反馈：** 根据结果调整

**Agent vs 普通 LLM 调用：**

| 维度 | 普通 LLM 调用 | Agent |
|------|--------------|-------|
| 交互方式 | 单次请求-响应 | 多轮循环 |
| 决策能力 | 无，直接回答 | 有，自主规划 |
| 工具使用 | 无 | 可以调用工具 |
| 上下文 | 单次输入 | 累积记忆 |
| 适用场景 | 简单问答 | 复杂任务 |

### 3. ReAct 模式（Reasoning + Acting）

**核心思想：**
推理（Reasoning）和行动（Acting）交织进行，边想边做。

**ReAct 循环：**
```
观察（Observation）
    ↓
思考（Thought）
    ↓
行动（Action）
    ↓
观察新结果（Observation）
    ↓
...循环直到任务完成
```

**示例：计算购物车总价**
```
用户：帮我计算购物车里的商品总价

Agent 思考：
Thought: 我需要先获取购物车里的商品信息，然后计算总价。
Action: 调用 get_cart_items() 工具

观察结果：
Observation: 购物车有 3 件商品：
  - 商品 A: 价格 100
  - 商品 B: 价格 200
  - 商品 C: 价格 300

Agent 思考：
Thought: 我已经获取了商品信息，现在需要计算总价。
Action: 调用 calculate_total([100, 200, 300])

观察结果：
Observation: 总价 = 600

Agent 思考：
Thought: 任务完成，可以给出答案。
Action: 向用户返回结果

Final Answer: 您的购物车商品总价是 600 元。
```

**Prompt 模板：**
```
你是一个智能助手，可以通过工具完成任务。

可用工具：
- get_cart_items: 获取购物车商品
- calculate_total: 计算总价
- search_product: 搜索商品

请按照以下格式回复：
Thought: [你的思考过程]
Action: [工具名称] [参数]
Observation: [工具返回的结果]
...（重复 Thought-Action-Observation 直到完成）
Final Answer: [最终答案]

用户问题：{{question}}
```

### 4. Agent vs Workflow

**核心区别：**

| 维度 | Workflow | Agent |
|------|----------|-------|
| 流程确定 | 预先定义 | 动态决策 |
| 灵活性 | 低 | 高 |
| 可预测性 | 高 | 较低 |
| 可控性 | 高 | 需要设计边界 |
| 适用场景 | 确定性流程 | 探索性任务 |
| 调试难度 | 低 | 高 |

**决策流程：**
```
任务确定?
    │
    ├── 是 → 流程确定?
    │           │
    │           ├── 是 → Workflow（硬编码/规则引擎）
    │           │
    │           └── 否 → 部分确定 → Workflow + Agent 混合
    │
    └── 否 → Agent（自主决策）
```

### 5. Agent 设计模式

#### 模式 1：单 Agent 模式

**适用：** 简单任务、单一领域

**架构：**
```
用户请求 → Agent → 工具1/工具2/工具3 → 结果
```

**优点：** 简单、易于控制
**缺点：** 复杂任务能力有限

#### 模式 2：Multi-Agent 协作

**适用：** 复杂任务、多领域协作

**架构：**
```
                    ┌──────────┐
              ┌────►│ Agent A  │────┐
              │     │ (分析)   │    │
              │     └──────────┘    │
              │                     │
用户请求 ─────►│     ┌──────────┐    ├──► 整合结果
              │────►│ Agent B  │────┤
              │     │ (执行)   │    │
              │     └──────────┘    │
              │                     │
              │     ┌──────────┐    │
              └────►│ Agent C  │────┘
                    │ (验证)   │
                    └──────────┘
```

**协作方式：**
| 方式 | 说明 | 适用场景 |
|------|------|----------|
| 顺序执行 | A → B → C | 流水线任务 |
| 并行执行 | A/B/C 同时 | 独立子任务 |
| 主从模式 | 主 Agent 协调 | 复杂任务分解 |
| 竞争模式 | 多 Agent 竞争 | 需要多方案对比 |

#### 模式 3：Agent + Workflow 混合

**适用：** 既有确定流程，又需要灵活处理

**架构：**
```
用户请求
    ↓
[Workflow 阶段 1：确定流程]
    ↓
[Agent 阶段：灵活处理]
    ↓
[Workflow 阶段 2：确定流程]
    ↓
结果输出
```

**示例：订单处理**
```
1. Workflow: 接收订单 → 验证信息 → 创建订单记录
2. Agent: 根据订单类型，选择合适的处理策略
3. Workflow: 执行支付流程 → 更新状态 → 发送通知
```

### 6. Agent 边界与约束设计

**为什么需要边界？**
- 防止 Agent 无限循环
- 控制成本（每次循环都要调用 LLM）
- 保证安全性（限制操作范围）
- 确保可预测性

**边界设计维度：**

| 边界类型 | 设计要点 | 实现方式 |
|----------|----------|----------|
| 步数限制 | 最大循环次数 | 计数器 + 终止条件 |
| 时间限制 | 最大执行时间 | 超时机制 |
| 成本限制 | 最大 Token 消耗 | 预算控制 |
| 工具限制 | 可用工具白名单 | 权限配置 |
| 范围限制 | Agent 可访问的数据范围 | 数据权限 |
| 人工干预 | 关键步骤人工确认 | 审批节点 |

**步数限制示例：**
```
max_iterations = 10
for i in range(max_iterations):
    thought, action = agent.think_and_act()
    if action == "FINISH":
        break
    if i == max_iterations - 1:
        return "任务未在限制步数内完成"
```

### 7. Agent 系统设计考量

**可控性设计：**
- 关键决策节点人工确认
- 工具调用日志记录
- 异常处理与回退
- 手动覆盖机制

**可观测性设计：**
- 记录每一步的 Thought/Action/Observation
- 可视化执行路径
- 调试与审计能力

**安全性设计：**
- 工具权限最小化
- 输入输出审查
- 沙箱执行环境
- 敏感操作二次确认

```
    │       └── 需要灵活调整? → Workflow + 配置化
    │
    └── 低确定性 → 复杂度?

                │

                            ├── 否 → 单 Agent + 强约束
                            │
                            └── 是 → Multi-Agent 协作
```

## 本章小结

- Agent 是能感知、决策、行动的自主系统
- ReAct = Reasoning + Acting，边想边做
- Agent 适合不确定性任务，Workflow 适合确定性流程
- Agent 必须设计边界：步数、时间、成本、权限
- 复杂场景可用 Multi-Agent 协作
