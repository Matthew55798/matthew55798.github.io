# 1.4 RAG 原理与知识库设计

## 本章目标

掌握 RAG（检索增强生成）的完整设计与实现方法，能够设计生产级的知识库系统。

**本章是课程的重点章节。**

## 核心知识点

### 1. RAG 解决的问题

**LLM 的局限性：**
- 知识有截止日期（知识不新）
- 无法访问私有数据（知识不全）
- 可能产生幻觉（知识不准）

**RAG 方案：**
将外部知识库与 LLM 结合：
```
用户问题 → 检索相关知识 → 组合上下文 → LLM 生成回答
                ↑
         企业知识库/实时数据
```

**核心价值：**
- 知识更新：知识库可以随时更新
- 知识扩展：可接入任意数据源
- 可溯源：回答可以追溯来源
- 成本优化：比微调便宜得多

### 2. RAG 完整流程

**流程概览：**
```
┌──────────────────────────────────────────────────────────┐
│                    数据准备阶段                            │
│  原始数据 → 加载 → 清洗 → 分割 → Embedding → 存储到向量数据库  │
└──────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────┐
│                    查询阶段                                │
│  用户问题 → Embedding → 向量检索 → Top-K 文档 → 组合上下文    │
└──────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────┐
│                    生成阶段                                │
│  上下文 + 用户问题 → LLM → 生成回答                          │
└──────────────────────────────────────────────────────────┘
```

#### 数据准备阶段

**1. 数据加载（Load）**

支持的数据源：
- 文档：PDF、Word、TXT、Markdown
- 结构化数据：数据库、CSV、JSON
- 网页：爬取网页内容
- API：第三方数据接口

**加载策略：**
| 数据源 | 工具 | 注意事项 |
|--------|------|----------|
| PDF | PyPDF、PDFMiner | 表格识别 |
| Word | python-docx | 样式信息 |
| 网页 | BeautifulSoup | 反爬策略 |
| 数据库 | SQLAlchemy | 增量同步 |

**2. 数据清洗（Clean）**

清洗内容：
- 去除格式标记、HTML 标签
- 统一编码（UTF-8）
- 去除重复内容
- 修正 OCR 错误
- 处理特殊字符

**3. 文档分割（Split）**

**为什么需要分割？**
- Embedding 模型有输入长度限制
- 检索粒度要细，才能精准匹配
- 过长的文档语义不聚焦

**分割策略：**

| 策略 | 做法 | 适用场景 |
|------|------|----------|
| 固定长度 | 每 N 个字符/Token 一段 | 通用场景 |
| 重叠分割 | 相邻段有重叠（防止断句） | 保持上下文连贯 |
| 语义分割 | 按句子/段落自然边界 | 文档结构清晰 |
| 递归分割 | 先按大段，再细分 | 复杂文档 |
| 智能分割 | 基于语义完整性的分割 | 高质量要求 |

**分割参数：**
- Chunk Size：每段大小（通常 200-500 Token）
- Chunk Overlap：重叠大小（通常 10-20%）
- 分隔符：优先在段落、句子边界分割

**4. Embedding（嵌入）**

将分割后的文本转换为向量

**模型选择：** 参见 0.5 章节

**5. 存储（Store）**

存储到向量数据库：
- 向量 + 元数据（来源、时间、ID 等）
- 建立索引加速检索

#### 查询阶段

**1. 用户问题 Embedding**

使用相同模型将问题转为向量

**2. 向量检索**

查找相似向量：
- 相似度度量：余弦相似度
- 返回 Top-K（通常 3-10 个）

**检索优化策略：**

| 策略 | 做法 | 效果 |
|------|------|------|
| 重排序 | 初筛后用小模型精排 | 提高准确性 |
| 混合搜索 | 向量 + 关键词混合 | 提高召回率 |
| 多查询 | 生成多个相关问题分别检索 | 提高覆盖率 |
| 查询改写 | 优化用户问题表达 | 提高相关性 |
| 元数据过滤 | 按标签、时间等过滤 | 缩小范围 |

#### 生成阶段

**1. 上下文组装**

将检索结果组合成 Prompt：
```
基于以下信息回答问题：

[文档1]
[文档2]
[文档3]

用户问题：[问题]

如果无法从以上信息中找到答案，请明确说明。
```

**2. LLM 生成**

- 使用 Prompt 调用 LLM
- 可选：流式输出
- 可选：要求提供来源

```

                                                       ↓
                                                返回结果 + 来源
```

### 4. 各环节设计决策

#### 分割策略决策

**决策因素：**
| 因素 | 建议 |
|------|------|
| 文档类型 | FAQ 按问答对；文档按段落；代码按函数 |
| 粒度要求 | 高粒度用小 Chunk；低粒度用大 Chunk |
| 上下文依赖 | 强依赖增加 Overlap；弱依赖可减少 |
| 存储成本 | Chunk 越多，存储成本越高 |

**Chunk 大小选择：**
```
小 Chunk（100-300 Token）：
  - 优点：检索精准、存储少
  - 缺点：可能丢失上下文
  - 适用：FAQ、定义类知识

中 Chunk（300-500 Token）：
  - 平衡方案
  - 适用：通用文档

大 Chunk（500-1000 Token）：
  - 优点：上下文完整
  - 缺点：检索噪音大、存储多
  - 适用：流程说明、长文
```

#### 检索策略决策

**Top-K 选择：**
| K 值 | 适用场景 | 风险 |
|------|----------|------|
| 1-3 | 精准问答 | 可能遗漏相关信息 |
| 5-7 | 通用场景 | 平衡方案 |
| 10+ | 研究型问答 | 上下文窗口压力大 |

**相似度阈值：**
- 阈值过高：召回不足
- 阈值过低：噪音太多
- 建议：0.6-0.8，按场景调优

#### 向量数据库选型

**选型维度：**
| 维度 | 考量 |
|------|------|
| 规模 | <100K 用轻量；>1M 用专业方案 |
| 延迟 | 实时应用用内存型；离线用磁盘型 |
| 成本 | 托管服务 vs 自建成本 |
| 运维 | 是否有专人维护 |
| 功能 | 是否需要混合搜索、过滤等 |

### 5. 知识库更新与同步

**更新策略：**

| 策略 | 触发条件 | 适用场景 |
|------|----------|----------|
| 实时更新 | 文档变更立即更新 | 高频更新场景 |
| 定时同步 | 每小时/天批量更新 | 一般场景 |
| 手动触发 | 管理员手动更新 | 低频更新、审核场景 |
| 版本管理 | 保留历史版本 | 需要追溯场景 |

**增量更新：**
- 只处理变更的文档
- 记录文档版本号
- 支持删除和更新

### 6. RAG 评估与优化

**评估指标：**

**检索质量：**
- 召回率：相关文档是否被检索到
- 精确率：检索到的文档是否相关
- MRR（平均倒数排名）：相关文档的平均排名

**生成质量：**
- 答案相关性：回答是否切题
- 忠实度：回答是否基于检索内容
- 有用性：回答是否有帮助

**优化方向：**

| 问题 | 可能原因 | 优化方案 |
|------|----------|----------|
| 检索不到 | 分割不当、Embedding 问题 | 调整分割、换模型 |
| 检索噪音多 | Chunk 太大、阈值太低 | 减小 Chunk、提高阈值 |
| 回答不完整 | 上下文过长被截断 | 精简 Prompt、减少 Chunk 数 |
| 回答不准确 | 检索内容不准确 | 优化检索、增加重排序 |
| 成本高 | Token 消耗大 | 优化 Prompt、缓存结果 |

### 各环节技术选型决策矩阵

**分割策略决策：**
```
文档类型?
    │
    ├── FAQ → 按问答对分割
    │
    ├── 技术文档 → 按章节/标题分割
    │
    ├── 代码 → 按函数/类分割
    │
    └── 通用文档 → 递归分割（先段落再句子）

上下文依赖强度?
    │
    ├── 强 → 大 Chunk + 大 Overlap
    │
    └── 弱 → 小 Chunk + 小 Overlap
```

**检索策略决策：**
```
数据规模?
    │
    ├── <100K → Chroma / pgvector
    │
    ├── 100K-1M → Weaviate / Pinecone
    │
    └── >1M → Milvus / 自建方案

查询类型?
    │
    ├── 关键词为主 → 混合搜索（向量+关键词）
    │
    └── 语义查询为主 → 纯向量搜索
```

## 本章小结

- RAG = 检索 + 生成，解决 LLM 知识局限
- 数据准备是 RAG 的基础：Load → Clean → Split → Embed → Store
- 检索质量决定生成质量，要多策略优化
- 分割策略要根据文档类型和查询方式选择
- RAG 需要持续评估和优化
