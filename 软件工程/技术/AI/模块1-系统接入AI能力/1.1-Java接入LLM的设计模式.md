# 1.1 Java 接入 LLM 的设计模式

## 本章目标

掌握 Java 系统接入 LLM 的各种设计模式，能够设计稳定、高效、可扩展的接入层架构。

## 核心知识点

### 1. 接入层架构设计

**为什么需要接入层？**

直接调用 LLM API 的问题：
- 强耦合：业务代码依赖特定 LLM 提供商
- 难以测试：需要真实 API Key
- 缺乏控制：没有重试、降级、限流
- 难以切换：更换 LLM 需要改大量代码

**接入层职责：**
- 抽象 LLM 调用细节
- 提供统一的调用接口
- 实现横切关注点（重试、降级、监控）
- 支持多模型路由

### 2. 同步 vs 异步调用设计

#### 同步调用

**适用场景：**
- 简单问答
- 用户等待时间短（<3秒）
- 实时性要求高

**设计要点：**
```
请求 → 等待响应 → 返回结果
```

**注意事项：**
- 设置合理的超时时间（建议 10-30 秒）
- 考虑 LLM 响应延迟波动
- 避免阻塞主线程（使用线程池）

**决策矩阵：**
| 场景 | 建议 | 理由 |
|------|------|------|
| 简单问答 | 同步 | 用户等待可接受 |
| 复杂生成 | 异步 | 耗时较长 |
| 批量处理 | 异步 | 不需要实时 |
| 用户交互 | 同步/流式 | 体验好 |

#### 异步调用

**适用场景：**
- 长文本生成
- 批量处理任务
- 不需要立即返回结果

**设计模式：**

1. **回调模式**
   ```
   提交任务 → 返回任务 ID
                     ↓
            后台处理 → 回调通知
   ```

2. **轮询模式**
   ```
   提交任务 → 返回任务 ID
                     ↓
            客户端轮询查询状态
   ```

3. **消息队列模式**
   ```
   业务服务 → 消息队列 → 消费服务 → LLM API
                              ↓
                        结果 → 消息队列 → 业务服务
   ```

**选型建议：**
- 简单场景：回调模式
- 高可靠：消息队列模式
- 已有 MQ 基础设施：复用现有 MQ

### 3. 流式响应设计

**为什么需要流式？**

- 用户体验：边生成边显示，不用等待完整响应
- 超时控制：避免长文本导致超时
- 资源利用：逐步处理，内存友好

**流式工作流程：**
```
用户提问
    ↓
发送流式请求
    ↓
接收 Token 1 → 显示
接收 Token 2 → 追加显示
接收 Token 3 → 追加显示
    ↓
流结束 → 完整响应存储
```

**设计要点：**
1. **SSE（Server-Sent Events）**
   - 适合 Web 应用实时推送
   - 浏览器原生支持
   - 单向流（服务器→客户端）

2. **WebSocket**
   - 双向通信
   - 适合对话场景
   - 复杂度较高

3. **HTTP 流**
   - 最简单
   - 逐行读取响应
   - 适合后端服务间通信

### 4. 重试与降级策略

#### 重试策略

**什么时候重试？**
- 网络超时
- 服务端错误（5xx）
- 限流错误（429）

**什么时候不重试？**
- 客户端错误（4xx）
- 内容错误（内容过长等）
- 成本敏感场景（重试 = 双倍费用）

**重试设计模式：**

1. **固定间隔重试**
   - 简单实现
   - 可能加重服务器负担

2. **指数退避**
   ```
   第 1 次：等待 1 秒
   第 2 次：等待 2 秒
   第 3 次：等待 4 秒
   第 4 次：等待 8 秒
   ```
   - 避免雪崩效应
   - 推荐做法

3. **带抖动的退避**
   - 添加随机因子
   - 避免多个客户端同时重试

#### 降级策略

**降级层次：**

1. **模型降级**
   ```
   GPT-4 失败 → 尝试 GPT-3.5
            ↓
   仍然失败 → 使用本地小模型
            ↓
   最终失败 → 返回预设回答
   ```

2. **功能降级**
   - 完整功能 → 简化功能
   - AI 生成 → 模板返回
   - 实时生成 → 缓存结果

3. **熔断机制**
   - 连续失败 N 次后，暂停调用
   - 保护下游服务
   - 自动恢复检测

**熔断器状态流转：**
```
关闭（正常调用）
    ↓ 失败次数 > 阈值
打开（拒绝调用，快速失败）
    ↓ 等待超时
半开（允许少量调用测试）
    ↓ 成功
关闭（恢复正常）
```

### 5. 多模型路由设计

**为什么需要多模型？**

- 成本优化：简单任务用小模型
- 能力互补：不同模型擅长不同任务
- 可用性：某个模型故障时切换
- A/B 测试：对比不同模型效果

**路由策略：**

| 策略 | 适用场景 | 实现复杂度 |
|------|----------|------------|
| 任务类型路由 | 不同任务用不同模型 | 低 |
| 成本优先路由 | 根据预算选择模型 | 中 |
| 负载均衡 | 分散请求到多个模型 | 中 |
| 智能路由 | 根据输入复杂度选择 | 高 |

**示例：任务类型路由**
```
简单分类 → GPT-3.5（便宜、快速）
复杂推理 → GPT-4（能力强、贵）
代码生成 → Claude（代码能力强）
中文场景 → 文心一言 / 通义千问
```

### 6. 响应缓存策略

**缓存的价值：**
- 降低成本（相同输入不重复计费）
- 提高响应速度
- 提高可用性（缓存兜底）

**缓存设计要点：**

1. **缓存键设计**
   - 包含：模型、参数、输入内容
   - 考虑：输入规范化（去除无关空格等）

2. **缓存命中率优化**
   - FAQ 类查询：命中率 > 80%
   - 开放式对话：命中率 < 10%

3. **缓存更新策略**
   - TTL（生存时间）
   - 主动刷新
   - 版本控制（Prompt 变更时失效）

**缓存架构示意：**
```
请求 → 检查缓存?
        │
    命中 → 返回缓存结果
        │
    未命中 → 调用 LLM → 存入缓存 → 返回结果
```

## 设计实战

### LLM 接入层架构设计

**分层架构：**

```
┌─────────────────────────────────────────────────────┐
│                  业务服务层                           │
│   客服服务    内容服务    分析服务                       │
└──────────┬────────────┬─────────────────────────────┘
           │            │
           ▼            ▼
┌─────────────────────────────────────────────────────┐
│                  接入层 Facade                        │
│   统一接口定义 / 参数校验 / 日志记录                     │
└──────────┬──────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────┐
│                  策略层                               │
│   重试策略 / 降级策略 / 路由策略 / 缓存策略              │
└──────────┬──────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────┐
│                  适配层                               │
│   OpenAI适配器    Claude适配器    文心一言适配器        │
│   模型转换 / 协议适配 / 错误码映射                       │
└──────────┬──────────────────────────────────────────┘
           │
           ▼
┌─────────────────────────────────────────────────────┐
│                  LLM 服务商                          │
│   OpenAI    Anthropic    百度    阿里                  │
└─────────────────────────────────────────────────────┘
```

### 调用模式选型决策树

```
是否需要实时响应?
    │
    ├── 是 → 能否接受等待 3 秒以上?
    │           │
    │           ├── 是 → 流式响应（SSE/WebSocket）
    │           │
    │           └── 否 → 同步调用（带超时控制）
    │
    └── 否 → 数据量多大?
                │
                ├── 小 → 回调模式
                │
                └── 大 → 消息队列模式
```

### 降级策略设计文档模板

```markdown
## 降级策略设计：[功能名称]

### 降级层级

#### 层级 1：模型降级
- 主模型：[模型名称]
- 降级模型：[模型名称]
- 触发条件：主模型连续失败 3 次

#### 层级 2：功能降级
- 完整功能描述：[功能描述]
- 降级功能描述：[简化版本]
- 触发条件：所有模型都不可用

#### 层级 3：服务降级
- 降级方案：返回预设模板 / 提示用户稍后再试
- 触发条件：服务完全不可用

### 恢复策略
- 自动恢复检测间隔：[时间]
- 人工干预阈值：[连续失败次数]
```

## 本章小结

- 接入层是隔离业务与 LLM 的关键，必须设计
- 同步适合简单场景，异步适合复杂/批量任务，流式提升体验
- 重试要指数退避，降级要分层设计
- 多模型路由可以优化成本和可用性
- 缓存能显著降低成本，但要评估命中率
