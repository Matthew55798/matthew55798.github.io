# 1.6 Tool/Skill 集成设计

## 本章目标

掌握将现有系统 API 抽象为 AI 可用 Tool 的设计方法，能够设计安全、灵活的 Tool 集成架构。

## 核心知识点

### 1. Tool 的本质

**一句话定义：**
Tool 是 AI 可以调用的外部能力，让 AI 能"做"而不只是"说"。

**为什么需要 Tool？**

LLM 本身只能生成文本，无法：
- 查询数据库获取实时数据
- 执行操作（下单、发送邮件）
- 访问外部系统（CRM、ERP）
- 进行计算（精确数学计算）

**Tool 让 LLM 拥有了"手"和"脚"。**

### 2. Function Calling 机制

**工作原理：**

```
用户：帮我查一下订单 12345 的状态

LLM 思考：需要查询订单信息
    ↓
识别需要调用工具
    ↓
生成工具调用请求：
{
  "function": "query_order_status",
  "parameters": {
    "order_id": "12345"
  }
}
    ↓
系统执行工具
    ↓
返回结果给 LLM
    ↓
LLM 生成最终回答：
"您的订单 12345 已发货，预计明天送达。"
```

**调用流程：**
```
用户请求
    ↓
LLM 分析是否需要工具
    │
    ├── 不需要 → 直接回答
    │
    └── 需要 → 生成函数调用 JSON
                ↓
        系统解析并执行函数
                ↓
        返回执行结果
                ↓
        LLM 基于结果生成回答
```

### 3. API 抽象为 Tool 的设计模式

#### 模式 1：直接映射

**适用：** API 功能单一、参数简单

**设计：**
```
原始 API: GET /api/orders/{order_id}
    ↓
Tool: query_order
    参数: order_id (string)
    返回: order_info (object)
```

**优点：** 简单直接
**缺点：** API 变更影响 Tool

#### 模式 2：适配层封装

**适用：** API 复杂、需要组合多个调用

**设计：**
```
原始 API: 
  - GET /api/orders/{id}
  - GET /api/orders/{id}/items
  - GET /api/products/{id}

适配层:
Tool: get_order_with_details
    参数: order_id
    内部逻辑:
      1. 调用订单 API 获取基本信息
      2. 调用订单项 API 获取商品列表
      3. 调用商品 API 获取商品详情
      4. 组合返回
    返回: 完整订单信息
```

**优点：** 隐藏复杂性、统一接口
**缺点：** 需要额外开发

#### 模式 3：语义化封装

**适用：** 面向业务场景、需要自然语言理解

**设计：**
```
原始 API: 技术导向的接口

语义化 Tool:
  name: "check_inventory"
  description: "查询指定商品的库存情况，返回可售数量和预计补货时间"
  parameters:
    - product_name: "商品名称或关键词"
    - location: "仓库位置（可选，默认查全部）"
  
内部映射:
  - 根据 product_name 模糊匹配 product_id
  - 调用库存查询 API
  - 转换为自然语言友好的返回
```

**优点：** AI 更容易理解和使用
**缺点：** 需要精心设计描述

### 4. Tool Schema 设计

**Schema 是 AI 理解 Tool 的说明书。**

**Schema 结构：**
```json
{
  "name": "tool_name",
  "description": "工具功能描述（AI 用）",
  "parameters": {
    "type": "object",
    "properties": {
      "param1": {
        "type": "string",
        "description": "参数说明"
      },
      "param2": {
        "type": "number",
        "description": "参数说明"
      }
    },
    "required": ["param1"]
  }
}
```

**设计原则：**

| 原则 | 说明 | 示例 |
|------|------|------|
| 命名清晰 | 动词+名词 | `query_order` 优于 `order_info` |
| 描述详细 | 说明功能、场景、限制 | "查询订单状态，需要订单号，返回状态和物流信息" |
| 参数明确 | 每个参数都有说明 | 不只有类型，还要说明用途和格式 |
| 示例丰富 | 提供调用示例 | 参数示例、返回值示例 |
| 错误说明 | 可能的错误情况 | "订单不存在时返回 404" |

**描述优化示例：**

❌ 差：
```json
{
  "name": "get_data",
  "description": "获取数据",
  "parameters": {
    "id": {"type": "string"}
  }
}
```

✅ 好：
```json
{
  "name": "query_order_status",
  "description": "查询指定订单的当前状态、物流信息和预计送达时间。适用于用户询问订单进度时。订单号必须是 6-20 位数字。",
  "parameters": {
    "order_id": {
      "type": "string",
      "description": "订单号，6-20 位数字，例如：1234567890"
    }
  }
}
```

### 5. Tool 权限与安全设计

#### 权限控制

**控制维度：**
| 维度 | 控制方式 | 示例 |
|------|----------|------|
| 用户级 | 哪些用户能用 | 管理员可用退款，普通用户不可用 |
| 会话级 | 当前上下文权限 | 只能操作自己的订单 |
| 数据级 | 能访问哪些数据 | 只能看自己部门的数据 |
| 操作级 | 能执行哪些操作 | 查询可用，修改需要审批 |

**实现方式：**
```
Tool 调用
    ↓
权限检查
    │
    ├── 无权限 → 拒绝调用
    │
    └── 有权限 → 数据范围检查
                    │
                    ├── 超出范围 → 拒绝调用
                    │
                    └── 范围内 → 执行调用
```

#### 安全设计

**风险场景：**

| 风险 | 示例 | 防护 |
|------|------|------|
| 未授权访问 | 用户 A 查询用户 B 的订单 | 会话校验 + 数据权限 |
| 注入攻击 | 参数包含 SQL 注入 | 输入验证 + 参数化查询 |
| 过度调用 | 高频调用导致系统崩溃 | 限流 + 熔断 |
| 敏感操作 | 未经授权的退款 | 二次确认 + 审批 |
| 数据泄露 | Tool 返回过多敏感信息 | 字段过滤 + 脱敏 |

**安全策略：**

1. **输入验证**
   - 参数类型检查
   - 范围检查
   - 格式校验
   - 黑名单过滤

2. **输出控制**
   - 最小权限原则
   - 敏感字段脱敏
   - 错误信息泛化

3. **调用控制**
   - 限流（Rate Limiting）
   - 熔断（Circuit Breaker）
   - 审计日志

4. **人工确认**
   - 敏感操作人工审批
   - 大额操作二次确认
   - 异常操作告警

### 6. Tool 错误处理与回退

#### 错误类型

| 类型 | 示例 | 处理策略 |
|------|------|----------|
| 参数错误 | 缺少必填参数 | 返回错误，让 LLM 修正 |
| 业务错误 | 订单不存在 | 返回友好提示 |
| 系统错误 | 服务不可用 | 返回降级方案 |
| 权限错误 | 无权限访问 | 返回权限不足提示 |
| 超时 | 调用超时 | 重试或返回超时提示 |

#### 错误处理策略

```
Tool 调用
    ↓
执行
    ↓
成功? 
    │
    ├── 是 → 返回结果给 LLM
    │
    └── 否 → 错误类型?
                │
                ├── 可重试 → 重试 N 次
                │
                ├── 可修正 → 返回错误信息，让 LLM 修正
                │
                ├── 业务错误 → 返回友好错误信息
                │
                └── 系统错误 → 返回降级方案 / 人工介入
```

#### 回退策略

| 场景 | 回退方案 |
|------|----------|
| 查询失败 | 返回缓存数据 / 提示稍后重试 |
| 计算失败 | 返回估算值 / 提示人工计算 |
| 外部 API 失败 | 使用模拟数据 / 降级功能 |
| 权限不足 | 返回可公开信息 / 引导人工处理 |

### 7. Tool 注册与发现机制

**为什么需要注册与发现？**

- 动态添加/移除 Tool
- 多版本管理
- 权限控制
- 监控统计

**架构设计：**
```
┌─────────────────────────────────────────────────────────┐
│                  Tool 注册中心                           │
│                                                          │
│  Tool 清单                                               │
│  ├── Tool A (v1.0) - 状态：启用                          │
│  ├── Tool B (v2.0) - 状态：启用                          │
│  └── Tool C (v1.0) - 状态：禁用                          │
│                                                          │
│  元数据：Schema、权限、版本、统计                         │
└─────────────────────────┬───────────────────────────────┘
                          │
            ┌─────────────┼─────────────┐
            │             │             │
            ▼             ▼             ▼
    ┌───────────┐ ┌───────────┐ ┌───────────┐
    │  Agent 1  │ │  Agent 2  │ │  Agent 3  │
    │（客服场景）│ │（运维场景）│ │（分析场景）│
    └───────────┘ └───────────┘ └───────────┘
```

**注册流程：**
```
开发 Tool
    ↓
定义 Schema
    ↓
注册到 Tool 中心
    ↓
配置权限
    ↓
测试验证
    ↓
发布上线
```

### API 抽象为 Tool 的设计规范

```markdown
## Tool 设计规范

### 1. 命名规范
- 动词 + 名词
- 小写下划线分隔
- 示例：`query_order`、`create_refund`

### 2. Schema 设计规范

#### 名称
```json
"name": "query_order_status"
```

#### 描述
必须包含：
- 功能是什么
- 什么时候用
- 参数要求
- 返回什么
- 限制条件

示例：
```json
"description": "查询订单状态。当用户询问订单进度、物流信息时使用。订单号必须是已存在的有效订单号。返回订单状态、物流信息和预计送达时间。"
```

#### 参数
每个参数必须包含：
- 类型
- 描述（含示例）
- 是否必填
- 约束条件

示例：
```json
{
  "order_id": {
    "type": "string",
    "description": "订单号，10-20 位数字，例如：2024010112345678",
    "required": true
  },
  "include_items": {
    "type": "boolean",
    "description": "是否包含订单商品详情，默认为 false",
    "default": false,
    "required": false
  }
}
```

### 3. 安全规范
- 必须校验调用者身份
- 必须限制数据访问范围
- 敏感操作需要审批
- 所有调用记录审计日志

### 4. 错误处理规范
- 参数错误：返回 400，说明缺少什么参数
- 业务错误：返回 200 + 错误信息
- 系统错误：返回 500，记录日志
- 所有错误信息要友好，可被 LLM 理解

### 5. 版本管理
- Tool 版本跟随 API 版本
- 支持多版本共存
- 弃用需提前通知
```

## 本章小结

- Tool 让 AI 能"做"而不只是"说"
- Function Calling 是 Tool 调用的标准机制
- API 抽象需要考虑语义化、权限、安全
- Schema 设计决定 AI 使用 Tool 的效果
- 安全设计是多维度的：输入、输出、权限、调用控制
