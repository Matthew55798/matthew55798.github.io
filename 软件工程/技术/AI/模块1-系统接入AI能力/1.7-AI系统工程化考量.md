# 1.7 AI 系统工程化考量

## 本章目标

掌握 AI 系统在生产环境的工程化设计方法，能够设计成本可控、延迟可接受、安全可保障的 AI 增强系统。

## 核心知识点

### 1. 成本模型与优化

#### 成本构成

**LLM 调用成本：**
```
单次成本 = (输入 Token / 1000) × 输入单价 + (输出 Token / 1000) × 输出单价

示例（GPT-4）：
输入：1000 Token @ $0.03/1K = $0.03
输出：500 Token @ $0.06/1K = $0.03
单次 = $0.06

1 万次/天 = $600/天 = $18,000/月
```

**其他成本：**
- 向量数据库：存储 + 查询
- 计算资源：服务器、GPU
- 网络流量：API 调用、数据传输
- 存储：日志、历史数据

#### 成本优化策略

| 策略 | 实现方式 | 预期效果 | 适用场景 |
|------|----------|----------|----------|
| 模型降级 | GPT-4 → GPT-3.5 | -50% ~ -90% | 简单任务 |
| 响应缓存 | 相同输入返回缓存 | -30% ~ -70% | FAQ、重复查询 |
| Prompt 压缩 | 精简指令、去重 | -10% ~ -30% | 长 Prompt |
| 流式处理 | 边生成边输出 | 用户体验优化 | 实时交互 |
| 批量处理 | 合并请求 | -10% ~ -20% | 非实时场景 |
| 上下文压缩 | 摘要代替全文 | -30% ~ -50% | 长对话 |
| Embedding 优化 | 小模型、降维 | -50% ~ -80% | 大规模检索 |

#### 成本监控与告警

**监控维度：**
```
成本指标：
- 单次调用平均成本
- 日均调用成本
- 月度累计成本
- 成本趋势（周环比、月环比）

使用指标：
- 调用次数
- Token 消耗（输入/输出）
- 缓存命中率
- 模型分布（大模型 vs 小模型占比）

效率指标：
- 成本/请求
- 成本/有效回答
- 单位业务价值的成本
```

**告警策略：**
| 告警类型 | 触发条件 | 响应措施 |
|----------|----------|----------|
| 日成本超标 | 单日 > 预算 120% | 检查异常调用 |
| 单次成本高 | 单次 > 平均值 3 倍 | 检查 Prompt |
| Token 激增 | Token 数突增 50% | 检查输入长度 |
| 缓存失效 | 命中率 < 50% | 检查缓存策略 |

### 2. 延迟优化

#### 延迟构成

```
总延迟 = 网络延迟 + 队列等待 + 处理延迟 + 生成延迟

网络延迟：50-200ms（取决于地理位置）
队列等待：0-5000ms（取决于负载）
处理延迟：100-500ms（Prompt 处理、检索等）
生成延迟：500-10000ms（取决于输出长度和模型）

总计：700ms - 15s
```

#### 延迟优化策略

**1. 架构层面**

| 策略 | 做法 | 效果 |
|------|------|------|
| 就近部署 | 选择离用户近的机房 | -50-200ms |
| CDN 加速 | 静态资源、缓存 | -50-100ms |
| 异步处理 | 非关键路径异步化 | 感知延迟降低 |

**2. 模型层面**

| 策略 | 做法 | 效果 |
|------|------|------|
| 模型降级 | 简单任务用小模型 | -50-90% |
| 流式输出 | 首 Token 快速返回 | 感知延迟降低 |
| 预加载 | 预测用户行为提前生成 | -100-500ms |

**3. 缓存层面**

| 策略 | 做法 | 效果 |
|------|------|------|
| 多级缓存 | L1/L2/L3 缓存 | -70-90% |
| 预计算 | 热门问题预生成答案 | 几乎为零 |
| 语义缓存 | 相似问题复用答案 | -50-70% |

**4. 检索层面（RAG 场景）**

| 策略 | 做法 | 效果 |
|------|------|------|
| 索引优化 | HNSW、倒排索引 | -50-80% |
| 近似检索 | 牺牲精度换速度 | -30-50% |
| 结果缓存 | 热门查询缓存 | -70-90% |

#### 延迟预算设计

**不同场景的延迟要求：**

| 场景 | 目标延迟 | 最大可接受延迟 |
|------|----------|----------------|
| 实时聊天 | <1s | 2s |
| 客服回复 | <2s | 5s |
| 文档生成 | <5s | 10s |
| 批量处理 | <30s | 60s |
| 后台任务 | <5min | 10min |

**延迟分配：**
```
目标：总延迟 < 2s

分配：
- 网络往返：200ms
- 队列等待：300ms（限流保证）
- 检索（RAG）：300ms
- LLM 首 Token：500ms
- LLM 生成：700ms
- 总计：2000ms
```

### 3. 安全设计

#### 安全风险矩阵

| 风险类别 | 具体风险 | 影响 | 缓解措施 |
|----------|----------|------|----------|
| 提示注入 | 用户输入覆盖系统指令 | 数据泄露、未授权操作 | 输入过滤、指令强化 |
| 数据泄露 | Prompt 包含敏感信息 | 隐私泄露 | 数据脱敏、最小权限 |
| 幻觉 | LLM 生成错误信息 | 误导用户、决策错误 | 事实核查、来源标注 |
| 有毒输出 | 生成有害内容 | 品牌风险、合规问题 | 内容审核、输出过滤 |
| 滥用 | API 被恶意调用 | 成本激增、服务中断 | 限流、认证、监控 |
| 供应链 | 依赖库漏洞 | 系统被攻击 | 依赖扫描、版本管理 |

#### 安全架构设计

```
用户请求
    ↓
┌─────────────────────────────────────────┐
│              输入层防护                  │
│  - 身份认证                             │
│  - 限流熔断                             │
│  - 输入过滤（注入检测）                   │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│              处理层防护                  │
│  - 数据脱敏                             │
│  - 权限校验                             │
│  - Prompt 安全                           │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│              模型层防护                  │
│  - 内容审核 API                          │
│  - 输出过滤                             │
│  - 敏感词检测                            │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│              审计层                      │
│  - 全链路日志                            │
│  - 异常检测                              │
│  - 合规报告                              │
└─────────────────────────────────────────┘
    ↓
响应返回
```

#### 内容安全策略

**输入侧：**
- 注入攻击检测
- 敏感信息识别（身份证号、手机号等）
- 恶意意图识别

**输出侧：**
- 内容分类（政治、色情、暴力等）
- 敏感信息脱敏
- 事实准确性检查

### 4. 可观测性设计

#### 观测维度

**日志（Logging）：**
- 请求日志：输入、参数、输出
- 错误日志：异常、超时、降级
- 审计日志：谁在什么时间做了什么

**指标（Metrics）：**
- 业务指标：QPS、成功率、延迟
- 成本指标：Token 消耗、费用
- 质量指标：用户满意度、准确率

**追踪（Tracing）：**
- 请求链路：端到端追踪
- 依赖关系：服务调用图
- 性能瓶颈：热点分析

#### 关键指标设计

```
业务指标：
- ragas_qps：RAG 系统 QPS
- ragas_latency_p99：P99 延迟
- ragas_success_rate：成功率

成本指标：
- llm_cost_per_request：单次请求成本
- llm_token_usage：Token 消耗
- cache_hit_rate：缓存命中率

质量指标：
- answer_relevance：回答相关性
- retrieval_precision：检索准确率
- user_satisfaction：用户满意度
```

### 5. 高可用与容错设计

#### 故障场景与应对

| 故障场景 | 影响 | 应对策略 |
|----------|------|----------|
| LLM 服务不可用 | 无法生成回答 | 多服务商降级、缓存兜底 |
| 向量数据库故障 | RAG 检索失败 | 降级到关键词搜索、返回提示 |
| 网络故障 | 调用超时 | 重试、熔断、返回友好提示 |
| 限流触发 | 请求被拒绝 | 排队、降级、提示稍后重试 |

#### 降级策略

**分层降级：**
```
L1: 完整功能（AI 生成 + RAG）
    ↓ 故障
L2: 降级功能（AI 生成，无 RAG）
    ↓ 故障
L3: 基础功能（关键词搜索 + 模板回答）
    ↓ 故障
L4: 保底功能（返回"服务暂时不可用"）
```

#### 灾备设计

**多区域部署：**
- 主区域：处理主要流量
- 备区域：故障时切换
- 数据同步：向量数据库同步

**数据备份：**
- 向量数据定期备份
- 配置数据版本控制
- 支持快速恢复

## 本章小结

- 成本优化是多层次的：模型选择、缓存、Prompt 优化
- 延迟优化要分场景：实时 vs 非实时有不同的策略
- 安全是系统工程：输入、处理、输出、审计四层防护
- 可观测性是生产必需：日志、指标、追踪三位一体
- 高可用需要主动设计：降级、熔断、多区域容灾

## 思考题

1. 如果你的 AI 系统日成本突然翻倍，你会如何排查和优化？
2. 如何设计一个既能保证安全，又不严重影响用户体验的内容审核策略？
3. 当你的 LLM 服务商出现故障时，你的系统应该在多长时间内完成降级？
