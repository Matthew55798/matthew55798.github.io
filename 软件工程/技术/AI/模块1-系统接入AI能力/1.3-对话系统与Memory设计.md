# 1.3 对话系统与 Memory 设计

## 本章目标

掌握对话系统的 Memory 设计方法，能够为不同场景选择合适的会话管理策略。

## 核心知识点

### 1. 对话系统的核心挑战

**状态管理：**
- 多轮对话需要记住之前的上下文
- 用户可能随时切换话题
- 需要区分当前话题和历史信息

**上下文限制：**
- LLM 有上下文窗口限制
- 不能无限累积对话历史
- 需要在有限空间内保留关键信息

**用户体验：**
- 对话要连贯自然
- 避免重复提问
- 个性化记忆（用户偏好）

### 2. Memory 的类型与适用场景

#### Buffer Memory（缓冲记忆）

**原理：** 完整保存最近 N 轮对话

**存储格式：**
```
[用户]: 你好
[助手]: 您好，有什么可以帮您的？
[用户]: 我想退货
[助手]: 好的，请问订单号是多少？
[用户]: 123456
```

**优点：**
- 简单直观
- 保留完整对话
- 易于调试

**缺点：**
- 上下文窗口占用大
- 无法处理超长对话
- 无法跨会话记忆

**适用场景：**
- 短对话（<10轮）
- 实时客服
- 调试阶段

#### Window Memory（窗口记忆）

**原理：** 只保留最近 K 轮对话

**示例（K=4）：**
```
对话历史（只保留最近4轮）：
- 第 N-3 轮
- 第 N-2 轮
- 第 N-1 轮
- 第 N 轮（当前）

更早的对话被丢弃
```

**优点：**
- 控制上下文长度
- 避免窗口溢出
- 实现简单

**缺点：**
- 早期信息丢失
- 可能遗忘关键上下文
- 不适合长对话

**适用场景：**
- 中等长度对话（10-30轮）
- 对历史依赖不强的场景
- 成本敏感场景

#### Summary Memory（摘要记忆）

**原理：** 定期对历史对话进行摘要，用摘要代替原始对话

**工作流程：**
```
对话轮次 1-10：
  - 完整保留

对话轮次 11-20：
  - 对 1-10 轮生成摘要
  - 保留：摘要 + 11-20 轮原始对话

对话轮次 21-30：
  - 对 1-20 轮生成摘要
  - 保留：摘要 + 21-30 轮原始对话
```

**摘要触发策略：**
| 策略 | 触发条件 | 适用场景 |
|------|----------|----------|
| 固定轮次 | 每 N 轮生成摘要 | 规律对话 |
| Token 阈值 | Token 数超过阈值 | 变长对话 |
| 话题切换 | 检测到话题变化 | 多话题对话 |
| 手动触发 | 业务逻辑控制 | 精确控制 |

**优点：**
- 大幅压缩上下文
- 保留关键信息
- 支持超长对话

**缺点：**
- 摘要可能丢失细节
- 需要额外的 LLM 调用（生成摘要）
- 摘要质量影响效果

**适用场景：**
- 长对话（>30轮）
- 需要跨会话记忆
- 复杂任务追踪

#### Vector Memory（向量记忆）

**原理：** 将对话内容 Embedding 后存储，按需检索

**工作流程：**
```
用户提问 → Embedding → 向量检索 → 相关历史 → LLM 生成回答
                ↑
历史对话 → Embedding → 向量数据库（存储）
```

**检索策略：**
1. **相似度阈值：** 只返回相似度 > 0.7 的历史
2. **Top-K：** 返回最相关的 K 条
3. **时间衰减：** 近期对话权重更高
4. **混合策略：** 相似度 + 时间 + 重要性

**优点：**
- 语义检索，不限于关键词
- 可跨会话检索
- 支持大规模历史

**缺点：**
- 需要向量数据库
- 检索可能遗漏相关信息
- 实现复杂度较高

**适用场景：**
- 超长对话（100+轮）
- 跨会话记忆
- 知识密集型对话

#### Entity Memory（实体记忆）

**原理：** 提取对话中的关键实体（人名、地点、订单号等）单独存储

**示例：**
```
对话：
用户：我叫张三，订单号是 12345
用户：我想查询这个订单

实体提取：
- 用户名：张三
- 订单号：12345

后续对话可直接使用：
"您好张三，订单 12345 的状态是..."
```

**优点：**
- 精确记忆关键信息
- 可跨会话使用
- 便于业务集成

**缺点：**
- 需要实体识别
- 只适用于结构化信息
- 不支持自由文本记忆

**适用场景：**
- 需要记住用户身份
- 业务流程有明确字段
- 与现有系统集成

### 3. Memory 选型决策矩阵

| Memory 类型 | 上下文长度 | 跨会话 | 成本 | 复杂度 | 推荐场景 |
|-------------|-----------|--------|------|--------|----------|
| Buffer | 短 | 否 | 低 | 低 | 实时客服、短对话 |
| Window | 中 | 否 | 低 | 低 | 一般对话、成本敏感 |
| Summary | 长 | 部分 | 中 | 中 | 长对话、任务追踪 |
| Vector | 超长 | 是 | 中 | 高 | 知识库问答、个性化 |
| Entity | 结构化 | 是 | 低 | 中 | 业务流程、用户画像 |

### 4. 混合 Memory 策略

**为什么需要混合？**

单一 Memory 类型无法满足复杂场景：
- 需要短期上下文 + 长期记忆
- 需要结构化信息 + 自由文本
- 需要精确匹配 + 语义检索

**混合策略示例：**

```
用户提问
    │
    ├── 近期上下文（Window Memory）
    │       └── 最近 5 轮对话
    │
    ├── 对话摘要（Summary Memory）
    │       └── 本轮话题的摘要
    │
    ├── 相关历史（Vector Memory）
    │       └── 语义相似的历史对话
    │
    └── 用户信息（Entity Memory）
            └── 用户名、会员等级等

合并后输入 LLM
```

**优先级策略：**
1. 近期上下文：最高优先级（当前话题）
2. 对话摘要：次高优先级（话题背景）
3. 相关历史：中等优先级（参考信息）
4. 用户信息：基础信息（个性化）

### 5. Session 管理机制

#### Session 生命周期

```
创建 → 活跃 → 空闲 → 超时 → 销毁
  │      │      │      │      │
  │      │      │      │      └── 清理资源
  │      │      │      └───────── 触发保存
  │      │      └──────────────── 进入休眠
  │      └─────────────────────── 持续交互
  └────────────────────────────── 首次交互
```

**状态设计：**
| 状态 | 说明 | 触发条件 |
|------|------|----------|
| ACTIVE | 活跃状态 | 有最近交互 |
| IDLE | 空闲状态 | 超过 N 分钟无交互 |
| SUSPENDED | 挂起状态 | 超过 M 分钟无交互 |
| CLOSED | 关闭状态 | 显式关闭或超时 |

#### 会话隔离与共享

**隔离级别：**
- 用户级：每个用户独立会话
- 设备级：同一用户不同设备独立
- 业务级：不同业务线独立会话

**会话共享：**
- 跨设备同步：用户换设备继续对话
- 客服转接：人工接管 AI 会话
- 上下文继承：新会话继承历史偏好

## 本章小结

- Memory 是对话系统的核心，影响体验与成本
- 5 种 Memory 类型各有优劣，需要按场景选择
- 复杂场景需要混合策略，组合短期+长期+结构化记忆
- Session 管理要考虑生命周期、隔离、持久化
- 成本与效果需要权衡，不是 Memory 越多越好
