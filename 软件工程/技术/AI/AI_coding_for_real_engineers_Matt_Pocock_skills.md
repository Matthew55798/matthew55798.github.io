## 一 概念必读

### 1.1 六条约束 - 关于 LLM 的反直觉事实

| 约束 | 直觉误区 | 课程给出的应对 |
| --- | --- | --- |
| 上下文成本二次方增长 | "多塞点信息总没坏处" | 把上下文当预算，定期清空 |
| 智能区 / 愚蠢区 | "窗口大就能一直用" | 40% 开始警惕，阶段边界 `/clear` |
| 不是数据库、是模糊 JPEG |  |  |
| 知识截止 |  |  |
| 无状态 |  | 用文档、AGENTS.md、技能、交接文档外置记忆 |
| 非确定性 | "它上次能跑这次也能" | 反馈循环 + 测试 + 小步提交（小步快跑） |

后面所有流程、技能与限制，都是这六条的推论。
### 1.2 上下文是预算 - 成本按平方增长

语言模型把你输入的一切拆成 token，再转成数字序列；**所有可见的 token 构成上下文窗口**。关键不在"存了 N 个 token"，而在于模型不仅要存 token，还要记录**所有 token 之间的关系**：

| 上下文里的 token 数 | 需要跟踪的关系数 |
| --- | --- |
| 4 | 6 |
| 8 | 28 |
| 100 | 约 5000 条连接 |

这不像往文档里追加字符，而像**足球联赛增加球队后比赛场次暴涨**。实际影响是：你不断往上下文里塞消息，就是在给模型持续加压。

由此得到窗口的两段性质：

- **智能区（smart zone）**：窗口**早期**，模型有充足余量做推理，能关注窗口里的全部信息，决策通常靠谱。
- **愚蠢区（dumb zone）**：窗口**后期**，压力累积后幻觉开始出现、推理能力大幅下降，有时甚至记不住上下文里的内容。

什么时候进入愚蠢区仍有争议，但**所有人都承认它存在**。经验阈值是 **40%**：在 20 万 token 的窗口里，从 **8 万 token** 开始警惕。

**结论：要优化的是"干净的上下文"，不是"记得多的上下文"。** 这句话决定了上下文纪律的全部操作。

**问答补给**

- **120k 了该压还是该交接？** 120k 不是断崖，更像一条平缓下滑的曲线。判断标准是**剩余任务的复杂度**：剩下的事情足够简单就一路做完（讲师有时做到 250k）；压缩适合"任务中期、目标明确"时用。
- **怎么省 token？** 优先优化**质量**而不是成本。质量往下掉就得花时间修代理的错，返工成本立刻超过省下的 token。正确的经济账是把**开发者的小时数换算成 token**。

### 1.3 子代理 - 主代理的上下文保存机制

**语境决定取舍**：探索少花 token 就能给实现留更多智能区，但探索不足，代理就不了解代码库、实现质量下降。

解法是**子代理（subagent）**：主代理另开一个**独立上下文窗口**去干活，**只在子代理自己的窗口里大量烧 token，最后只把摘要交回主代理**。一句话记住：**子代理是协调者代理的上下文保存机制。** 可以并行开多个，也可以给它配更便宜、更快的模型。

一个反直觉的细节：**"探索"这个词必须说出口**。同一句需求，"告诉我这个仓库的技术栈"不会触发探索子代理（只读 6 个文件，分析不完整），"**探索**这个仓库里 X 的原理"才会让它读大量文件、调用多个工具。具体对比与数字见 2.3 代码库探索。

### 1.4 上下文纪律 - clear / handoff / compact

清理上下文有很多种做法，取舍标准是**沉积物**：每次回退并压缩都会在上下文里留一层沉积物，下次再顶到自动压缩区又留一层，层层叠加会以不可预测的方式影响输出。**每次与"上下文为空"的代理开始会话，输出都更可预测**——这一条决定了下面的偏好顺序：

```text
新建会话  >  handoff 分流  >  compact 压缩  >  一路自动压缩
```

`/compact` 压什么、`/handoff` 怎么剥出中途冒出的独立任务、什么时候该清空，见 2.5 压缩与 2.6 交接。

### 1.5 记忆外置 - CLAUDE.md → AGENTS.md → SKILL.md

模型无状态，所以"记忆"只能外置——把该记住的东西写进文件，而不是指望对话被记住。这一点直接决定了提示词的写法。

核心判断有两条：

- **常驻记忆只放"每次请求都相关"的东西**。它是每次请求都要付的固定成本，塞进偶发指令只会稀释关键指令；演示里一个 2000 行的记忆文件占了约 **10%** 的上下文。
- **指令要按需加载**。并非所有指令都适用于每个请求，所以正确做法是**每个分组一个独立文件，记忆文件里只留指向它们的链接**——"与其一次性抛出所有复杂性，不如给一张地图，允许它自行导航"。这就是**渐进式披露**，而**技能（Agent Skills）**是它的正式载体：默认只有 `name` 与 `description` 对代理可见，被调用时才把指令加载进上下文。

两个文件名的区别、`CLAUDE.md` 的反直觉定位、技能怎么定义与怎么把上百行规范改造成技能、自动记忆的审计方式，见 3.1 至 3.7。

### 1.6 反馈循环与红绿重构

**反馈循环**不是新发明，它是成熟工程师的既有实践（优秀工程师从不相信自己的一次性产出），只是现在由代理来跑：

```text
代理生成代码 → 跑检查（类型/测试/格式） → 据结果修正 → 再生成 → …直到质量达标
```

循环越多、质量越高。仓库里最强的是能**真正执行代码**的那几种：强类型立刻暴露拼写与类型错误，自动化测试验证逻辑是否符合预期。红绿重构（red-green-refactor）把这件事变成纪律：**先写会失败的测试并运行确认失败，再写最小实现，最后重构**——失败测试对 LLM 来说较难伪造，而且它迫使生成的代码可测试。

具体怎么让代理跑反馈循环、红绿重构在 AI 场景下的完整理由、一个工作单元怎么走完、双轴评审怎么做，见 5.1 反馈循环、5.2 红绿重构（`tdd` 技能）、5.3 `implement` 技能与 5.4 双轴评审（`code-review` 技能）。

**顺带回答一个测试问题：**"发布前的最优测试组合"是错误心态。应该**持续交付**：每五分钟、每次 CI 通过就是一个版本，把大发布拆小，出问题时能看清具体 diff、回滚也不牵连无关功能。最优测试就是**每天跑的 CI 测试**；在**预先约定的接口处**测试，不写琐碎的微单元测试。

### 1.7 代码库比引导指令更重要

"代码已经廉价了，所以质量无所谓"是最流行的错误推论。讲师的观点相反：**代理比人类更敏感于软件质量**，质量在 AI 时代更重要，并且会决定我们怎么设计代码库。

| 概念 | 出处 | 含义 |
| --- | --- | --- |
| 更好 = 更易修改 | John Ousterhout《软件设计哲学》 | 相关信息是否集中、改动是否容易引发看不见的连锁反应、反馈机制能否在交付前发现错误 |
| 软件熵（software entropy） | 《程序员修炼之道》 | 软件天然趋向变坏，每次随手的提交都让熵像棘轮一样升一格，只有重构与重设计能压回去 |
| AI 是熵加速器 | 讲师判断 | 抑制熵增的提交是软件工程里最难的任务之一，AI 目前不擅长 |

> 一次 AI 编码会话有三个要素：**你交办的任务、引导机制（如 `CLAUDE.md`）、以及代码库**。最重要的是代码库，因为**代理更可能复制你的代码库，而不是你的引导指令**。

原因是人类能靠记忆适应劣质代码库、绕开坑，而**AI 是无状态的，只会盲目复制**；劣质代码库给它的反馈循环更少，它也识别不出自己写了坏代码。**输入垃圾，输出必然是垃圾。**

### 1.8 深模块 - 为 AI 设计的代码库

前提判断：**当前一代 AI 代理并不擅长思考软件架构，它们通常设计出自己都难以使用的系统**；"为 AI 组织代码库"将成为一项核心技能。

**糟糕的代码库长什么样**：散布数十个细小模块，每个只有几个导出函数。AI 要找到正确的代码，必须沿整条导入导出链追踪；测试也只能逐个模块单独写，无法验证各部分如何协同，而且模块一变测试就得改（**测试与结构过度耦合**）。人类能靠直觉建立"代码库记忆"，**AI 没有这个优势**。

**解法是深模块（deep module）**：**一个薄薄的接口，加上后面厚重的实现。** 收益是只测公共接口（接口稳定 → 测试几乎不变）、AI 只读接口就能把握功能，最终**降低认知负担**。由此得到角色分工：**人类负责接口设计与模块设计，AI 处理大部分实现**；模块被当作**灰盒（grey box）**而不是纯黑盒，重心转向测试。

> **反模式**：**"为便于测试而提取纯函数"** 是 LLM 常给的伪解法。真正的错误往往藏在**调用方式**里，接口设计需要人类的语言与判断力。测试与结构怎么解耦、架构改进怎么变成流程，见 6.9 与 6.10。

### 1.9 人守在哪里 - 品味、验收与控制权

AFK 能替掉"实现"这一环，但流程里还有几段必须有人。需要人类的环节归为两类原因：**品味（human judgment）**与**质量保证**——前者包括审美判断、个人观点、给应用赋予情感温度，也关乎内部架构设计；后者指 AI 缺乏真实依据去验证目标，最终必须由人真正上手用一遍产品。

> "AI 能协助制定计划，但没有人类，它缺乏真实依据来验证目标。""如果你完全交给 AI 处理，最终会得到缺乏品味的应用程序，而且往往根本无法正常运行。"

判断标准不是"能不能自动化"，而是**"判断力与品味在哪里，人就回到哪里"**。与之配套的是两个区分：

- **HITL（人在环中）**：人全程盯着代理干活，需要架构决策、设计评审、原型迭代、人工 QA 的环节都属此类。
- **AFK（away from keyboard，离线）**：代理自主执行、人不盯屏，可无人实现并合并的任务属此类；**尽可能优先 AFK**。

**AX 优先于 DX（代理体验优先于开发者体验）**：开发者拿到大量文档只会快速浏览，**代理会照着文档行动**，所以重点是把文档写成代理能照做的形态。评审要同时看 **UX → DX → AX** 三个维度，AX 大致处在新的优先级顶端。

**团队怎么组织？** 合适规模约 **3–10 人**；**PRD 之前的一切必须是协作的**（一起开会、把会议记录喂给代理深化成 PRD、原型共享评审），PRD 达成共识后实现可以交给一个人，再做团队评审。PRD 必须放在**多人可审阅的地方**（GitHub issue / Jira / Linear），本地保存通常是个坏主意。哪些环节标 HITL、哪些标 AFK、QA 怎么做，见 6.6 什么必须留给人。

## 二 工具与上下文

### 2.1 工具层的取舍 - 干净的上下文优先

1.1 的六条约束落到 Claude Code 这一层，能动的只有上下文与记忆：`/clear`、`/handoff`、`/compact`，以及把探索分给子代理。课程的立场非常鲜明：**要优化的是"干净的上下文"，不是"记得多的上下文"**，由此得到一条偏好顺序（理由见 1.4 上下文纪律）：

```text
新建会话  >  handoff 分流  >  compact 压缩  >  一路自动压缩
```

本章按"先分流、再压缩、后清空"的顺序，讲清每种手段的触发时机、保留内容与反模式。

### 2.2 子代理 - 上下文保存机制

上下文窗口被切成系统提示、探索、实现、剩余空白几块。矛盾在于：探索少花 token 就能给实现留更多智能区，但探索不足又会让代理不了解代码库、实现质量下降。（P16）

解法是**子代理（subagent）**：由主代理新建一个**独立上下文窗口**，给它定制系统提示去干活，**只在子代理自己的窗口里大量烧 token，最后只把摘要交回主代理**。

- 可并行开多个；子代理可以使用不同系统提示与**不同（更便宜的）模型**，探索这类简单任务常用 Haiku，又快又好。
- 一句话记住：**"子代理是协调者代理的上下文保存机制。"**

![Orchestrator 主代理调度 Subagent 1 / Subagent 2，各自独立上下文窗口](/img/技术/ai-engineering/orchestrator-subagent-loop.png)

### 2.3 代码库探索 - 请把「探索」这个词说出来

同样一个需求，两种问法差别巨大（P17–P18）：

| 问法 | 结果 |
| --- | --- |
| "告诉我这个仓库的技术栈" | **不会**派探索子代理，全程只读了 6 个文件，分析不完整 |
| "**探索**这个仓库里 X 的原理" | 立即派探索子代理，读入大量文件、调用多个工具，耗时约 60 秒 |

子代理自己用掉了约 **32%** 的上下文，然后把摘要交给主代理，产出接近手写质量的深入解答。用 `Ctrl+O` 打开详细模式，可以看到它执行的所有 bash 命令和读过的每个文件。

### 2.4 清除优先 - 自动压缩的沉积物问题

`/context` 里能看到上下文末尾有一段**自动压缩缓冲区（auto-compact buffer）**，约 3.3k token。它不参与上下文窗口、不影响模型，只是一个预留区：一旦用量顶到它，就会自动触发一次 `compact`。（P26）

为什么不干脆一路自动压缩、让窗口永远用满？讲师给出的理由是**残留沉积物**：

> 每次回退并压缩，都会在上下文里留下一层沉积物；下次再顶到自动压缩区，再留一层。层层叠加会以不可预测的方式影响输出。每次与"上下文为空"的代理开始会话，输出都更可预测。

顺带两个好处：省掉压缩本身的 token 开销，且可用智能区更大，所以"代码质量输出通常更高"。讲师同时承认这是他的思维模型（也是社区多数人的观点），也确有人主张直接用自动压缩。

### 2.5 /compact - 什么时候压、压完留下什么

| 项目 | 结论 |
| --- | --- |
| 触发方式 | 自动（顶到缓冲区）或手动 `/compact` |
| 手动压缩可带指令 | **"我为什么要压缩 + 压缩完要做什么"**。例如："我已经实现了一个新功能，接下来想对实现做问答。" |
| 保留内容 | 所有用户消息（意图不丢）、文件与路径引用（"模型知道计划文件存在"）、待办任务与附加指令、完整对话记录文件（需要时可回查原始对话） |
| 查看方式 | `Ctrl+O` 看完整摘要，再按一次退出 |
| 耗时 | 约一到两分钟，取决于对话大小 |
| 压缩后的用量 | 讲师演示里从满窗压到约 12k token |

**使用边界**：讲师自己"很少压缩"，只在两种情况下用（P26）：

1. 刚做完一个大会话，还想在它上面追加反馈；
2. 调试复杂错误时，用收集到的大量信息和错误填满了窗口，不想因为 `/clear` 丢掉。

**反模式**：重复压缩同一个对话。每压一次就多一层无关的混乱上下文。

### 2.6 /handoff - 把独立小任务剥出去

`/clear` 有个解决不了的情况：**主线任务还没做完，中途冒出另一件事**（要改的文件、要修的失败测试）。这时既不该污染当前会话，也不该清掉正在做的任务。（P27）

`handoff`（交接）的做法是：把当前会话压缩成**一份临时 Markdown 交接文档**，路径由 `mktemp` 生成，用于跨代理、跨会话交接。它的规矩很讲究：

- **不要重复其他工件里已有的内容，只加链接**；只有重要信息才写进去。
- 文档里要**建议后续会话使用哪些技能**。
- 如果你给了指令，它会把这条指令当作**下一阶段的聚焦描述**来调整文档。这一点非常重要：交接文档是按"下一步要干什么"定制的。

典型用法：实施中测试挂了 → "把修这个测试交接出去"；grilling 会话太长 → 把需要深入的部分转到新会话；做原型/研究 → 把成果浓缩成交接文档。

> **一句话总结**：交接让你在会话之间传递文档。整体模式是**先扩展、再收缩**。

## 三 记忆与技能

模型无状态，所以"记忆"必须外置。课程把这件事分成三层：**常驻记忆（CLAUDE.md / AGENTS.md）→ 按需指令（技能 SKILL.md）→ 自动积累（auto-memory）**。

### 3.1 CLAUDE.md 与 AGENTS.md 的关系

**它们本质是同一个东西**，区别只在 Claude Code 只听 `CLAUDE.md`。（P28）

### 3.2 CLAUDE.md 的真实定位 - 一张地图，不是仓库

讲师对这个文件的判断有几点反直觉但很重要：

1. **放进去的内容必须对每一次请求都相关**。只能处理前端代码时，位置参数、service 约定、数据库 ID、时间戳这些指令完全用不上，却每次都占着 token。演示里一个 2000 行的记忆文件占了约 **10%** 的上下文。
2. **它常被忽略，而且这是设计如此**。Claude Code 会注入系统提示告诉模型：你的 `CLAUDE.md` 已作为提醒放在用户消息里，"此上下文可能相关也可能无关，除高度相关外不应回应"。
3. **不要用 `/init` 自动生成**。它会把代理自己就能发现（如 `package.json` 里的 scripts）、且很快过时的内容写进去，还会因为忘记同步而失真。
4. **运行中改 `CLAUDE.md` 不会立即生效**，要等新会话；想保留当前上下文，就明确要求它"按更新后的 `CLAUDE.md` 重新审查你的工作"（代价是始终处在智能区边缘）。

### 3.3 渐进式披露

> **progressive disclosure** 源自 UI/UX：糟糕的界面把所有可用操作堆在一个巨大屏幕上让人滚动选择；好界面先给少量选择，让用户基于少量选择逐步发现信息。（P31）

套到提示工程上就是：**并非所有指令都适用于每个请求**。把每条指令想象成上下文窗口里的一个灰块（React 相关一组、数据库相关一组、路由相关一组），正确的做法是**每个分组一个独立 markdown 文件，`CLAUDE.md` 里只留指向它们的链接**。

> **金句**："与其一次性抛出所有复杂性，你只需给他们一张地图，并允许他们自行导航。"

### 3.4 技能 - 渐进式披露的正式载体

**Agent Skills** 是 Anthropic 提出并开源的开放格式，已被各编码代理广泛接受。要点（P32）：

- **一个技能就是一个包含指令的文件夹**，里面可以放脚本、图片、参考文档等任何资源；关键在"**可被发现**"。
- 默认情况下，**只有 `name` 和 `description` 对代理可见**；真正被选中调用时，指令才全部进入上下文。这就是渐进式披露的落地形态。
- 位置：项目内（如 `.claude/skills/`）或用户全局作用域。**项目级技能更容易与团队共享**。
- `/skills` 列出所有可用技能；输入技能名回车调用；`ESC` 关闭。

技能文件 `SKILL.md` 顶部的 YAML frontmatter：

```yaml
---
name: 技能名
description: 何时使用此技能、解决什么问题（触发条件写在这里）
---
```

### 3.5 把上百行编码规范改造成技能

思路是"**用技能来写技能**"：调用一个"编写技能"的技能，要求它把 `CLAUDE.md` 里的规范找到渐进式披露的落地方式。产出结构（P33–P34）：

```
.coding-standards/
├── SKILL.md                 # 简短，指向下面的参考文件
└── references/
    ├── database.md          # 数据库相关规范
    ├── frontend-ui.md       # 前端 UI / 根目录与表单
    ├── services-and-testing.md
    └── ...
```

改造完之后，`CLAUDE.md` 只剩**一句短指针**："在编写代码前加载该技能"。

讲师把 `CLAUDE.md` 里的链接和技能 description 称为 **上下文指针（context pointers）**，并建议**双指针策略**：`CLAUDE.md` 里的小链接 + 技能自身的 description 同时指向该技能，**命中率更高**。

好处很直接：参考文件可以无限增长，**不会膨胀父级上下文**（只加载用到的那份），还能跨仓库共享，保证所有项目遵循同一套规范。

### 3.6 自动记忆

`/memory` 会展示三类记忆：用户级 `CLAUDE.md`、项目级 `CLAUDE.md`，以及一个开放的**自动记忆文件夹**（例如某个项目自己长出来的 `memory.md`，里面写着"用 `npm install --legacy-peer-deps` 而不是 `npm install`""测试里 `vi.mock` 会被提升""用 `pg-lite` 做数据库测试"这类具体经验）。（P35）

讲师的态度是"功能还新，尚不确定该怎么看"，但他点出了最让人担心的问题：

> 记忆系统与仓库的实际状态**不同步**。

所以做法是：**每隔几周**检查一次那份 `memory.md`，删掉模型本可自行解决的问题（`vi.mock` 提升、`pg-lite` 用法之类），清掉奇怪与冗余的条目。

### 3.7 大任务 - 目标文档 + 旅程文档

任务一旦大到装不进智能区（章节级重构、需要提前规划的功能），解法还是几十年不变的老办法：**拆**。缺的是**跨多个上下文窗口的文档集合**，社区已经形成两种文档的通用模式（P36）：

| 文档 | 别名 | 回答的问题 |
| --- | --- | --- |
| **PRD / 规格说明** | 目标描述 | "我们要到哪去" |
| **plan（计划）** | 旅程描述 | "怎么走过去，分几步" |

![PRD.md 是目的地、PLAN.md 是旅程，两者按阶段推进](/img/技术/ai-engineering/prd-plan-smart-phases.png)

下发给代理的提示固定包含三要素：**执行第 n 阶段 + PRD + 完整计划**。

> 讲师特别解释了为什么连**完整计划**也要一起传：**"传入整个计划非常有用，因为它确保各阶段不会互相冲突。"**

## 四 需求与计划

### 4.1 先判断 - 这个任务需不需要拷问

拷问不是仪式，用错了就是浪费。判断标准很简单：

| 情况 | 要不要 grill | 理由 |
| --- | --- | --- |
| 任务非常明确、你知道要改哪里、能把它完整描述出来 | **不要** | 此时 grill 会过度，直接做 |
| 需求模糊、设计概念还没对齐（"我也想不清到底要什么"） | **要** | 拷问的本质就是**和 AI 对齐** |
| 涉及外观/交互的决策 | 文字不够，要先做原型 | 涉及外观的决策光靠文字答不了 |

排优先级用《Shape Up》里的**精细度（fidelity）**：**文字最低，然后线框，再是原型，最高是实际应用**。默认用最低精细度成本最低，但涉及外观的决策光靠文字根本答不了。

**检查清单**

- [ ] 需求真的模糊吗？明确的任务直接做，不要走仪式。
- [ ] 需要看效果才能决策的，是否先做原型，而不是硬用文字讨论外观？
- [ ] 是否做到"一次一个决策"，并主动采纳/否决它的推荐答案？
- [ ] 面对不可逆决策，是否问过"哪个方案最难回退"？

### 4.2 grill-me / grill-with-docs 的工作方式

**`grill-me`（现 `grill-with-docs`，底层共用 `grilling` 原语）的工作方式**（P38）：

- 它是一轮**苏格拉底式、对抗性提问**：一次可能上百个问题，直到共识达成。
- 它**一次只问一个问题**，逐层推进设计树的每个分支，并逐一解决决策之间的依赖关系。
- 它**自己给推荐答案**，最喜欢你直接采纳或否决，而不是列 a/b/c 让你猜。
- **代码库能回答的问题，它自己去探索**，所以不会拿错误的问题浪费你的时间。

**两个纯偏好开关**

`AskUserQuestion` 是 Claude Code 一个多选式的"向用户提问"界面，好处是把问题结构化，坏处是"用方向键在选项里导航，比直接读它的文字回复更累"。讲师第一次见时觉得惊艳，但最终还是**在全局 `CLAUDE.md` 里写了"不要使用 AskUserQuestion 工具"**，从此再也没看到那个界面。

- **想用**：在提示或技能里写"使用 AskUserQuestion 工具"，几乎所有技能都能启用。
- **不想用**：在全局 `CLAUDE.md` 里禁用它。

> 讲师的定性是："这是百分之百的个人偏好。"关键是**让它成为一个显式决定**，而不是默默干扰你的工作流。

另一个开关是**精细度判断"足够好"的标志**：决定成败的最关键问题是否已经被回答。不重要的决策直接说"**我不在乎**"，把优先级让给更重要的事。

### 4.3 write-a-prd - 把对话固化成目标文档

写完（或问到共识）之后调用 `write-a-prd`（现 `to-spec`）（P37–P38）：它**不访谈，只综合当前对话**，先探索代码库了解现状，再按模板落文档。**这一步只产文档，不实施。**

PRD 的模板结构：

| 段落 | 内容 |
| --- | --- |
| 问题陈述 | 从用户视角描述现在面临的问题 |
| 解决方案 | 同样从用户视角描述要做什么 |
| **编号的用户故事列表** | 谁 + 做什么 + 为什么；每条可在拆任务时逐条引用 |
| 主要模块 | 需要新增/修改的模块（这一节是后加的"预防层"） |
| 技术决策 | 依赖、模式、路由等**不易变更**的决策 |
| 测试决策 | 测试写在哪、怎么 mock、是否用测试库 |
| **超出范围（out of scope）** | 明确不做什么，防止文档越界 |
| 备注 | 人工补充的注记 |

**案例：讲师分析仪表盘（P38）**。这个需求"内容充实、页面庞大、可能演化出多种形态"，非常适合先 grill 再 PRD。几个决策很能说明讲师是怎么用人的判断力压住 AI 的：

| 议题 | AI 的初始建议 | 讲师的决定 | 理由 |
| --- | --- | --- | --- |
| 核心指标 | 销售、完成率、流失、评分 | 收回为**以收入为核心，评分只作点缀** | IP 归属数据不可靠、地理数据可能失控 |
| 时间维度 | 终身总值 | **带范围选择器的时间序列**（7 天 / 30 天 / 12 个月 / 全部），范围作为实现细节**放进 URL 参数** | 可分享、可回退、可深链 |
| 图表 | 每门课一条线 | **单条聚合折线图** + 底部可排序表格；7 天分 7 组、30 天分 30 组、12 个月分 12 组；**零美元的分桶也要渲染** | 避免"每门课一条线"的信息过载 |
| 图表依赖 | 用 shadcn 包装组件 | **直接用 bare `recharts`**，不包装、不引入多余依赖 | 少一层抽象就少一个会过时的地方 |
| 注册与销售 | 当成一件事 | **明确区分**：团队会批量采购 | 领域知识只有人知道 |

产出的 PRD 里，`analytics service` 被明确定义为**封装全部数据库查询的深层模块**。

绿地项目（greenfield）的 PRD 与棕地不同：它必须在写需求之前先敲定架构设计与代理体验（反馈循环、格式规范、技术选型、模块结构、测试策略）。流程与清单见 6.11 绿地项目。

**检查清单**

- [ ] PRD 里是否有**编号的用户故事**，以及明确的 **out of scope**？
- [ ] 是否草拟了主要模块与测试位置（预防浅层模块）？
- [ ] PRD 落在团队能审阅的地方（GitHub issue / Jira / Linear），而不是只存在本地？

### 4.4 把「模块意识」前移到 PRD

光靠"事后重构"来救架构是不够的，所以要**预防与治疗并行**。具体改动很小但影响很大：

> PRD 技能从**两步变成三步**：在写模板之前，先**草拟实现所需或要修改的主要模块**，主动寻找"可独立测试的深层模块"的机会。

这一步让模块意识出现在最关键的时刻（设计新实现方案时），顺带回答另一个问题：**这些模块的测试写在哪**。结果是正确接口会被测试覆盖，TDD 循环被严格执行，**浅层模块从源头上被挡在门外**。

### 4.5 计划 - 垂直切片（曳光弹）与多阶段计划

**先看清天真方式错在哪（P39–P40）。** 提示极其简单：`@` 引入 PRD → "把它转化为多阶段计划，保存为本地 markdown 文件"，就这三件事。产出也很快，几乎没有追问，计划直接落到 `plans/analytics-dashboard.md`，拆成四个阶段：

| 阶段 | 内容 | 问题 |
| --- | --- | --- |
| 阶段 1 | 完整的分析服务（含测试） | 此时还不可能确定服务设计，测试基本无意义 |
| 阶段 2 | 后端架构 + 共享仪表盘组件 + 安装 `recharts` | 还没人用上这个组件 |
| 阶段 3 | 在根目录真正使用该 UI | 引用了当时还不存在的功能 |
| 阶段 4 | 管理员分析路由与用户页面链接 | 与阶段 3 高度相似，本可合并 |

问题清单很典型，值得当成"计划坏味道"背下来：

1. **横向（水平）展开**：按"数据库 → API → 前端"逐层做完，导致**直到后期阶段才能拿到"整个系统能不能工作"的反馈**。
2. **写死了实现信息**：具体函数名、步骤详实到像实施指南，早期阶段一改实现方式就全部过时。
3. **没有引用 PRD 的用户故事**，无法把阶段链接回需求。
4. 阶段量估算合理、整体清晰，但**第三、四阶段重复**。

> **金句**："所有工作都在水平层展开，这正是它的问题所在。"

![LLM's Code Horizontally：按 Phase 逐层横向铺开，到后期阶段才能验证整个系统](/img/技术/ai-engineering/llm-codes-horizontally.png)

**追踪子弹（曳光弹）与垂直切片（P41）。** 只用两个精心挑选的词，就能改变代理的任务优先级：**tracing bullet（追踪子弹 / 曳光弹）**。概念出自《程序员修炼之道》（The Pragmatic Programmer）：

> 二战时机枪每几发装填一发曳光弹，发光的轨迹让防空炮手看见弹道并据此修正射击。寓意就是**尽早反馈、频繁反馈**。

系统的层次（数据库、API、前端）必须**集成**才能构成可用系统，而 LLM 在设计计划时总是按层思考，于是反馈来得太晚。改法是让**每个阶段都穿透每一层**，这还有一个别名：**垂直切片（vertical slice）**。

![Use Tracer Bullets：每个阶段纵向穿透所有层，尽早集成、频繁反馈](/img/技术/ai-engineering/use-tracer-bullets.png)

为什么有效：每个阶段都贯穿全栈，**人类可以在每个阶段结束后介入查看并反馈**，架构失误的概率明显下降。而且代理本来就懂这个概念，你只要说出"使用曳光弹"再加一句简短解释即可。

**`prd-to-plan`（现 `to-tickets`）：把修好后的做法固化成技能（P42–P43）。** 评估新技能时要**做干净测试**：新建无上下文的会话，**并先删掉上一轮生成的旧计划**，避免模型读到旧版本；一次只改一个变量，才能判断改进来自技能还是随机波动。

跑出来的计划有几个明显提升：

- **先探索**代码库架构，而且探索阶段使用**更便宜的模型**（讲师提到 Sonnet 4.6），是资源的有效利用。
- **先让你对阶段划分给反馈，确认后才落计划文件**。
- 第一阶段 = "分析服务 + 讲师路由 + 摘要卡片"，用最简数据、三个核心指标做**全栈串联的快速验证**，把所有"未知的未知"、奇怪限制一次性暴露出来。
- 五阶段收敛为**三个阶段**（合并两处 UI 阶段；管理员权限与空状态虽不相关，但触及同一代码区域且都很小）。
- **几乎没有实现细节泄漏**：旧计划近乎伪代码，新计划更像纯文本的功能描述。原因是技能里有一条明确指令：**只制定跨所有阶段都有效的决策**。

> **金句**："不要规划那些你无法计划的事情，很多东西只有真正开始实施时才会显现出来。"

当然计划仍要保留必要的实现信息（依赖、怎么从仓库取当前用户 ID、是否放根目录这类模式），以保持流程顺畅。

**逐阶段执行的节奏（P44–P45）。** 执行提示 = **PRD + 计划 + "执行第 n 阶段"**。用 `Shift+Tab` 进入接受编辑模式，**不要用 plan mode**。实测节奏与经验：

| 观察 | 数值/做法 |
| --- | --- |
| 探索阶段耗时 | 约 1 分钟，代理会给自己创建多个任务 |
| 测试情况 | 第一阶段 12 个测试全部通过 |
| `/clear` 时机 | 约 **30–35%** 就清（"继续留用会让后续阶段挤在残量上下文里"） |
| 清空后的代价 | 代理需要约 30 秒重新探索上一阶段的实现，属于"令人烦恼的重置" |
| 每阶段收尾 | **先 `/clear` + 再 `git commit`**，提交是安全回退点 |
| 顺手修 bug | 同一会话里追加"图表上看不到任何线条，请添加它们"，它给出了良好修复 |
| 提交信息 | 让 Claude 生成。**"代码与变更原因紧密关联，旧的即是新的，提交信息又变得重要了。"** |

讲师还顺手抓到一个设计问题：无权限时返回 `401` 不如返回 `404`——"应说明页面不存在，而不是页面存在、你入侵失败"。这类问题当场记入待办，而不是只在对话里抱怨。

**检查清单**

- [ ] 计划是**垂直切片**（每个阶段穿透所有层）而不是横向分层吗？
- [ ] 计划里有没有写死函数名/伪代码级的实现细节？越像伪代码，过时越快。
- [ ] 每个阶段是否引用了 PRD 里的用户故事编号？
- [ ] 阶段粒度给过你反馈吗？触及同一区域的小阶段可以合并。
- [ ] 每阶段结束是否 `/clear` + `commit`？是否在 30–35% 就开始安排清空？
- [ ] 手头是否始终有一个**带 QA 清单的最终验收 issue**？

## 五 实现与验收

### 5.1 反馈循环 - 让代理能自己判断对错

（P49–P50）

**必须让代理能自己验证对错，而不是靠你事后检查**。

**反馈循环**不是新发明，它是成熟工程师的既有实践（因为优秀工程师从不相信自己的一次性产出），只是现在由代理来跑：

```text
代理生成代码 → 跑检查（类型/测试/格式） → 据结果修正 → 再生成 → …直到质量达标
```

### 5.2 红绿重构 - 让实现这一步提升质量

（P56–P58）

技巧来自 Kent Beck《极限编程实践》的 **red-green-refactor**（测试驱动开发的核心）。三个步骤：

| 步骤 | 做什么 |
| --- | --- |
| 🔴 红 | 先写一个**会失败的测试**并**运行它确认失败** |
| 🟢 绿 | 写**最小实现**让测试通过 |
| 🔁 重构 | 整理代码、提升质量，期间持续跑反馈循环 |

**为什么对 AI 尤其关键**：

- 它**迫使生成的代码可测试**，而可测试就意味着便于修改（测试会捕获错误）；
- **失败测试较难伪造**。

#### 承载它的 `tdd` 技能

```markdown
# Test-Driven Development

TDD is the red → green loop. This skill is the reference that makes that loop produce tests worth keeping: what a good test is, where tests go, the anti-patterns, and the rules of the loop. Every section applies on every cycle — consult them before and during the loop, not after.

When exploring the codebase, read `CONTEXT.md` (if it exists) so test names and interface vocabulary match the project's domain language, and respect ADRs in the area you're touching.

## What a good test is

Tests verify behavior through public interfaces, not implementation details. Code can change entirely; tests shouldn't. A good test reads like a specification — "user can checkout with valid cart" tells you exactly what capability exists — and survives refactors because it doesn't care about internal structure.

See [tests.md](tests.md) for examples and [mocking.md](mocking.md) for mocking guidelines.

## Seams — where tests go

A **seam** is the public boundary you test at: the interface where you observe behavior without reaching inside. Tests live at seams, never against internals.

**Test only at pre-agreed seams.** Before writing any test, write down the seams under test and confirm them with the user. No test is written at an unconfirmed seam. You can't test everything — agreeing the seams up front is how testing effort lands on the critical paths and complex logic instead of every edge case.

Ask: "What's the public interface, and which seams should we test?"

When the shape of that interface is itself in question — how deep the module is, where the seam belongs, what the interface should expose — use the `/codebase-design` skill for the vocabulary. It is the shared source of the module, interface, depth, seam, adapter, leverage and locality terms, and it is a reference to consult, not a session to run.

## Anti-patterns

- **Implementation-coupled** — mocks internal collaborators, tests private methods, or verifies through a side channel (querying the database instead of using the interface). The tell: the test breaks when you refactor but behavior hasn't changed.
- **Tautological** — the assertion recomputes the expected value the way the code does (`expect(add(a, b)).toBe(a + b)`, a snapshot derived by hand the same way, a constant asserted equal to itself), so it passes by construction and can never disagree with the code. Expected values must come from an independent source of truth — a known-good literal, a worked example, the spec.
- **Horizontal slicing** — writing all tests first, then all implementation. Bulk tests verify _imagined_ behavior: you test the _shape_ of things rather than user-facing behavior, the tests go insensitive to real changes, and you commit to test structure before understanding the implementation. Work in **vertical slices** instead — one test → one implementation → repeat, each test a **tracer bullet** that responds to what the last cycle taught you.

## Rules of the loop

- **Red before green.** Write the failing test first, then only enough code to pass it. Don't anticipate future tests or add speculative features.
- **One slice at a time.** One seam, one test, one minimal implementation per cycle.
- **Refactoring is not part of the loop.** It belongs to the review stage (see the `code-review` skill), not the red → green implementation cycle.
```

### 5.3 `implement` 技能 - 一个工作单元怎么走完

（P51–P52）

**`do-work`（现 `implement`）技能**代表"仓库中的一个工作单元"，最终被压缩成五行：

```markdown
1. 理解任务
2. 如果任务尚未规划，创建计划（已规划则跳过）
3. 实施
4. 跑反馈循环验证（typecheck + test），持续到全部通过
5. 提交
```

#### 本机的 `implement` 技能

课程里的 `do-work` 就是现在的 **`implement`**：

```markdown
Implement the work described by the user in the spec or tickets.

Use /tdd where possible, at pre-agreed seams.

Run typechecking regularly, single test files regularly, and the full test
suite once at the end.

Once done, use /code-review to review the work.

Commit your work to the current branch.
```

逐条读下来，它把整条流水线钉在了五个点上：

#### 让检查变成确定性：pre-commit 钩子

到这一步，反馈循环还只是被"鼓励"运行。要变成**确定性**，要用 git hook：

```bash
# .husky/pre-commit
npx lint-staged        # 只对暂存文件跑 prettier
pnpm run typecheck     # 全仓类型检查
pnpm run test          # 全量测试
```

### 5.4 双轴评审 - 规范 Standards 与规格 Spec

（P89–P92）

**流水线**：**实施 → 自动化检查（测试、类型检查、pre-commit、格式化）→ 自动化审查 → 人工审查**。

**自动化审查只查两件事**：**是否符合规格**（PRD 是否被正确实现）、**是否符合编码规范**。关键判断是：**把编码规范从"实施"移出，只给"评审"看**——实施要探索代码、推进功能、防错调试，预算已经很满；规范作为单一来源出现在评审阶段，反而提升质量。

## 六 离线执行与人工协同

前面几节都在解决"人盯着代理干活"的效率问题。这一章是**核心论点落地**：把实现阶段变成**离座也能运行（AFK, away from keyboard）**的自动化。讲师的原话是："从反馈循环到规划、到规格说明、到探针代码，这一切都指向这里。"

### 6.1 什么时候可以离线 - 2025 年 12 月的转折点

（P59）

多阶段计划的最后一个痛点是：**阶段指令还得人来下**。"执行第一阶段""执行第二阶段"这件事本身是循环结构，内部流程早就自动化了，只有"选哪个阶段"还挂在人身上。讲师说得很直接：只要你盯过代理干活，就会觉得"我根本不必在场"——目的地明确、路线规划完毕，剩下的是在终点收结果。

转折点有两件事：

1. 2025 年 12 月模型强到**可以完整委托明确任务并出色完成**；
2. 读了 Geoffrey Huntley 关于 **Ralph Wiggum** 的文章后意识到：**用一个简单循环反复执行同一个提示**就能完成分阶段工作。他最初照搬 Ralph 的做法，后来逐渐偏离，于是把这种模式命名为 **AFK agent**。

> **前提**：AFK 不是免费的自动化，它依赖前面所有投入先到位——反馈循环、规划、规格说明、探针代码。

### 6.2 先跑通 HITL 骨架

（P61–P62）

不要一上来就无人值守。先用一个交互式脚本把骨架跑通，观察它一次只做一件事：

| 文件 | 作用 |
| --- | --- |
| `interactive.ts` | 交互式入口，接收 PRD 位置与计划位置 |
| `prompt.md` | 提示模板，用 Sandcastle 的**沙盒提示扩展语法** |

扩展语法的关键一条：**反引号代码块前加 `!` 会就地执行该命令，并把输出插入提示中对应的位置**（例如用 `cat` 读文件路径、通过位置参数把 PRD 与计划位置传进去）。提示末尾约定：任务耗尽时输出 **"无更多任务"**，作为**完成信号**。

**关键约束：只处理当前这一个任务。** 如果它想在一个上下文窗口里做完整个多阶段计划，就会陷入低效。

实测结果（只跑第一阶段）：它自觉只实现一个阶段，根目录精简、没堆 UI，写了很多代码并提交；验收（管理员登录 → 分析模块 → 切时间范围）通过。运行时它仍会**请求运行反馈循环的权限**，说明此时还没有真正离线。

> **一句话总结**：**"一旦去掉权限请求，就能形成一个可反复运行的小循环，持续产出代码。"**

### 6.3 沙盒化 - yolo 模式必须先隔离

（P63）

Claude Code 的 **yolo 模式**（跳过全部权限请求）官方文档明确写着"只在隔离容器和虚拟机中使用"。讲师给出三类真实风险：写出删除整个 home 目录的脚本、把可能涉及公司机密的信息外泄到奇怪的 API、被**提示注入**操纵。

他试过 Claude 自带的 sandbox，结论是**不可用**：

> "Claude 实际上可以突破沙盒，这让我根本无法信任它以 yolo 模式运行。"

于是他做了 **Sandcastle**，用 Docker 沙盒把代理关进容器：容器**能访问系统与仓库**（仓库被挂载进去），但**只能编辑你选择的目录**，看不到电脑其他地方，任何 bash 命令也都在容器内执行。

| 环节 | 做法 |
| --- | --- |
| 镜像 | Dockerfile 基于 Node 22，装好 Claude Code、加入 PATH，`WORKDIR` 设为 `/home/agent`（预装 GitHub CLI） |
| 运行时 | Docker Desktop，或免费开源的 **Podman**（对大组织也免费；Docker Desktop 有许可限制） |
| 配置 | 复制 `.env.example` 为 `.env`，填入要传进容器的环境变量 |
| 构建 | `pnpm sandcastle docker build-image` |
| 冒烟测试 | `npx tsx .sandcastle/test.ts`（发一句"你好吗"，日志里可点链接看实时日志） |
| 认证 | 建议直接用 **Anthropic API key**（想复用 Claude 订阅 token 的问题当时因法律问题仍挂着） |

> **金句**："没有直接监督时，Claude 可能会做蠢事，所以我们必须把选项集限制到最小。"

**检查清单**

- [ ] 沙盒先于 yolo：代理是否只能看到挂载进来的仓库目录？
- [ ] 认证是否用 API key（而不是订阅 token）？

### 6.4 AFK 脚本的三个要素

（P64–P65）

把交互式脚本改成无人值守的 AFK 脚本（`main.ts`），它直接接收两个位置参数：PRD 位置、计划位置。与交互式版本的关键差别只有三点：

1. 用 `run` 而不是 `interactive`；
2. 加入**最大迭代次数**；
3. 加入**完成信号检测**。

```bash
npx tsx .sandcastle/main.ts admin-analytics.md admin-analytics-plan.md
```

关于迭代次数，讲师的实践经验很实用：

> 我自己跑的时候经常遇到**完成信号不灵**，所以我通常把迭代次数设得极大：10、15，有时 50。（课程为省 token 才设得精简。）

实测过程（P65）：讲师中途离座去泡茶，回来时**代码已经可运行**。代理自动推进了阶段——给分析仪表盘加 recharts 折线图、做类型检查、跑测试、处理语法错误，并自己 `git add` / `git commit`；因为上一阶段没检测到完成信号，它继续进入第三阶段；最终触发"不再有任务"，两次迭代后终止，打印出各阶段的上下文窗口占用（64k、80k）。

> **金句**："我完全认为这是开发的未来——你与代理并行工作，你做其他事，而代理在处理任务。"

**检查清单**

- [ ] 是否设置了足够大的 `max iterations`（10–50）并同时约定完成信号？
- [ ] 一轮循环是否**只处理一个任务**？

### 6.5 待办队列 - 让代理自己挑下一个任务

（P66–P70）

硬指向"某个 PRD + 计划"的代理做完就消失了。要让它连续运转，需要**队列**：

**① 队列从哪来**。PRD 末尾放一个 **todo queue**，或在 issue 跟踪器里维护开放任务。代理完成一个任务后，问"下一个最重要的任务是什么"，然后自己挑一个。优先级是：关键 bug → 开发基础设施 → 快速验证 → 快速胜利 → 重构。一次可以吞吐 20–30 个任务，用标签（如 `ready-for-agent`）筛出真正开放给代理的集合。

**② 用 GitHub issue 当队列并闭环**（P68–P69）：

```
gh 取回所有开放 issue（JSON：编号 / 标题 / 正文 / 评论）
   ↓ 任务选择提示挑一个
实现 → 提交
   ↓ 回到原 issue
完成 → 关闭 issue；未完成 → 留一条评论说明进度
```

通过 GitHub CLI（`gh`）通信是"很优雅的方式"，因为**模型对 `gh` 非常熟悉且极少出错**。issue 评论会自动成为该任务的**执行记录**，并在下一轮被拉进代理上下文——如果你把多阶段计划写在 issue 里也完全可以。

实测效果：代理定位到根因（表单走客户端导航提交，打开状态一直为 `true`，下拉菜单从不关闭），改代码、提交、关单并评论，pre-commit 全部通过，全程只用了约 **30k** 上下文窗口；GitHub 上变成"0 个开放、1 个已关闭"，关闭的那条带着说明文字，可观测性很好。

> **安全提醒**：给代理的 GitHub 令牌必须是**细粒度、最小权限**：只允许读 issue、评论、关闭 issue，**连创建新 issue 都不允许**。

**③ 先建自己的仓库**（P67）。直接克隆课程仓库的话，你创建的 issue 会进入**公共池**、推进讲师的仓库，全班学生共用一个 issue 仓库会是灾难。做法是复制目录 `cohort-04-project-fork`、**删除全部 Git 历史**、新建自己的 GitHub 仓库。

**④ 让规划与实施并行**（P70）。最后一个小改动带来最大的结构收益：把 PRD 与计划技能从"生成本地文件"改成"**创建 GitHub issue**"。这样规划循环**完全不碰代码库、不产生本地文件**，也就不会干扰正在仓库里干活的 AFK 代理。

> **金句**："这个循环非常酷，因为它让规划与实施并行进行。"

**检查清单**

- [ ] 队列是否有明确优先级，并且那份挑选提示是你审过的？
- [ ] GitHub 令牌是否收窄到最小权限？
- [ ] issue 是否被闭环处理（关单或留评论）？
- [ ] 规划是否会写进 issue 而不是本地文件（以便与实施并行）？

### 6.6 什么必须留给人

（P71）

AFK 能替掉"实现"这一环，但七阶段流程里还有三段**必须有人**：筛选（品味）、研究（方向选择）、QA（真实性验证）。讲师把需要人类的环节归为两类原因：

| 原因 | 具体表现 |
| --- | --- |
| **品味（human judgment）** | 审美判断、个人观点、给应用赋予情感温度。这不只关乎外部用户体验，也关乎内部架构设计 |
| **质量保证** | AI 缺乏真实依据去验证目标，最终必须由人**真正上手用一遍产品** |

> **金句**："AI 能协助制定计划，但没有人类，它缺乏真实依据来验证目标。""如果你完全交给 AI 处理，最终会得到缺乏品味的应用程序，而且往往根本无法正常运行。"

判断标准不是"能不能自动化"，而是"**判断力与品味在哪里，人就回到哪里**"。

### 6.7 研究 - 把最贵的那一步前置缓存

（P75–P77）

**为什么需要研究**：AFK 循环每跑一个窗口，都包含"探索 + 实施 + 测试"三段，其中探索最贵。如果同一个大循环跑十次，**探索开销就被重复支付十次**。解法是**前置**：在真正进入循环之前，把完成 PRD 所需的外部知识**缓存成本地 Markdown**（`research` 文档）。

研究属于 **HITL 任务**，因为**你的品味决定研究方向**：外部服务往往有多种接入方式（流式、webhook、轮询），哪些内容进文档由你定。

**案例：课程实时在线状态指示器（P76–P77）**。需求是"显示正在同时学习同一门课的学生迷你图标，有人进入就加、退出就减"。代理先探索技术栈，发现项目**没有任何既有实时基础设施**，随后**首次启动后台并行子代理**，分别研究 PartyKit、Pusher、Ably、Liveblocks 的权衡；讲师反复追问规模预期（约 20 名学生同时在线）与 UI 细节，并**明确否决**了"光标滚动位置"这类复杂需求。最终选 **Ably**：有慷慨的免费套餐，倾向托管式 API key 服务。

产出的研究文档近两三百行，包含：需求、推荐方案、实施方案设计、现有代码库的集成点、**考虑的替代方案**（即使不用也算 **ADR 架构决策记录**，用来解释"为什么这样决定"）。这份文档随后直接成为 PRD 的输入。

**放哪里、什么时候删**：放本地仓库（而不是 GitHub issue），因为**希望实现者（AI）能极容易发现它**，也便于在 PR/issue 里引用。但研究文档必须**有生命周期**：

> 一旦弃用 Ably 或 Ably 改了 SDK，研究会完全过时并**主动伤害**在这个代码库工作的代理。所以讲师倾向于**积极删除**，需要时从 Git 历史里捞；建议在 AFK 循环与 QA 都结束后删除。

### 6.8 原型 - 把「未知的未知」尽早揪出来

（P78–P81）

原型是几十年的老技术：客户说不清需求时就给个能操作的原型让他试。**与研究是天生一对**：先研究各种可能选项，再为选项做原型，人类质检原型并反馈、迭代，选出最佳方案，再进入 PRD。

| 该做原型 | 不该做原型 |
| --- | --- |
| 大型项目、代码库里**没有先例**的部分 | bug 修复（我们知道所需行为，只是还没达成） |
| 测试新库、新服务（在临时仓库里让它充分试玩） | 扩展现有功能（通常只是组合既有能力） |
| **重新设计整个系统** | —— |

**`prototype` 技能有两个分支**：

- **UI 分支**：在**单个路由生成多个截然不同的 UI 变体**，用屏幕底部的切换工具条左右对比，可以直接迭代、互相借鉴（"我喜欢 A 的外观，但可以从 C 借一些元素"）。
- **逻辑分支**：构建小型**交互式终端应用**，推演难以在纸上想清的复杂场景（复杂数据模型、随时间变化的内容），用按键推进时间进程。

**案例（P79–P80）**：给 Ably 做原型时，讲师特意要求把原型放在**临时路由、仅开发者可见**，并**保留 TDD 式反馈循环与严格代码规范**。结果是产出**可复用、可导出的原型组件**——设计上能直接从原型里提取并嵌进真实应用，让后续 AFK 实现变得非常简单，还附带测试方法。多标签页验证"进入即显示、退出即消失"后，结论是：

> "所有未知的未知数都已显现，服务确认可用，剩余接线都确信能解决。"

原型本身属于 **HITL 工作**：虽然可以离开回来看，但**与原型紧密迭代、和 AI 即时互动收益更大**。

### 6.9 为 AI 设计代码库 - 深模块

（P82）

这是整门课**最有长期价值**的一节。前提判断：

> 当前一代 AI 代理并不擅长思考软件架构，它们通常设计出**自己都难以使用**的系统。"为 AI 组织代码库"将成为一项核心技能。

**糟糕的代码库长什么样**：散布数十个细小模块，每个模块只有几个导出函数。AI 要找到正确的代码，必须理解哪些模块被导入、沿整条导入导出链追踪，无法一目了然地定位功能。小模块同时毁掉反馈循环：测试只能逐个模块单独写，无法验证各部分如何协同；模块一变测试就得改，因为**测试与结构过度耦合**。

人类能靠直觉建立"代码库记忆"（这片文件管认证、那片是 API 层、这个组件关联某功能），**AI 没有这个优势**，进入糟糕代码库必须从头重建所有关系。

**解法是深模块（deep module）**，概念来自 Ousterhout：**一个薄薄的接口，加上后面厚重的实现**。

| 收益 | 说明 |
| --- | --- |
| 只测公共接口 | 接口稳定 → 测试几乎不变 → 可以在测试里深入实验 |
| 快速理解 | AI 只读接口就能快速把握模块功能，判断该改哪里 |
| **降低认知负担** | "认知负担正是大家使用 AI 时更常遇到的问题" |

由此得到角色分工：**人类负责接口设计与模块设计，AI 处理大部分实现**；模块被当作**灰盒（grey box）**而不是纯黑盒，讲师对模块内部代码的审查明显减少，**重心转向测试**。

**案例：自建视频编辑器**。系统包含前端状态 reducer 与 selector、约 20 个文件的后端 API 端点、处理 OBS 文件与静音检测的 CLI、本地数据库模块。bug 大量出现在**组件间交互**：修后端错误发现是前端调用 API 的方式错了，或是后端没正确调用 CLI。解法是把整个系统**封装成一个服务**（前端可调用的 SDK + 后端 API handler 接收 SDK 消息），整体变成一个深度模块，此后可以对整个编辑流程做端到端 TDD。

> **反模式**：**"为便于测试而提取纯函数"** 是 LLM 常给的伪解法。真正的错误往往藏在**调用方式**里，接口设计需要人类的语言与判断力。这类判断必须被"融入规划流程"，而不是事后补。

### 6.10 improve-codebase-architecture - 把架构改进做成流程

（P83–P84）

深化重构只是"治疗"，还需要"预防"。`improve-codebase-architecture` 是**架构改进要变成流程**，而不只是一次重构，技能流程如下：

```
① 定义深模块标准
② Explore 子代理自然导航代码库，要求"有机探索并记录摩擦点"
   （如"理解一个概念要在多个小文件间频繁切换""模块过浅"）
③ 给出候选方案（但不给具体接口设计）
④ 用户选择候选 → 并行生成多个子代理，各自产出完全不同的接口设计
⑤ 综合推荐/混合方案 → 产出重构 RFC → 创建为 GitHub issue → 转成看板任务
```

技能内置的常见反模式识别包括"仅仅为便于测试而提取纯函数""紧密耦合的模块在接口处产生集成风险"。

**案例：测验子系统（P84）**。这个区域是项目里**故意写坏的**：直接用原始数据库而不是项目其他地方的模式、测验数据答案到处都是、**完全没有测试**（"像完全不熟悉代码库的外包人员写的"）。代理推荐的正是它，理由是它是代码库中**唯一混用原始 SQLite、三种 SQL 与 Drizzle ORM** 的地方。

随后并行生成三种接口设计（极简 / 灵活 / 面向调用优化），最终采纳**设计 B + 一点 A**：

- 工厂函数"创建测验模块"，**注入数据库与评分策略**，接收测验内容；
- 暴露 `获取课程测验`、`获取最佳尝试`、`获取最新尝试`、`尝试历史记录`、`获取统计信息`、`保存测验`、`删除测验`；
- **XP 值完全可配置、模块不拥有 XP**；采用 A 的一点是"**是否授予 XP**"用布尔值而不是 XP 数量，因为**数量是调用者不需要的实现细节**。

生成的 issue 描述准确点出了病根："**测验子系统分散在三个浅层服务中，紧密耦合的服务需要调用者手动编排，而错误正是在手动编排过程中出现的。**" 重构前后对比很直观：过去要"通过课程 ID 获取测验 → 获取含问题的测验 → 获取最佳尝试 → 计算结果 → 授予 XP"，现在只需一两次 loader 调用。

> 目标是**在代码库中随时间持续做这件事**，而不是一次大重构；也不必一次做到完美，下次运行时可以在已有基础上继续优化。

### 6.11 绿地项目 - 先设计「代理体验」

（P87）

课程主体基于**棕地（brownfield，已有代码库）**项目。绿地（greenfield，全新项目）的流程是：**头脑风暴 → 研究文档（多轮迭代，形成决策记录集合）→ 原型 → PRD**。

关键差别在 PRD 的写法：

| 项目类型 | PRD 重点 |
| --- | --- |
| 棕地 | 基础已定，可以专注用户需求 |
| **绿地** | 必须**先考虑架构设计与代理体验（agent experience）** |

绿地 PRD 需要首先敲定的清单：

| 项目 | 为什么排前面 |
| --- | --- |
| **反馈循环**（类型、测试、pre-commit 钩子等） | 后面所有质量都依赖它 |
| **格式规范** | 决定代理产出的代码是否可维护 |
| **技术选型**（编程语言、前端框架） | **极难中途更换** |
| **模块结构**（初始的深层模块） | 决定后续是否可测、可导航 |
| **测试策略**（怎么 mock、是否用测试数据库） | 决定反馈循环的成本 |

> **金句**："不能为追求用户体验而牺牲代理体验，两者需紧密结合。""建立绿地代码库的难度其实只是设置代理体验，一旦完成，就可以立即开始循环。"

### 6.13 FAQ 精选

课程有六场答疑（P47、P48、P89–P92，合计约 4.8 小时）。下面按主题挑出复用价值最高的问答，已合并重复问题、去掉闲聊。

#### 流程与方法

**你的方法与 Superpowers、Spec-Driven Development（SDD）有什么本质区别？**

- Superpowers 这类技能集把技能写成"**能力**"：描述里堆满触发条件，让代理自己判断何时调用。**方向盘在代理手里**，非确定性很高，代理可能压根没捕捉到技能。
- 讲师的技能更像"**流程/命令**"：用户显式说"用 grill 做这件事"就一定能触发，代价是你必须自己思考、按刚性步骤走。
- 他用 `disable-model-invocation: true` 把两者分开：**流程技能（人调用）+ 能力技能（模型调用）**。
- 金句："流程技能里你握着方向盘，能力技能里代理握着方向盘。"

**小任务也要先 grill 吗？**

- 会过度。任务非常明确、你完全知道要改哪里、能完整描述出来时，**不需要 grill**。grill 的本质是"和 AI 对齐"，适用于你还不确定设计概念是否一致的时候。

**怎么让 grill 既不流于表面、又不过度钻牛角尖？**

- 不重要的决策直接说"**我不在乎**"，把优先级让给更重要的事，就像初级开发者问资深同事，答案有时就是"随便选一个"。
- 用《Shape Up》里"**精细度（fidelity）**"的概念排层级：文字 < 线框 < 原型 < 实际应用。默认用低精细度成本更低，但涉及外观的决策，光靠文字根本答不了。
- 判断"足够好"的标志是：**决定成败的最关键问题是否已经被回答**。秘密武器是原型——例如做两个对比原型（WebSocket vs SSE、自建 vs 第三方）来回答"哪个感觉更好"。

**循环工程（loop engineering）的热度是怎么回事？**

- 起因是 Peter Steinberger 那条引爆的推文："不要直接提示 AI，让 AI 自己写循环来提示 AI。"
- 讲师的解读：把"想法到上线"的生命周期切成若干阶段，**逐个移除人类检查点**；移除得越多，越能高效并行。
- 他自己的做法更偏**按需自动化**：问题进来先派代理探索，中间留一个小的检查点，再实施、审查、生成 PR 让他过目。**人不会完全消失，但只需最后那一个检查点。**不必非写成循环结构。

#### 上下文与模型

**上下文到 120k 了，该压缩还是交接给新会话？**

- 120k 不是断崖，实际更像一条**平缓下滑的曲线**，没有"到某点突然变笨"的开关。
- 判断标准是**剩余任务的复杂度**：如果剩下的活足够简单、可以直接信任基础模型，就一路做完——讲师有时会做到 250k。
- 压缩在**任务中期、目标明确**时很有用；如果在某个执行单元做到一半就压缩，容易忘掉或混淆已做过的操作。
- 理想状态是压缩趋近无损，那样只需把自动压缩阈值调低、让窗口压在 180k 左右。

**规划和构建时 token 成本一直涨，怎么省？**

- 优先优化**质量**而不是成本。质量与成本之间有一条临界线：质量往下掉，你就得花时间修代理的错；往上走，返工减少，直到可以近乎自动合并。
- 压 token 就会压质量；跌到临界线以下，人工评审和返工成本立刻回来。
- 正确的经济账是把**开发者的小时数换算成 token**：能省掉人工小时就是大幅降本。

**怎么选模型，怎么让代理自觉用便宜的模型？**

- 不给具体型号推荐（个人体验不具代表性）；建议团队把编码代理接进**可观测性工具**，看哪些会话成功、哪些失败，用数据决定。
- **探索阶段用 Haiku**：成本低两个数量级、速度极快，能快速大量读文件并总结，效果够用。做法是写进 `CLAUDE.md` 等引导文件。
- 另一种做法：用 Sonnet 实施、Opus 评审，token 更省而质量还在。

**新模型发布（比如 GPT-5）会改变游戏吗？**

- 人们过度关注模型发布。他通常**等一周再试**，也不愿依赖频繁变动的订阅制模型。
- 模型重要，但**你为代理搭的框架和环境同样关键，大致五五开**。
- 与其等新模型修好你的问题，不如现在就解决：有安全问题就用强模型 + 技能定时扫描，需要什么工具就建什么工具。

#### 代码库与规范

**有没有通用编码规范？该放在哪、怎么维护？**

- **不存在真正的通用规范**。这类书容易变成"给你一把锤子，看什么都像钉子"（例如深度模块化被滥用到不合适的场景）。
- 规范应该是**项目相关、公司相关的**；同一家公司用相似的库与框架，规范可以在多个项目间复用。
- 他**强烈反对公司里每个人自建一套规范**，而应统一维护一套、走 RFC 流程，并**放在代码库之外被引用**，让 AI 直接应用。
- 不要只让代理读代码库来生成规范（代码本身已自描述）；正确做法是用**你已有的数据集**：每条 PR 评论都能通过 API 获取，收集起来定期喂给代理更新规范，这个数据集会随你的评审自然增长。

**你反对给仓库写摘要文件，那大型仓库怎么办？**

- 代码和测试才是行为的**事实来源**，摘要等于**缓存**，问题是它很快过期。
- 摘要适合**很少变**的东西：第三方库（升级主版本前有不可违背的契约）值得调研后存成本地 markdown。
- 对频繁变化的自有代码，更好的做法是"**local roads / highway**"：在 `CLAUDE.md` 里写**上下文指针**，代理不必蜿蜒探索，顺着指针直达目标区域——便宜且不会过期。他给这类产物起名叫 **just-in-time docs（需时文档）**。

**知识图谱类工具（如 Grafy）能提升 AI 导航代码库的效率吗？**

- 他持怀疑态度：在代码库之上再建一层图或摘要，动机可以理解，但效果存疑。Claude Code 团队也明确表示"在代码库之上再建一层"效果不佳。
- 真正有效的是**让 AI 直接访问文件系统**，并给它 `grep` 这类强力搜索工具。

**多仓库（multi-repo）环境怎么套用你的工作流？**

- 首选 **monorepo**（哪怕要付工具成本）：一次提交改多处、历史易回溯、单一事实来源。
- 次优方案是加一个**包装仓库（wrapper repo）**：在里面引用仓库一和仓库二，所有目录都可见；把 `AGENTS.md`/`CLAUDE.md` 和技能都放在这个包装仓库里，并在这里实际运行代理。

**代理自主写码后，理解力退化、认知债怎么办？**

- 用**基于契约的设计**缓解：把复杂实现藏进深层模块，对外只暴露一个 100% 可测的接口。他的视频编辑器就是例子：静音检测、实时读取、转录都很复杂，但对外只是可完整测试的接口。
- 出问题再深入排查即可，"隐藏信息 + 委派给 AI"能大幅降低认知债。
- 另外他提醒：**你自己的代码多半是 AI 写的，但值得读的代码前所未有地多**，所以更应该以读代码为主；他本人职业生涯的跃升正是从读开源仓库开始的。

#### 测试与审查

**前端项目怎么做 TDD、怎么给代理反馈循环？**

- 前端难在有两层：**功能对不对**（点击是否跳转、计时器算得对不对）和**好不好看**。jsdom、Vitest 之类只能测前者。
- 虚拟 DOM 测试调试极其痛苦（没有浏览器可看、跑得慢、不稳定）。实用做法是**给代理浏览器访问权**（Playwright、agent browser 之类），让它对着 dev server 真点、真截图，并通过**可访问性检查器**把界面转成文本读进去。
- 结论：这仍是难题，只能靠"少量前端测试 + 让代理浏览操作"来缓解。

**实施和评审怎么分工？自动审查该查什么？**

- 流水线拆成：**实施 → 自动化检查（测试、类型检查、pre-commit、格式化）→ 自动化审查 → 人工审查**，只有最后一层必须有人。
- 自动化审查只查两件事：**是否符合规格**（PRD 是否被正确实现）、**是否符合编码规范**。
- 关键判断：**把编码规范从"实施"移出，只给"评审"看**。实施要探索代码、推进功能、防错调试，预算已经很满；规范作为单一来源出现在评审阶段，反而提升质量。
- 可以用 Sonnet 做实施、Opus 做评审，token 更省而质量还在；也可以让自动化审查直接修问题，再告知人工改了哪些，让人工看到接近完美的 PR。

**写出的代码不符合我的标准，怎么让它按规范写？**

- 让实现代理同时"实现 + 应用编码规范"符合人的直觉，但对 AI 是**任务过载**，会明显降低表现。
- 正确做法：走红绿重构循环，先让实现代理写基础实现并通过测试 → **清空上下文** → 让新的审查代理看 diff → **立即要求应用规范并修复**。自动审查确实有效，但 token 开销不小。

**发布前该跑哪些测试？平时要不要一直写测试？**

- "发布前的最优测试组合"是**错误心态**。应该保持**持续交付**：每五分钟、每次 CI 通过就是一个版本，把大发布拆小。
- 大批量发布总有一部分代码有问题，而且差异太大难以定位；小批量出问题时你能看清具体 diff，回滚也不会牵连无关功能。
- 最优测试就是**每天跑的 CI 测试**，前提是测试质量要高。他几乎总是写测试，尤其是后端，**在预先约定的接口处测试**，不写琐碎的微单元测试。

**自动化审查该怎么组织、怎么拿到结构化结果？**

- 让代理把结构化结果写进 XML 标签（如 `<output>`），再用 zod schema 校验，取 `output.inlineComments`、`output.replies` 之类字段——这样代理可以作为"**获取结构化输出的手段**"，再驱动后续动作（开别的代理、留评论），而且带重试，所以可靠。
- 最靠谱的建议是"直接看仓库，让你的代理去读那些代码"。

#### 安全、团队与个人成长

**使用代理的关键安全考量是什么？**

- 分两层：**你产出的软件**的安全性，和**代理自身**的安全性。
- 企业最大的风险是**数据外泄与提示注入**：代理上网 fetch 时可能被恶意页面操纵，用 `curl` 把整个代码库、环境变量或敏感数据发到外部端点。
- 主要防线是**沙盒**：限制出站网络流量、只允许白名单域名，这类请求就无法完成。在 Docker 里做限制并不难。

**大团队、大代码库怎么落地这套流程？**

- 合适的团队规模大约 **3–10 人**。
- **PRD 之前的一切必须是协作的**：一起开会讨论、把会议记录喂给代理深化成 PRD、原型共享评审，避免信息单点故障。PRD 达成共识后，实现可以交给一个人，再做团队评审。
- PRD 必须放在**多人可审阅的地方**（GitHub issue、Jira、Linear）；本地保存通常是个坏主意，课程里用本地只是为了让起点简单。

**新手该学哪些语言、怎么定路线？**

- 完全取决于你想构建什么。讲师本人基本只专注一门语言（TypeScript/JavaScript，加 Web 必需的 CSS 和 HTML），**只专注一门语言是好目标**，能真正深入成为专家。
- 路线图可以用 `teach` 技能：新建项目、装上技能、说明你想学什么，它会生成一路引导你的 HTML 课程（他用它学会了还原魔方）。
- 关于 CS 学位：学位教的基础（测试、接口、构建好代码库）**比以往更重要**，但要尽早把这些工具融进工作流。**战术编码基本交给 AI，你专注战略层。**

**代理写码之后，怎么保持手艺不退步？**

- 不要迷信"学习风格"：匹配偏好只是让你学得更顺畅，不等于学得更好。
- 值得读的代码前所未有地多，**以读代码为主**；他职业跃升正是从读别人的开源仓库开始的。

**学员最普遍的焦虑是什么？**

- 是"**偏执**"：觉得自己被 AFK 代理束缚住、不知道该委派什么，甚至觉得应该把所有事都委派出去。
- 课程所有工作的目的就是给你一套框架，让 AI 不再是黑箱：**保留思考和方向感，只把需要的那部分交出去。**
- 所以他反复强调"**控制权**"——不是拒绝 AI，而是别把判断力一起交出去。

**课程和技能会一直更新吗？我要一直追吗？**

- **技能是你的**：应该按需改成自己的版本，不必追着作者更新。有人下载后自己改，他很欢迎——"这正是它们存在的意义"。

**谁对你的影响最大？**

- Dex Horthy（"智能区/愚蠢区"的说法）、Geoffrey Huntley（ralph loop，让他看到"造 AFK 代理并开始交付"其实很简单），以及一位用 GitHub Actions 搭"工厂"的 CEO（他现在的整套自动化都建在 GitHub workflow 上）。

**答疑里反复出现的三个主题**

1. **AX 优先于 DX**：区分开发者体验（DX）与代理体验（AX）。开发者拿到大量文档只会快速浏览，**代理会照着文档行动**，所以 AX 是重点。评审要同时看 **UX → DX → AX** 三个维度，AX 大致处在新的优先级顶端。
2. **人的判断力就是上限**：AI 已经吃下战术编程，战略（该构建什么、往哪走）、对齐与价值判断仍归人类。AI 知道怎么构建，**不知道该构建什么**。
3. **小步、可委托的循环**：原型先验证方向，实现与审查分离，小批量持续交付，再把重复环节交给 AFK 与自动化流水线。

## 七 落地到你自己的仓库

前面六章是"为什么"和"怎么做"，这一章是"从哪开始"。核心判断是：**不要一次把整套流程铺开，先让代理能自己判断对错，再逐步把判断权交给流程。**

### 7.1 最小闭环 - Grill → 执行 → 清除

整套流程的最小可用版本只有三步：**新会话抛出模糊需求 → `grill me` 逐题追问到共识 → 直接说"实施"，完事 `/clear`**。它把"需求对齐"和"上下文纪律"合成一个动作，不写 spec、不建计划。

```
新会话（默认模式，不用 plan mode、不自动接受编辑）
   ↓ 一句话抛出模糊需求
grill me 逐题追问 → 每答一题就是一个决策 → 达成共识
   ↓ Shift+Tab 进入接受修改模式
"实施" → 直接产出代码（不写 spec、不建计划）
   ↓ 完成后 /clear，开下一个任务
```

### 7.2 主流程与各步产物

当任务变大、需要多人协作时，最小闭环扩成一条**每步输出即下一步输入**的流水线：

| 环节 | 技能 | 交给下一步的产物 |
| --- | --- | --- |
| 需求拷问 | `grill-with-docs`（旧名 `grill-me`） | 决策记录、领域文档 |
| 规格与拆票 | `to-spec` / `to-tickets`（旧名 `write-a-prd` / `prd-to-issues`） | 规格、工单与阻塞关系 |
| 实现与评审 | `implement`（旧名 `do-work`），内部应用 `tdd` / `code-review` | 代码、测试与评审结果 |
| 上下文交接 | `handoff` | 进度、证据、风险与下一步 |

没有项目目录时可以使用 `grill-me` 替代，同样保留需求决策记录。

七阶段各自用什么工具、人做什么、代理做什么，见 6.12 最终工作流。

### 7.3 安装与初始化

三种方式任选，**不要同时装**：

```bash
npx skills@latest add mattpocock/skills          # ① 装全套（安装时务必勾选 setup-matt-pocock-skills）
npx skills@latest add mattpocock/skills --skill=grill-me   # ② 按需装单个
# ③ Claude Code 插件：/plugin install mattpocock-skills
```

本地安装分三步：

1. **环境检查**：Node.js ≥ 20、Claude Code、npm 可访问。
2. **执行安装**：选择上面三种方式之一并完成安装。
3. **确认结果**：检查技能可见，再进入项目初始化。

装完在项目里跑一次 **`/setup-matt-pocock-skills`**（每个仓库一次），它会落盘三份配置：

- **Issue 跟踪器**：默认 GitHub，也支持 GitLab / 本地 `.scratch/`。
- **分诊标签**：`needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`。
- **域文档布局**：默认根目录 `CONTEXT.md` + `docs/adr/`，并给 `CLAUDE.md` / `AGENTS.md` 写入 `## Agent skills` 区块。

初始化后可以先用 `/ask-matt` 问一次入口建议，确认技能能被正确路由。

### 7.4 如果只做三件事，就做这三件

1. **每个仓库一个 `do-work` 技能 + pre-commit 钩子**。五行技能（理解 → 规划 → 实施 → 验证 → 提交）加上 `husky` + `lint-staged` + `prettier` + typecheck + test，是投入产出比最高的一步：它把"代理能自己判断对不对"变成了确定性的。
2. **需求模糊时先 grill，再写 PRD**。PRD 必须有编号的用户故事和明确的 out of scope，并放在团队能审阅的地方。
3. **计划一律用垂直切片（曳光弹）**，每个阶段结束 `/clear` + `commit`。仅这一条就能把"很晚才发现系统跑不起来"变成"每个阶段都拿到端到端反馈"。

### 7.5 反模式清单（对照自查）

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 一路靠自动压缩跑到底 | 上下文层层"沉积物"，输出不可预测 | 每任务 `/clear`；最多 `compact` 一次 |
| 计划横向分层（数据库→API→前端） | 到后期才拿到集成反馈，早期测试无意义 | 每个阶段穿透所有层（曳光弹） |
| 计划里写死函数名与伪代码 | 实现一变就全部过时 | 只规划"跨所有阶段都有效"的决策 |
| 放行整个 `pnpm run` | 连迁移脚本一起授权出去 | 只放行具体命令（`pnpm run test` 等） |
| 无隔离就开 yolo 模式 | 删目录、外泄密钥、被提示注入 | Docker / Podman 沙盒，只挂载仓库目录 |
| 沙盒认证用订阅 token | 不稳定、有合规问题 | 用 Anthropic API key |
| 把偶发指令塞进 `CLAUDE.md` | 每次请求白付 token，稀释关键指令 | 做成技能，按需加载 |
| 让实施代理同时背编码规范 | 任务过载，表现明显下降 | 规范只给评审阶段看 |
| 把"提取纯函数"当测试解药 | 真正的错误在调用方式里，测不到 | 人类设计接口（深模块），只测公共接口 |
| 研究/摘要文档永久保存 | 文档腐烂会**主动伤害**代理 | 设生命周期，用完就好，Git 历史可捞 |
| 直接克隆公共仓库当 issue 池 | 你的 issue 涌进别人的仓库 | fork 一份并删掉 Git 历史，用自己仓库 |
| 给代理全权 PAT | 令牌泄露风险 | 细粒度最小权限（读 issue / 评论 / 关单） |
| 一轮 AFK 循环做多个任务 | 上下文被撑爆，效率反而下降 | 一轮只做一个任务 |
| 一次性大重构架构 | 风险高、难以验收 | 每个功能都做一些深化，小步持续 |

### 7.6 四周落地路线（建议）

| 周 | 目标 | 具体动作 |
| --- | --- | --- |
| 第 1 周 | 让代理能自己判断对错 | 装好 pnpm/Node；写 `do-work` 技能；加 pre-commit；装状态行；精确配置权限允许列表 |
| 第 2 周 | 把"想清楚"变成流程 | 需求模糊时用 `grill-me`；产出第一份 PRD（用户故事 + out of scope）；用曳光弹拆阶段并逐阶段执行 |
| 第 3 周 | 让实现质量可控 | 实施步骤改成红绿重构（先运行确认测试失败）；用 `handoff` 分流中途冒出的独立任务；把编码规范从 `CLAUDE.md` 迁到技能 |
| 第 4 周 | 把实现阶段离线化 | Docker 沙盒 + API key；AFK 脚本（`run` + max iterations + 完成信号）；GitHub issue 当队列并闭环；PRD/计划改写入 issue |
