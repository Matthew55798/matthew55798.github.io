# 集合

> 参考：JavaGuide《[Java 集合常见面试题（上）](https://javaguide.cn/java/collection/java-collection-questions-01.html)》《[Java 集合常见面试题（下）](https://javaguide.cn/java/collection/java-collection-questions-02.html)》。本文结合本知识库原有内容做了整理与补充，图片已转存到本地。

Java 集合，也叫作容器，主要由两大接口派生而来：一个是 `Collection` 接口，主要用于存放单一元素；另一个是 `Map` 接口，主要用于存放键值对。对于 `Collection` 接口，下面又有三个主要子接口：`List`、`Set`、`Queue`。

![Java 集合框架概览](/img/技术/集合/java-collection-hierarchy.png)

> 注：图中只列举了主要的继承派生关系，并没有列举所有关系，例如省略了 `AbstractList`、`NavigableSet` 等抽象类以及其他辅助类。

## 数据结构

### List

- `ArrayList`：底层是 `Object[]` 数组。
- `Vector`：底层是 `Object[]` 数组，方法大多使用 `synchronized`，属于较老的线程安全实现。
- `LinkedList`：底层是双向链表，JDK 1.6 之前为循环链表，JDK 1.7 取消了循环。

### Set

- `HashSet`：无序、唯一，底层基于 `HashMap` 保存元素。
- `LinkedHashSet`：`HashSet` 的子类，内部通过 `LinkedHashMap` 实现，可以维护插入顺序。
- `TreeSet`：有序、唯一，底层是红黑树。

### Queue

- `PriorityQueue`：底层是 `Object[]` 数组实现的小顶堆。
- `DelayQueue`：底层依赖 `PriorityQueue`。
- `ArrayDeque`：底层是可扩容的动态双向数组。

### Map

- `HashMap`：JDK 1.8 之前由数组 + 链表组成；JDK 1.8 之后，当链表长度大于阈值 8，且数组长度达到 64 时，链表会转为红黑树。
- `LinkedHashMap`：继承自 `HashMap`，在数组 + 链表 / 红黑树基础上增加双向链表，用于维护插入顺序或访问顺序。
- `Hashtable`：数组 + 链表组成，方法大多使用 `synchronized`，基本已经被 `ConcurrentHashMap` 替代。
- `TreeMap`：底层是红黑树，可以按 key 排序，并支持范围查询、边界查询等操作。

## List、Set、Queue、Map 的区别

- `List`：存储的元素有序、可重复，适合按下标访问、按顺序遍历的场景。
- `Set`：存储的元素不可重复，常用于去重、成员判断。
- `Queue`：按特定排队规则确定元素出入顺序，通常遵循 FIFO，也有优先级队列、双端队列等实现。
- `Map`：使用 key-value 存储。key 不可重复，每个 key 最多映射一个 value。`HashMap` 的 key-value 无显式顺序，`LinkedHashMap` 可维护插入或访问顺序，`TreeMap` 可按 key 排序。

## ArrayList 和 Array 的区别

`ArrayList` 内部基于动态数组实现，`Array` 是 Java 原生数组，二者的核心区别如下：

- 长度：`Array` 创建后长度固定；`ArrayList` 会按元素数量动态扩容。
- 类型：`Array` 可以存基本类型和对象；`ArrayList` 只能存对象，基本类型需要使用包装类。
- 泛型：`ArrayList` 支持泛型，类型约束更友好；数组不支持泛型数组的直接创建。
- 操作能力：`ArrayList` 提供 `add()`、`remove()`、`set()`、`contains()` 等常用 API；数组主要通过下标访问，插入和删除需要手动移动元素。
- 创建方式：数组创建时必须指定长度或初始元素；`ArrayList` 可以不指定容量。

示例：

```java
String[] array = new String[]{"hello", "world", "!"};
array[0] = "goodbye";

ArrayList<String> list = new ArrayList<>(Arrays.asList("hello", "world", "!"));
list.add("goodbye");
list.set(0, "hi");
list.remove(0);
```

## ArrayList 插入和删除元素的时间复杂度

插入：

- 头部插入：需要把已有元素整体后移一位，时间复杂度是 `O(n)`。
- 尾部插入：容量足够时为 `O(1)`；如果触发扩容，需要复制数组，扩容这一步是 `O(n)`。
- 指定位置插入：需要把目标位置之后的元素后移，平均移动 `n/2` 个元素，时间复杂度是 `O(n)`。

删除：

- 头部删除：需要把后续元素整体前移一位，时间复杂度是 `O(n)`。
- 尾部删除：直接删除末尾元素，时间复杂度是 `O(1)`。
- 指定位置删除：需要把目标位置之后的元素前移，平均移动 `n/2` 个元素，时间复杂度是 `O(n)`。

可以简单理解为：`ArrayList` 随机访问快，尾部追加快；越靠近头部的插入、删除，移动成本越高。

## HashMap 和 Hashtable 的区别

- 线程安全：`HashMap` 非线程安全；`Hashtable` 的方法大多使用 `synchronized` 修饰，是线程安全的。
- 性能：`HashMap` 没有全表同步开销，通常效率更高；`Hashtable` 基本已经被淘汰。
- null 支持：`HashMap` 允许一个 `null` key 和多个 `null` value；`Hashtable` 不允许 `null` key 或 `null` value。
- 初始容量与扩容：`Hashtable` 默认初始容量为 11，扩容为 `2n + 1`；`HashMap` 默认初始容量为 16，扩容为原来的 2 倍。
- 指定初始容量：`Hashtable` 会直接使用给定容量；`HashMap` 会通过 `tableSizeFor()` 调整到 2 的幂次方。
- 底层结构：JDK 1.8 之后 `HashMap` 使用数组 + 链表 / 红黑树；`Hashtable` 仍是数组 + 链表。
- 哈希扰动：`HashMap` 会对 `hashCode()` 做高低位扰动以降低冲突；`Hashtable` 直接使用 key 的 `hashCode()`。

`HashMap` 保证容量为 2 的幂次方的核心方法：

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

## HashMap 和 TreeMap 的区别

`HashMap` 和 `TreeMap` 都继承自 `AbstractMap`，但定位不同：

- `HashMap` 基于哈希表，关注平均 `O(1)` 的读写性能，不保证顺序。
- `TreeMap` 基于红黑树，实现了 `SortedMap` 和 `NavigableMap`，可以按 key 排序，并支持范围查询、边界查询和逆序视图。

![TreeMap 继承关系图](/img/技术/集合/treemap-hierarchy.png)

`NavigableMap` 提供的典型能力：

- 定向搜索：`ceilingEntry()`、`floorEntry()`、`higherEntry()`、`lowerEntry()`。
- 子集操作：`subMap()`、`headMap()`、`tailMap()`。
- 逆序视图：`descendingMap()`。
- 边界操作：`firstEntry()`、`lastEntry()`、`pollFirstEntry()`、`pollLastEntry()`。

总结：如果只需要快速存取，优先考虑 `HashMap`；如果需要按 key 排序或做范围检索，使用 `TreeMap`。

## HashMap 的底层实现

### JDK 1.8 之前

JDK 1.8 之前，`HashMap` 底层是数组 + 链表，也就是链表散列。`HashMap` 会先通过 key 的 `hashCode()` 计算哈希值，再经过扰动函数处理，然后通过 `(n - 1) & hash` 计算桶下标。

如果桶位为空，就直接放入；如果桶位已有元素，则比较 hash 和 key：

- hash 和 key 都相同：覆盖旧值。
- 不相同：通过拉链法解决冲突，把元素放入链表。

JDK 1.8 中的 `hash()` 方法：

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

拉链法就是把数组和链表结合起来：数组中每个位置都是一个桶，发生哈希冲突时，把冲突元素放到同一个桶的链表中。

![JDK 1.7 HashMap 内部结构](/img/技术/集合/jdk17-hashmap.png)

### JDK 1.8 之后

JDK 1.8 之后，`HashMap` 变为数组 + 链表 / 红黑树。当桶中链表长度超过 8 时，会触发树化判断；如果当前数组长度小于 64，会优先扩容，而不是直接转红黑树。

![JDK 1.8 HashMap 内部结构](/img/技术/集合/jdk18-hashmap.png)

优先扩容而不是直接树化的原因：

- 扩容可以降低哈希冲突概率，很多时候比维护红黑树更划算。
- 红黑树需要维护自平衡，节点结构也更重，过早树化会增加复杂度和内存成本。

阈值 8 和 64 的意义：

- 链表长度达到 8 的概率很低，设为 8 可以在性能和空间之间取得平衡。
- 数组长度小于 64 时，优先扩容通常更能改善冲突；达到 64 后，红黑树的查询优势才更明显。

链表和红黑树的转换规则：

- 树化：链表长度超过 8，且数组长度至少为 64。
- 退化：树节点数量小于 6 时，红黑树会退化回链表。

## HashMap 为什么长度是 2 的幂次方

`HashMap` 根据 `(n - 1) & hash` 计算数组下标。当数组长度 `n` 是 2 的幂次方时，`hash % n` 等价于 `hash & (n - 1)`，位运算比取模效率更高。

更重要的是，2 的幂次方可以让扩容后的元素分布更均匀。例如从 8 扩容到 16：

```plain
旧数组位置：
hash       = 10101100
length - 1 = 00000111
& -----------------
index      = 00000100  (4)

新数组位置：
hash       = 10101100
length - 1 = 00001111
& -----------------
index      = 00001100  (12)
```

扩容后只需要看新增的高位：

- 高位为 0：元素位置不变。
- 高位为 1：元素移动到 `原索引 + 原容量` 的位置。

因此，容量为 2 的幂次方有三个好处：

- 位运算效率高。
- 哈希分布更均匀。
- 扩容迁移逻辑更简单，只需要判断高位变化。

## HashMap 多线程操作导致死循环问题

JDK 1.7 及之前版本的 `HashMap` 在多线程环境下扩容可能出现死循环。原因是扩容迁移链表时使用头插法，多个线程同时迁移同一个桶时，可能把链表节点指向错误位置，形成环形链表，后续 `get()` 遍历链表时就可能无限循环，CPU 飙升。

JDK 1.8 改用尾插法，避免了 JDK 1.7 扩容链表倒置导致环形链表的问题。但这不代表 `HashMap` 可以在并发环境下使用，因为并发 `put()` 仍然可能发生数据覆盖、计数错误等问题。并发场景应该使用 `ConcurrentHashMap`。

## HashMap 为什么线程不安全

`HashMap` 不保证线程安全。多线程并发写入时，主要风险包括：

- 数据覆盖：两个线程同时向同一个桶写入，后写入的线程可能覆盖先写入的数据。
- 计数错误：多个线程同时修改 `size`，可能导致实际插入多次，但 `size` 只增加一次。
- 死循环：JDK 1.7 及之前版本在并发扩容时可能形成环形链表。
- 结构不一致：扩容、链表插入、树化等结构变更没有并发控制，读线程可能看到中间状态。

典型并发覆盖场景：

1. 线程 A 和线程 B 同时执行 `put()`，并且 hash 到同一个桶。
2. 线程 A 判断桶为空后被挂起。
3. 线程 B 完成插入。
4. 线程 A 恢复执行，并基于之前“桶为空”的判断继续插入，覆盖线程 B 的结果。

## ConcurrentHashMap 和 Hashtable 的区别

`ConcurrentHashMap` 和 `Hashtable` 都能用于线程安全的 Map 场景，但实现方式和并发性能差异很大。

- 底层结构：JDK 1.7 的 `ConcurrentHashMap` 是 Segment 数组 + HashEntry 数组 + 链表；JDK 1.8 是 Node 数组 + 链表 / 红黑树。`Hashtable` 是数组 + 链表。
- 锁粒度：`Hashtable` 使用同一把对象锁，同一时间基本只能有一个线程访问同步方法；`ConcurrentHashMap` 锁粒度更细。
- 并发能力：JDK 1.7 的 `ConcurrentHashMap` 使用分段锁；JDK 1.8 使用 CAS + `synchronized`，只锁桶级别的链表或红黑树首节点。
- 读写效率：`ConcurrentHashMap` 的并发读写效率远高于 `Hashtable`，也是现代并发 Map 的首选。

## ConcurrentHashMap 线程安全的具体实现方式

### JDK 1.7

JDK 1.7 的 `ConcurrentHashMap` 使用分段锁。整体结构由 `Segment` 数组和 `HashEntry` 数组组成。

- `Segment` 继承 `ReentrantLock`，每个 `Segment` 负责守护一部分桶。
- 默认 `Segment` 数组大小为 16，也就是默认支持 16 个分段并发写。
- 写入不同 `Segment` 时可以并发执行；写入同一个 `Segment` 时需要竞争同一把锁。

![Java 7 ConcurrentHashMap 存储结构](/img/技术/集合/java7-concurrenthashmap.png)

### JDK 1.8

JDK 1.8 几乎重写了 `ConcurrentHashMap`，取消了分段锁，采用 `Node + CAS + synchronized` 保证线程安全。

- 数据结构和 JDK 1.8 的 `HashMap` 类似：数组 + 链表 / 红黑树。
- 初始化数组、设置桶第一个节点等场景会使用 CAS。
- 当桶中已有元素时，使用 `synchronized` 锁住当前桶的头节点，再进行链表或红黑树的插入、更新。
- 锁粒度细到桶级别，只要 hash 不冲突，多个线程就能并发写不同桶。

![Java 8 ConcurrentHashMap 存储结构](/img/技术/集合/java8-concurrenthashmap.png)

红黑树场景下，`TreeNode` 会被 `TreeBin` 包装。`TreeBin` 通过 `root` 维护红黑树根节点，并通过 `waiter`、`lockState` 等字段协调读写，避免并发修改红黑树结构导致不一致。

## JDK 1.7 和 JDK 1.8 的 ConcurrentHashMap 有什么不同

- 线程安全实现：JDK 1.7 使用 `Segment` 分段锁；JDK 1.8 使用 `Node + CAS + synchronized`。
- 数据结构：JDK 1.7 是 Segment 数组 + HashEntry 数组 + 链表；JDK 1.8 是 Node 数组 + 链表 / 红黑树。
- 锁粒度：JDK 1.7 锁住一个 Segment；JDK 1.8 锁住桶的头节点，粒度更细。
- 冲突处理：JDK 1.7 使用拉链法；JDK 1.8 在链表过长时会转为红黑树。
- 并发度：JDK 1.7 最大并发度受 Segment 数量限制，默认 16；JDK 1.8 的并发度与桶分布相关，通常更高。

## ConcurrentHashMap 能保证复合操作的原子性吗

不能简单认为所有复合操作都是原子的。

`ConcurrentHashMap` 能保证单个基本操作的线程安全，例如 `put()`、`get()`、`remove()`。但复合操作由多个基本操作组成，例如“先判断 key 是否存在，再插入”：

```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

这个逻辑不是原子的。两个线程可能同时判断 key 不存在，然后分别写入，最终结果取决于后写入的线程。

应该使用 `ConcurrentHashMap` 提供的原子复合方法：

- `putIfAbsent()`
- `compute()`
- `computeIfAbsent()`
- `computeIfPresent()`
- `merge()`

示例：

```java
map.putIfAbsent(key, value);

map.computeIfAbsent(key, k -> value);
```

这些方法把“判断 + 写入 / 计算 + 更新”封装在 `ConcurrentHashMap` 内部完成，可以保证对应复合语义的原子性。

## 红黑树补充

红黑树是一种自平衡二叉搜索树，它通过颜色标记和旋转操作保持近似平衡，从而保证查找、插入、删除的最坏时间复杂度为 `O(log n)`。

`HashMap` 在链表过长时使用红黑树，主要是为了避免链表查询退化为 `O(n)`。选择红黑树而不是 AVL 树，主要是因为红黑树在插入、删除时旋转次数相对较少，在频繁更新的数据结构中更折中。

常见平衡结构对比：

- 红黑树：每个节点只需要额外颜色位，平衡性和更新成本折中较好。
- AVL 树：平衡更严格，查询性能好，但插入和删除维护成本更高。
- B 树 / B+ 树：适合磁盘和数据库索引场景，节点需要保存多个 key 和指针。
- Splay 树 / Treap：不需要完全相同的平衡元数据，但操作特性和适用场景不同。

在 `HashMap` 这个场景中，红黑树在查询性能、更新成本、内存占用和实现复杂度之间取得了较好的平衡。
