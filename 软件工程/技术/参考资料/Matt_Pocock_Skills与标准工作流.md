# Matt Pocock Skills 与标准工作流

> 《AI 驱动的全流程软件开发实战》第二部分 ｜ 前置讲义：[AI 工程词汇](/软件工程/技术/AI/AI工程词汇.md)

《[AI 工程词汇](/软件工程/技术/AI/AI工程词汇.md)》讲的是"名词"，本文讲的是"动作"：一套可以直接落地的 AI 开发主流程。

需要先说明一点：随着基模能力与 Agent 本身能力越来越强，一些工作流也正在慢慢被淘汰。所以下面这些流程的价值不在于照抄步骤，而在于理解每一步**为什么要这么设计**。

## 2.1 Skills 的定位

Matt Pocock Skills 的定位可以概括成三个词：**小而精、易调整、可组合**。

- **按需选择**：按当前工程问题选择技能，而不是一次性加载一整套方法。
- **工程与生产力并重**：技能分为 `engineering`、`productivity` 等分类。
- **本地可落地**：围绕真实课程案例，体验一次完整的技能工作流。

官方仓库：<https://github.com/mattpocock/skills>

## 2.2 调用方式与 ask-matt 路由

技能有三种进入方式：

| 入口 | 用途 | 课程示例 |
| --- | --- | --- |
| 用户显式调用 | 主动点名技能，组织工作过程 | `/grill-with-docs`、`/to-tickets` |
| 模型自动调用 | 按任务触发条件应用方法 | `tdd`、`code-review` |
| ask-matt 路由 | 不确定入口时获取技能建议 | `/ask-matt` |

技能名称与可用入口以已安装版本为准。

## 2.3 安装方式

| 方式 | 安装范围 | 适用场景 |
| --- | --- | --- |
| 全套安装 | `npx skills@latest add mattpocock/skills` | 完整体验技能主流程 |
| 按需安装 | 追加 `--skill=grill-me` 等参数 | 只需要部分技能 |
| Claude Code 插件 | 按官方文档完成市场配置与安装 | 通过插件方式管理技能 |

安装命令以实际环境实测为准。

## 2.4 本地安装与项目初始化

本地安装分三步：

1. **环境检查**：Node.js ≥ 20、Claude Code、npm 可访问。
2. **执行安装**：选择上面三种方式之一并完成安装。
3. **确认结果**：检查技能可见，再进入项目初始化。

项目初始化需要确认三件事：

- **Issue 跟踪方式**：GitHub、GitLab 或本地 Markdown。
- **项目规则**：分诊标签、领域文档与 Agent 配置。
- **首次调用**：执行 `/setup-matt-pocock-skills`，完成后体验 `/ask-matt`。

## 2.5 标准主流程与各步产物

主流程是一条**每步输出即下一步输入**的流水线：

| 环节 | 技能 | 交给下一步的产物 |
| --- | --- | --- |
| 需求拷问 | `grill-with-docs` | 决策记录、领域文档 |
| 规格与拆票 | `to-spec` / `to-tickets` | 规格、工单与阻塞关系 |
| 实现与评审 | `implement`，内部应用 `tdd` / `code-review` | 代码、测试与评审结果 |
| 上下文交接 | `handoff` | 进度、证据、风险与下一步 |

没有项目目录时可以使用 `grill-me` 替代，同样保留需求决策记录。

## 2.6 需求拷问：grill-with-docs

- **设计理念**：用提问与取舍收敛模糊需求。
- **运转流程**：一次聚焦一个问题，持续记录决策。
- **核心产物**：决策记录、`CONTEXT.md` 与 ADR。

## 2.7 规格与垂直切片拆票

- **`to-spec`：综合规格**——将已确认的讨论整理为问题、方案、用户故事和测试决策。
- **`to-tickets`：垂直切片**——每张票覆盖一项可验证行为及相关实现层。
- **依赖与完成标准**——标明阻塞关系，按可开工顺序推进。

观察要点：交付范围、完成标准、阻塞关系、开工顺序。

## 2.8 按票实现与双轴评审

| 环节 | 关注点 | 完成依据 |
| --- | --- | --- |
| `implement` | 以一张票为当前工作边界 | 范围与验收条件明确 |
| `tdd` | 按可观察行为推进红、绿循环 | 失败原因正确，目标测试通过 |
| `code-review` | 规范 Standards 与规格 Spec | 代码符合约定，行为满足需求 |

测试聚焦约定的接口与行为，避免与内部实现绑定。

一次完整的红绿循环可以这样演示：示例任务是把 SECS 日志清洗成图表数据。

观察要点：行为是否明确，失败是否有效，实现后是否通过。

## 2.9 上下文交接与接续

- **记录事实**：当前进度、产物位置与验证结果。
- **明确下一步**：后续任务、建议技能与遗留风险。
- **保护上下文**：引用已有产物，清理敏感信息。

演示时可以对照旧会话的交接文档与新会话的接续结果。核对三点：进度一致、证据可追溯、下一步明确。

## 2.10 两条主线的呼应与选型

本课程有两条可选的框架主线，区别在定位与粒度：

| 维度 | Superpowers | Matt Pocock Skills |
| --- | --- | --- |
| 课程定位 | 整套工程方法与开发节奏 | 可组合的实战工程技能 |
| 本次处理 | 已移出正文，见附录自学参考 | 课堂精讲与演示 |
| 课程重点 | 设计、计划、TDD 与子代理开发 | 拷问、拆票、实现与交接 |
| 共同基础 | 清晰目标、可靠上下文、逐步验证 | 清晰目标、可靠上下文、逐步验证 |

落到日常工作里，按手上任务的形态选入口：

| 场景 | 建议做法 |
| --- | --- |
| 遇到一个新需求 | 从需求拷问开始，保留决策和验收条件 |
| 已有明确任务 | 按任务范围实现，通过测试和评审验证 |
| 准备切换会话 | 先交接进度、证据与下一步，再继续执行 |

不确定如何开始时，可以使用 `ask-matt` 获取入口建议。

## A. 主流程之外的技能地图

| 场景 | 技能 | 主要用途 |
| --- | --- | --- |
| 外来任务 | `triage` | 分诊外来 issue / PR，形成 agent brief |
| 疑难问题 | `diagnosing-bugs` | 复现、假设、定位、修复与回归 |
| 大型任务 | `wayfinder` | 梳理决策地图与后续路径 |
| 独立能力 | `prototype` / `research` / `wizard` | 原型验证、资料研究、人机操作协作 |
| 基础词汇 | `domain-modeling` / `codebase-design` | 领域模型与模块设计 |

`triage` 用于外来任务分诊，`to-tickets` 用于规格拆票，两者不要混用。
