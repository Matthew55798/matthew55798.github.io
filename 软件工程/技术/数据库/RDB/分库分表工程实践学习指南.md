## 一、核心中间件官方资源

### Apache ShardingSphere (强烈推荐)

**定位**: Apache顶级项目，Database Plus生态，功能最全面的分库分表中间件

| 资源类型 | 链接 | 说明 |
|---------|------|------|
| 官网 | https://shardingsphere.apache.org/ | 产品特性、架构介绍 |
| GitHub | https://github.com/apache/shardingsphere | 20.7k⭐，源码+示例 |
| 中文文档 | https://shardingsphere.apache.org/document/current/cn/overview/ | 完整配置手册 |
| PDF文档 | https://shardingsphere.apache.org/pdf/shardingsphere_docs_en.pdf | 离线查阅 |

**核心架构**:
```
┌─────────────────────────────────────────────────────────┐
│                    Apache ShardingSphere                 │
├─────────────────────────────────────────────────────────┤
│  ShardingSphere-JDBC (客户端)  │  ShardingSphere-Proxy (服务端)  │
│  - Java应用集成                 │  - 独立部署                      │
│  - 性能最优                     │  - 支持多语言                    │
│  - 低侵入                       │  - DBA友好                       │
└─────────────────────────────────────────────────────────┘
```

**核心功能**:
- 数据分片 (分库分表)
- 读写分离
- 分布式事务 (XA/BASE)
- 数据加密
- 数据脱敏
- 影子库压测
- 数据迁移

#### 1. 订单系统分库分表实践
- **链接**: https://tech.meituan.com/2016/11/18/dianping-order-db-sharding.html
- **背景**: 订单单表突破200G，抢购活动数据库瓶颈
- **核心方案**:
  - 垂直切分 + 水平切分
  - UserId后四位 mod 32 分库，div 32 mod 32 分表

  - 8个集群(主从)，每个集群4个库
- **数据迁移**: 三阶段双写迁移方案
- **唯一ID**: 时间戳+用户标识码+随机数

## 三、分布式ID生成方案

### 1. 美团 Leaf (推荐⭐)
- **GitHub**: https://github.com/meituan-dianping/leaf (6.7k⭐)
- **方案**:
  - 号段模式：基于数据库批量ID分配
  - Snowflake模式：基于时间戳的分布式ID
- **特点**:
  - 高性能：Leaf-segment单机QPS 5万+
  - 高可用：双buffer优化，数据库故障仍可短期服务
  - 生产验证：美团内部广泛使用

### 2. 滴滴 TinyID
- **GitHub**: https://github.com/didi/tinyid (2.4k⭐)
- **方案**: 号段模式优化版
- **特点**: 简单易用、高性能、支持多db配置、批量获取

### 3. 百度 UidGenerator
- **方案**: Snowflake改进版
- **特点**: 解决时钟回拨问题，支持自定义workerid

## 四、选型对比

| 对比维度 | ShardingSphere | MyCAT 2.0 |
|---------|---------------|-----------|
| **所属机构** | Apache基金会 | MyCAT社区 |
| **架构模式** | JDBC(客户端) + Proxy(服务端) | 纯Proxy |
| **侵入性** | JDBC低侵入，Proxy无侵入 | 无侵入 |
| **性能表现** | JDBC最优，Proxy有网络损耗 | 中等 |
| **功能丰富度** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| **社区活跃度** | 极高 (Apache顶级) | 一般 |
| **版本迭代** | 持续活跃 (5.5.x) | 较慢 (v1.22 2022) |
| **多语言支持** | Proxy支持任意语言 | MySQL协议兼容 |
| **功能覆盖** | 分片、读写分离、加密、脱敏、影子库 | 分片、读写分离 |
| **分布式事务** | XA/BASE/Seata | XA |
| **云原生支持** | Kubernetes Operator | 一般 |

### 选型建议

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| Java生态，追求极致性能 | **ShardingSphere-JDBC** | 客户端模式，无网络损耗 |
| 多语言环境，运维友好 | **ShardingSphere-Proxy** | 独立代理，透明接入 |
| 简单场景，快速上线 | **MyCAT** | 配置简单，学习成本低 |
| 复杂业务，功能全面 | **ShardingSphere** | 功能最全，生态完善 |

## 五、关键配置示例

### ShardingSphere-JDBC YAML配置

```yaml
# 数据源配置
dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://localhost:3306/ds_0
    username: root
    password: password
    maximumPoolSize: 20
    minimumIdle: 5
  ds_1:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://localhost:3306/ds_1
    username: root
    password: password
    maximumPoolSize: 20
    minimumIdle: 5

# 分片规则配置
rules:
  - !SHARDING
    tables:
      t_order:
        # 实际数据节点: ds_0.t_order_0, ds_0.t_order_1, ds_1.t_order_0, ds_1.t_order_1
        actualDataNodes: ds_${0..1}.t_order_${0..1}
        
        # 表分片策略
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: t_order_inline
        
        # 库分片策略
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: database_inline
        
        # 主键生成策略
        keyGenerateStrategy:
          column: order_id
          keyGeneratorName: snowflake
    
    # 分片算法定义
    shardingAlgorithms:
      database_inline:
        type: INLINE
        props:
          algorithm-expression: ds_${user_id % 2}
      t_order_inline:
        type: INLINE
        props:
          algorithm-expression: t_order_${order_id % 2}
    
    # 主键生成器
    keyGenerators:
      snowflake:
        type: SNOWFLAKE
        props:
          worker-id: 1  # 不同实例配置不同ID

# 全局属性配置
props:
  sql-show: true  # 开发环境显示SQL
  executor-size: 16  # 执行器线程数
  max-connections-size-per-query: 5
```

### Spring Boot集成

```yaml
# application.yml
spring:
  datasource:
    driver-class-name: org.apache.shardingsphere.driver.ShardingSphereDriver
    url: jdbc:shardingsphere:classpath:sharding-config.yaml
```

## 六、生产环境最佳实践

### 1. 分片键选择原则

```
✅ 推荐:
- user_id (用户ID) - 高基数，查询高频
- order_id (订单ID) - 业务唯一，天然分布均匀
- 组合键 (user_id + create_time)

❌ 避免:
- 时间字段 (create_time) - 热点问题，最新数据集中在单个分片
- 地区字段 (province_code) - 数据分布不均
- 低基数字段 (status) - 无法有效分片
```

### 2. 数据迁移三阶段方案

```
阶段一: 双写(事务成功以老模型为准)
├─ 新库同步写入
├─ 查询走老模型
├─ 每日Job数据对账
└─ Job导历史数据

阶段二: 切换(事务成功以新模型为准)
├─ 历史数据导入完毕
├─ 数据对账无误
├─ 双写，新模型事务为准
├─ 查询切新模型
└─ 每日Job数据对账

阶段三: 废弃(老模型不再写入)
├─ 老模型仅异步补终态
└─ 下游依赖迁移完成后完全废除
```

### 3. 常见坑点与解决方案

| 坑点 | 现象 | 解决方案 |
|------|------|----------|
| **分片键缺失** | WHERE无分片键导致全库扫描 | 确保WHERE包含分片键，或使用Hint强制路由 |
| **跨分片JOIN** | 性能极差，内存聚合 | 使用绑定表，或应用层JOIN |
| **分布式事务** | 跨分片事务不一致 | 使用XA事务，或最终一致性方案 |
| **主键冲突** | Snowflake workerId相同 | 不同实例配置不同worker-id |
| **主从延迟** | 刚写入数据读不到 | Hint强制主库读取，或事务内读主库 |

## 十、速查表

### 何时需要分库分表?
```
单表数据量 > 500万-1000万行
单库数据量 > 100GB
单表响应时间 > 业务要求 (如100ms)
QPS超过单机MySQL承受范围 (约2000-3000)
```

### ShardingSphere vs MyCAT 一句话总结
```
ShardingSphere: 功能最全，生态最好，Java首选
MyCAT: 简单够用，多语言友好，快速上手
```
