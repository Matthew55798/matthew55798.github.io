# 分布式数据库

扩展系统一共只有三种方法，数据分区，功能分区，增加副本。

## 数据库架构演进：为什么需要分布式数据库

在讨论分布式数据库的具体技术之前，我们先理解数据库架构是如何从单点一步步走向分布式的。

### 单库单表时代的困境

根据前人经验，单表数据量在 2000 万行左右是一个常见的性能拐点。超出这个规模后，单库单表面临以下核心问题：

| 问题 | 表现 |
|------|------|
| **性能瓶颈** | 数据量增加导致 B+树索引深度增加、CBO 估算偏差放大；即使是简单查询，响应时间也会逐渐恶化 |
| **数据热点** | 所有读写集中在一个库一张表，某些数据行频繁访问成为性能热点 |
| **高可用与灾备** | 单点故障导致整个应用不可用，且数据恢复时间长 |
| **扩展受限** | 水平扩展（加机器）和垂直扩展（升硬件）在单库单表架构下均有天花板 |
| **事务与锁竞争** | 高并发下大量事务操作导致锁等待、死锁频发 |
| **备份与维护** | 数据量增长使备份、表结构变更、索引重建的时间成本不可控 |

为了解决这些问题，数据库架构经历了以下五个阶段的演进。

### 第一阶段：单库单表 + 单机优化

业务初期，所有数据都在一个数据库实例中，几张核心业务表支撑整个系统。这个阶段的优化全部集中在单机层面：

- **SQL 调优与索引优化**：消除慢查询，确保索引被正确使用。
- **业务逻辑优化**：避免 N+1 查询，减少不必要的数据库交互。
- **硬件升级**：更换 SSD、增加内存、升级 CPU，用硬件红利换取时间。
- **冷热数据分离**：将历史数据归档，保证热数据表维持在可控规模。

**这个阶段的极限**：当单表数据达到千万甚至亿级时，性能瓶颈的根因往往**不是磁盘 I/O 达到上限**，而是——

1. **数据离散程度急剧升高**，数据分布变得极其复杂；
2. 数据库优化器无法为每一条 SQL 都分配到最优执行计划（CBO 估算偏差加大）；
3. 索引结构随数据量膨胀，维护成本和扫描成本同时上升。

简单说：**数据量大 → 分布复杂 → 优化器失准 → 性能崩盘。** 一旦突破这个阈值，单机优化已经走到尽头，必须对数据进行拆分。而拆分+缓存，恰好是解决上述三个问题的组合策略——拆分降低单分片的数据分布复杂度，让优化器回到舒适区；缓存兜底热点数据，避免重复查询。

### 第二阶段：增加缓存 + 读写分离

当读请求成为瓶颈时，引入缓存层和数据库主从复制：

```
                   ┌──────────┐
                   │  Client  │
                   └────┬─────┘
                        │
                   ┌────▼─────┐
                   │  Cache   │
                   └────┬─────┘
                        │ miss
              ┌─────────▼─────────┐
              │   读写分离路由     │
              └───┬──────────┬────┘
                  │          │
            ┌─────▼──┐  ┌───▼──────┐
            │ Master │  │ Slave(s) │
            │ (写)    │  │ (读)     │
            └────────┘  └──────────┘
```

**读写分离的优势**：读请求被分散到多个从库，读吞吐量可以水平扩展。

**读写分离的代价**：主从之间存在复制延迟（binlog 异步传输），会引入数据一致性问题。典型场景是「写后立即读」——主库写入成功，从库尚未同步，客户端读到旧数据。业界常见的应对手段包括：

| 方案 | 原理 |
|------|------|
| 写后强制读主库 | 同一事务 / 同一 Session 内，读操作路由到主库 |
| 半同步复制 | 从库接收 binlog 后即 ACK 主库，缩小延迟窗口 |
| 应用层补偿 | 缓存刚写入的数据，读从库 miss 时回退主库 |

> **一个小问题：Oracle RAC 算读写分离吗？**
> 
> 不算。Oracle RAC 是全对称的 **Shared-Disk** 架构——所有节点共享同一份存储，通过 Cache Fusion 做内存级别的数据同步。它没有「主从」角色之分，所有节点均可读写。
> 
> 不过，两者在**性能收益**上有重叠：RAC 也能将读写负载分散到多个节点。区别在于——读写分离只分摊读负载（写仍然集中在主库），而 RAC 读写负载均可分摊。但 RAC 的瓶颈在共享存储层，数据量超出单存储能力时仍需额外方案。

### 第三阶段：垂直拆分（按业务拆分）

当单一业务越来越复杂，数据库的耦合成为瓶颈时，按业务领域进行垂直拆分：

```
             单体应用 + 单库                      微服务 + 多库
        ┌──────────────────────┐         ┌──────────┐  ┌──────────┐
        │  User + Order +      │         │ User     │  │ Order    │
        │  Product + Payment   │   →     │ Service  │  │ Service  │
        └──────────┬───────────┘         └────┬─────┘  └────┬─────┘
                   │                          │              │
        ┌──────────▼───────────┐         ┌────▼─────┐  ┌────▼─────┐
        │      单一数据库       │         │ UserDB   │  │ OrderDB  │
        └──────────────────────┘         └──────────┘  └──────────┘
```

**垂直拆分的本质**：服务端拆分为微服务的同时，数据库也必须同步拆分——二者是同一个动作的两个面。每个业务域拥有独立的数据库，不同域之间通过 API 而非 JOIN 通信。

**垂直拆分的收益**：每个业务库的数据规模可控，单库的分布复杂度重新回到优化器的舒适区。

**垂直拆分的局限**：当某个业务域内部的数据量继续增长（如订单表单表过亿），垂直拆分就无能为力了。此时需要进入下一阶段——水平拆分。

### 第四阶段：水平拆分（分库分表）

垂直拆分解决的是「不同业务」的隔离问题，水平拆分解决的是「同一业务」的数据量问题。将单表按分片键（如 `user_id`）拆分到多个库的多张表中：

```
                     UserDB（分片前）                 UserDB_0 .. UserDB_N（分片后）
                ┌──────────────────────┐         ┌──────────┐     ┌──────────┐
                │  t_user (5000w rows) │         │ t_user_0 │     │ t_user_N │
                │  t_order (2亿 rows)  │   →     │ t_order_0│ ... │ t_order_N│
                └──────────────────────┘         └──────────┘     └──────────┘
```

**核心挑战**：跨分片 JOIN 不可用，分布式事务，全局唯一 ID 生成。这些将在后续章节逐一展开。

### 第五阶段：多元存储（数据库集群）

前四个阶段解决的问题都是「关系型数据库的单体瓶颈」。但并非所有数据都适合用关系型数据库处理。多元存储的思路是：**以数据的使用方式，选择最合适的存储引擎。**

| 数据类型 | 存储引擎 | 典型场景 |
|----------|---------|---------|
| 事务型关系数据 | MySQL / Oracle | 订单、账户余额 |
| 全文搜索 | Elasticsearch | 商品搜索、日志检索 |
| 缓存 / 热点数据 | Redis | Session、排行榜、实时计数 |
| 文档 / 非结构化 | MongoDB | 商品描述、用户画像 JSON |
| 时序 / 监控 | InfluxDB / TDengine | 指标采集、传感器数据 |
| 分析 / OLAP | ClickHouse / Doris | 报表、数据大屏 |

至此，数据库架构从单点走向集群，从单一引擎走向多元组合。后续章节将针对每一个具体技术点进行深入讲解。
