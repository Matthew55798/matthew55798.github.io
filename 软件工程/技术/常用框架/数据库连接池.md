# 第一部分：两个数据库连接池介绍

## 1. HikariCP 简介

> 官方定位：*Fast, simple, reliable.*（快、简单、可靠）

HikariCP 是一个"零开销"（zero-overhead）的生产级 JDBC 连接池。名字来源于日语 **Hi·ka·ri**（光），整个库约 **165 KB**，非常轻量。

官方 README 引用 Edsger Dijkstra 的一句话作为设计信条：

> **"Simplicity is prerequisite for reliability."**（简单是可靠的前提）

### 官方刻意的"缺失功能"

这是 HikariCP 最有辨识度的部分——**有些功能被有意不做**：

- **不做 `PreparedStatement` 缓存**。多数连接池（DBCP、Vibur、c3p0 等）在池层做 PSCache，HikariCP 认为这是 anti-pattern：池层的 PS 缓存只能**按连接**缓存，若应用有 250 条高频 SQL、池有 20 个连接，就等于让数据库持有 5000 份执行计划、池里缓存 5000 个 `PreparedStatement` 对象。而主流 JDBC 驱动（PostgreSQL、Oracle、Derby、MySQL、DB2 等）自带的语句缓存可以**跨连接共享执行计划**——250 条高频 SQL 在数据库里只对应 250 份计划。因此正确做法是在驱动层开启 `cachePrepStmts` 之类的参数。
- **不做 SQL 日志/慢查询日志**。理由同上：交给数据库驱动自身的属性实现；驱动不支持的场景可考虑 p6spy、log4jdbc 等方案。
- **不做连接检测 SQL**。驱动支持 JDBC4 时，HikariCP 使用 `Connection.isValid()`，官方强烈建议**不要**设置 `connectionTestQuery`。
- **不暴露一堆内部调优旋钮**。README 中甚至把 `com.zaxxer.hikari.housekeeping.period` 这类系统属性称为"Secret Properties"，明确声明**不支持用户修改**。

## 2. Druid 简介

> 官方定位：阿里巴巴开源的**高性能数据库连接池和 SQL 解析器**，把 JDBC 连接池、SQL 解析分析、安全防护和监控统计深度整合为一体，是 Java 生态中功能最全面的数据库中间件之一。

### 连接池参数配置

内容取自 Druid 官方文档 [`doc/connection-pool-guide.md`](https://github.com/alibaba/druid/blob/master/doc/connection-pool-guide.md)（连接池配置指南）。

| `maxEvictableIdleTimeMillis` | 25200000 | 连接最大空闲时间，超过则强制回收（7 小时） |
| `keepAlive` | false | 是否对空闲连接发送心跳保活 |

| 参数 | 默认值 | 说明 |

| 参数 | 说明 |
|------|------|
| `filters` | 以逗号分隔的 Filter 列表，常用 `stat,wall`（统计 + 防火墙） |

> 两点提醒：
>
> 1. 调用 `setMaxPoolPreparedStatementPerConnectionSize(n)`（n > 0）会**自动开启** `poolPreparedStatements = true`，无需手动设置。
> 2. 配置文件里的 kebab-case 参数（`max-active`、`max-wait`）与 Java API 的 camelCase 方法（`setMaxActive`、`setMaxWait`）一一对应。

### 最佳实践

1. **推荐启用 `testWhileIdle`**：在空闲检测时验证连接，性能开销最小；
2. **生产环境慎用 `testOnBorrow`**：每次获取连接都执行检测 SQL，高并发下有性能影响；
3. **必须设置 `validationQuery`**：否则连接检测无法生效；
4. **超时必配**：`maxWait` 避免无限等待；开发/测试环境可用 `removeAbandoned` + `removeAbandonedTimeout` + `logAbandoned` 定位连接泄漏（生产环境应靠代码审查与测试保证连接正确关闭）；
5. **连接池大小**按并发量分档（官方文档给的**经验起点**，完整分档表见第二部分「二、Druid」）：

经验公式：`maxActive ≈ 数据库可承载最大连接数 / 应用节点数`，同时确保 `maxActive >= 单节点最大并发线程数`。

# 第二部分：两个连接池的大小算法

## 一、HikariCP

> **`maximumPoolSize`**：控制池子允许达到的最大规模，**包含空闲连接和使用中的连接**。这个值基本上决定了到数据库后端的实际最大连接数。**合理取值最好由你的执行环境决定。** 当池子达到这个规模、且没有空闲连接可用时，`getConnection()` 调用会阻塞，最长阻塞 `connectionTimeout` 毫秒后超时。请阅读 [About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)。
>
> *Default: 10*
>
> **`minimumIdle`**：控制 HikariCP 试图在池中维持的最小**空闲连接数**。如果空闲连接低于这个值、且池中连接总数少于 `maximumPoolSize`，HikariCP 会尽力快速高效地补足连接。但是，为了获得最大性能、并对流量尖峰保持响应，我们建议**不要设置**这个值，而是让 HikariCP 作为一个**固定大小**的连接池运行。
>
> *Default: 与 maximumPoolSize 相同*

**connections = ((core_count * 2) + effective_spindle_count)**

```
A formula which has held up pretty well across a lot of benchmarks for years is
that for optimal throughput the number of active connections should be somewhere
near ((core_count * 2) + effective_spindle_count). Core count should not include
HT threads, even if hyperthreading is enabled. Effective spindle count is zero if
the active data set is fully cached, and approaches the actual number of spindles
as the cache hit rate falls. ... There hasn't been any analysis so far regarding
how well the formula works with SSDs.
```

### 《About Pool Sizing》全文中译

> 译文说明：以下为 HikariCP 官方 Wiki 页面 [About Pool Sizing](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing) 的完整中文翻译。原文中 `core_count`、`connections` 等概念与公式保留英文，便于与官方文档对照。图片为原页面引用。

配置连接池是开发者经常做错的一件事。配置连接池时，有一些原则需要理解，其中一部分可能对某些人来说是反直觉的。

### 1 万个前端用户同时在线

假设你有一个网站，规模也许还不到 Facebook 那个量级，但仍然经常有 1 万个用户**同时**发起数据库请求——算下来大约是每秒 2 万次事务。那么你的连接池应该开多大？你可能会惊讶地发现，问题不在于**该多大**，而在于**该多小**！

先看这段来自 Oracle Real-World Performance 团队的短视频，大约 10 分钟，会让人大开眼界：

[![Oracle Real-World Performance 演示视频封面](/img/技术/常用框架/连接池/oracle-pool-sizing-video.png)](https://www.youtube.com/watch?v=_C77sBcAtSQ)

{Spoiler Alert} 如果你还没看视频的话。拜托，先去看，然后回到这里。

从视频中可以看到：**在其他任何条件都不变的情况下，仅仅调小连接池大小，应用的响应时间就从约 100ms 降到了约 2ms——提升了 50 倍以上。**

### 但这是为什么？

在计算机的其他领域，我们似乎已经明白了"少即是多"的道理。为什么只有 4 个线程的 *nginx* Web 服务器，性能能大幅超过开了 100 个进程的 *Apache*？如果你回想一下计算机科学入门课的内容，这不是显而易见吗？

哪怕是一台只有一个 CPU 核心的计算机，也能"同时"支撑几十甚至几百个线程。但我们[应该]都知道，这不过是操作系统通过**时间分片**（time-slicing）变的一个魔术。实际上，那一个核心同一时刻只能执行**一个**线程；然后操作系统切换上下文，这个核心去执行另一个线程的代码，如此往复。这是计算机的一条基本定律：在单个 CPU 资源下，**顺序**执行 **A** 和 **B**，*永远*比通过时间分片"同时"执行 **A** 和 **B** 更快。一旦线程数超过 CPU 核数，你增加线程只会让它更慢，而不是更快。

这个说法*几乎*是对的……

### 受限的资源

现实情况并不像上面说的那么简单，但也差不太多——还有几个其他因素在共同起作用。要分析数据库的瓶颈，可以归纳为三个基本类别：**CPU**、**磁盘**、**网络**。**内存**也可以算进去，但与磁盘、网络相比，它们在带宽上差着好几个数量级。

如果忽略**磁盘**和**网络**，问题就简单了：一台 8 核服务器把连接数设为 8，就能获得最优性能，再多就会因为上下文切换的开销而开始变慢。但磁盘和网络无法忽略。数据库通常把数据存放在**磁盘**上，而传统机械磁盘由多张旋转的金属盘片和安装在步进电机驱动机械臂上的读/写磁头组成。读/写磁头同一时刻只能位于一个位置（为某一个查询读写数据），要处理另一个查询的数据就必须**寻道**移动到新位置。因此存在**寻道时间**成本；此外还有**旋转延迟**——磁盘必须等数据在盘片上"再转一圈"才能被读写。缓存当然能缓解这一点，但原理依然成立。

在这段时间里（即"I/O 等待"），连接/查询/线程只是被**阻塞**住、在等磁盘。而恰恰是在这段时间里，操作系统可以把这份 CPU 资源用到更值得的地方——去执行另一个线程的代码。所以，正因为线程会在 I/O 上阻塞，我们实际上可以通过**让连接/线程数多于物理计算核心数**来完成更多工作。

那么该多出多少？后面会讲。多出多少还取决于**磁盘子系统**：较新的 SSD 没有"寻道时间"成本，也没有旋转因素的影响。不要被"SSD 更快，所以我可以开**更多**线程"带偏——这恰恰反了 180 度。更快、无寻道、无旋转延迟，意味着**阻塞更少**，因此**更少**的线程（更接近核数）反而比更多线程表现更好。**只有当阻塞创造了执行机会时，更多线程才会带来收益。**

**网络**与**磁盘**类似。通过以太网接口把数据写到线路上，当发送/接收缓冲区填满并发生停顿时，同样会引入阻塞。10-Gig 接口的停顿会比千兆以太网少，千兆又比百兆少。但就资源阻塞而言，网络只能排到第三位，而且常常被人在计算中漏掉。

### 公式

下面这个公式由 PostgreSQL 项目提供，作为一个起点；但我们相信它在很大程度上适用于各种数据库。你应该测试自己的应用，也就是模拟预期负载，然后在这个起点**附近**尝试不同的连接池配置：

**connections = ((core_count * 2) + effective_spindle_count)**

```
A formula which has held up pretty well across a lot of benchmarks for years is
that for optimal throughput the number of active connections should be somewhere
near ((core_count * 2) + effective_spindle_count). Core count should not include
HT threads, even if hyperthreading is enabled. Effective spindle count is zero if
the active data set is fully cached, and approaches the actual number of spindles
as the cache hit rate falls. ... There hasn't been any analysis so far regarding
how well the formula works with SSDs.
```

译：多年来，有一个公式在大量基准测试中都表现得相当稳定：为了获得最优吞吐量，活跃连接数应当接近 `((core_count * 2) + effective_spindle_count)`。即使启用了超线程，核心数也**不应**把 HT 线程算进去。如果活跃数据集被完全缓存，有效主轴数为 0；随着缓存命中率下降，它会趋近于实际主轴数。……到目前为止，还没有关于这个公式在 SSD 上表现如何的分析。

> 词汇说明：`effective_spindle_count` 直译"有效主轴数"，在 RAID 场景下就是磁盘阵列中的**物理硬盘数量**。

猜猜这意味着什么？你那台 4 核 i7、配一块硬盘的小服务器，连接池大小应该是：

`9 = ((4 * 2) + 1)`。取个整数叫 `10` 吧。看起来太小了？试一下——我们敢打赌，在这样的配置上，你完全能轻松支撑 3000 个前端用户执行简单查询、跑到 6000 TPS。如果你做压测，很可能会看到：一旦连接池明显超过 `10`（在该硬件条件下），TPS 就开始下降、前端响应时间开始攀升。

### 公理：你要的是一个**小**连接池，并且让它饱和到有线程在排队等连接

如果你有 1 万个前端用户，就配 1 万个连接，那纯属疯狂；1000 个依然可怕；就算 100 个连接，也已经是过度配置了。你要的是一个**小**池子——最多几十个连接——而应用里其余的线程都阻塞在池上、排队等待连接。如果池子调得合适，它就应该正好卡在**数据库能够同时处理的查询数量**这个上限附近；正如前面所说，这个上限很少会远高于（CPU 核数 × 2）。

我们见过不少内部 Web 应用，前端用户只有几十个、活动也是间歇性的，却配了 100 个连接的连接池，每次都让我们惊叹。不要过度配置你的数据库。

### "Pool-locking"（池锁）

关于"单个执行者持有多个连接"所引发的 "pool-locking" 问题，这里说明一下：它很大程度上是**应用层**的问题。是的，加大池子在这些场景下确实能缓解锁死，但我们强烈建议：**在扩大池子之前，先审视一下应用层还能做什么。**

为了**避免死锁**而计算池子大小，有一个相当简单的资源分配公式：

&nbsp;&nbsp; *pool size = T<sub>n</sub> x (C<sub>m</sub> - 1) + 1*

其中 *T<sub>n</sub>* 是线程的最大数量，*C<sub>m</sub>* 是单个线程同时持有的**最大连接数**。

例如，假设有 3 个线程（*T<sub>n</sub>=3*），每个线程要完成某项任务需要 4 个连接（*C<sub>m</sub>=4*）。确保永不发生死锁所需的池子大小为：

&nbsp;&nbsp; *pool size = 3 x (4 - 1) + 1 = 10*

再举个例子：最多有 8 个线程（*T<sub>n</sub>=8*），每个线程完成某项任务需要 3 个连接（*C<sub>m</sub>=3*）。确保死锁永不可能发生的池子大小为：

&nbsp;&nbsp; *pool size = 8 x (3 - 1) + 1 = 17*

👉 这未必是**最优**的池子大小，而是避免死锁所需的**最小值**。

👉 在某些环境中，使用 JTA（Java 事务管理器）可以大幅减少所需的连接数：当一个线程在当前事务中已经持有一个 Connection 时，从 `getConnection()` 返回给它的是**同一个 Connection**。

## 二、Druid

> 根据应用并发量合理设置：

| 场景 | `initialSize` | `minIdle` | `maxActive` |
|------|--------------|-----------|-------------|
| 小型应用（< 50 QPS） | 2 | 2 | **10** |
| 中型应用（50–500 QPS） | 5 | 5 | **20** |
| 大型应用（> 500 QPS） | 10 | 10 | **50** |

以及一条经验公式：

> `maxActive ≈ 数据库可承载最大连接数 / 应用节点数`，同时确保 `maxActive >= 单节点最大并发线程数`
