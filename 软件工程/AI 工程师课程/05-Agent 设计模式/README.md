## 章节目录

### 5.1 Agent 基础

**设计主题**：ReAct 循环、Agent vs Workflow 边界

**主要概念**：

- **ReAct 循环**：感知（Perception）→ 思考（Thought）→ 行动（Action）→ 观察（Observation）
  ```
  用户输入 → LLM 分析 → 决策（调用 Tool / 直接回答）→ 执行 Tool → 观察结果 → 下一轮决策
       ↑                                                                   ↓
       └──────────────────────────── 循环（直到完成）──────────────────────┘
  ```
- **感知**：理解用户意图、解析输入、识别任务类型
- **思考**：内部推理过程，决定下一步行动（不输出给用户）
- **行动**：选择并执行 Tool，或生成最终回答
- **观察**：接收 Tool 执行结果，更新状态
- **何时用 Agent vs 固定流程**：

**Agent vs Workflow 对比**：

| 维度 | Agent | Workflow |
|------|-------|----------|
| 决策方式 | 自主决策，动态选择 | 预定义路径，固定执行 |
| 适用场景 | 开放式任务、多步骤推理、需要工具协作 | 确定流程、合规要求、高可靠性 |
| 可预测性 | 较低（每次路径可能不同） | 高（固定路径） |
| 延迟 | 较高（多轮推理） | 较低（直接执行） |
| 可控性 | 需设计约束和边界 | 完全可控 |
| 容错 | 可自我修复（重试其他路径） | 需显式错误处理 |

**决策树**：
```
任务确定性强？
├─ 是 → Workflow（SOP 流程）
└─ 否 → 需要工具协作？
    ├─ 否 → 直接 LLM
    └─ 是 → Agent（自主决策）
```

**类比说明**：
- **Agent ≈ 有自主决策能力的员工**：接到任务后自己思考怎么做，遇到问题自己想办法解决
- **Workflow ≈ 按 SOP 执行的员工**：严格按照既定流程操作，不偏离、不发挥
- **ReAct 循环 ≈ 工作中的 PDCA 循环**：计划（Plan）→ 执行（Do）→ 检查（Check）→ 改进（Act）
- 用 Agent 是放权，用 Workflow 是管控

**设计产出**：Agent vs Workflow 决策对照表

**主线项目对接**（V5 → 设计 Agent 编排层）：
- 确定哪些功能用 Agent、哪些用固定流程
- 设计 Agent 决策边界（何时停止自主决策）
- 设计 Agent 状态管理机制

### 5.2 Tool 设计模式

**设计主题**：将现有 API 抽象为 Tool

**主要概念**：

- **Tool 四要素**：
  | 要素 | 说明 | 设计要点 |
  |------|------|---------|
  | 名称 | Tool 的标识 | 语义化命名，如 `query_user_profile` |
  | 描述 | LLM 理解 Tool 用途 | 清晰说明功能、输入输出、使用场景 |
  | 参数 | Tool 的输入规范 | JSON Schema 定义，含类型、必填、枚举等 |
  | 返回 | Tool 的输出规范 | 统一结构，含成功/失败、数据、错误码 |

- **Tool 定义规范（JSON-Schema 风格）**：
  ```json
  {
    "name": "get_weather",
    "description": "获取指定城市的天气信息，支持今天和未来3天预报",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "城市名称，如\"北京\"
        },
        "days": {
          "type": "integer",
          "description": "预报天数，1-3",
          "enum": [1, 2, 3],
          "default": 1
        }
      },
      "required": ["city"]
    },
    "returns": {
      "success": "boolean",
      "data": {
        "city": "string",
        "temperature": "number",
        "condition": "string",
        "forecast": "array"
      },
      "error": {
        "code": "string",
        "message": "string"
      }
    }
  }
  ```

- **Tool 发现与选择**：
  - 注册：Tool 在启动时注册到 Tool Registry
  - 发现：Agent 从 Registry 获取可用 Tool 列表
  - 选择：LLM 根据任务描述选择合适的 Tool（Prompt 中注入 Tool 描述）
  - 优先级：可为 Tool 设置优先级或标签，缩小选择范围

- **参数校验**：
  - 必填项检查：调用前确保所有 required 参数存在
  - 类型校验：参数类型匹配 JSON Schema 定义
  - 范围校验：数值范围、枚举值、正则匹配
  - 提前拦截：在 LLM 调用 Tool 前校验，避免无效调用

- **返回值规范**：
  - 统一包装：`{success: boolean, data?: any, error?: {code, message}}`
  - 错误分类：业务错误（参数错误）vs 系统错误（服务不可用）
  - 结构化数据：便于 LLM 理解和后续处理
  - 上下文保留：返回结果中保留请求上下文（如 trace_id）

**类比说明**：
- **Tool ≈ 员工手中的工具箱**：锤子、螺丝刀、扳手，需要时拿出来用
- **Tool Registry ≈ 工具库管理台账**：记录有哪些工具、怎么用、谁可以用
- **参数校验 ≈ 借工具前的检查**：确认工具型号对、配件全，避免白跑一趟

**设计产出**：Tool 接口规范草案（参数、返回、描述、权限四要素）

**主线项目对接**（V5 → 设计 Tool 注册中心）：
- 设计 Tool Registry 数据结构
- 设计 Tool 版本管理机制
- 设计 Tool 发现与选择策略
- 设计参数校验中间件

### 5.3 Tool 安全与权限

**设计主题**：最小权限原则、沙箱执行

**主要概念**：

- **三层防线架构**：

  ```
  ┌─────────────────────────────────────────────────────────────┐
  │ 第一层：身份与权限（Identity & Permission）                  │
  │   - 用户身份认证（Token/API Key）                            │
  │   - Tool 级别权限控制（谁能调用什么 Tool）                    │
  │   - 操作范围限制（只能访问哪些数据）                          │
  └─────────────────────────────────────────────────────────────┘
                              ↓
  ┌─────────────────────────────────────────────────────────────┐
  │ 第二层：参数与边界校验（Input Validation）                    │
  │   - 参数类型与格式校验                                        │
  │   - 输入范围限制（防止注入、越界）                             │
  │   - 敏感参数拦截（密码、密钥等不可作为参数）                    │
  └─────────────────────────────────────────────────────────────┘
                              ↓
  ┌─────────────────────────────────────────────────────────────┐
  │ 第三层：沙箱与审计（Sandbox & Audit）                         │
  │   - 沙箱隔离（进程/容器级别隔离）                              │
  │   - 敏感操作拦截（删除、修改类操作二次确认）                    │
  │   - 审计日志（谁在什么时间调用了什么 Tool）                     │
  └─────────────────────────────────────────────────────────────┘
  ```

- **权限模型**：
  - **RBAC（基于角色的权限控制）**：为用户分配角色，角色绑定 Tool 权限
  - **ABAC（基于属性的权限控制）**：根据用户属性 + 资源属性动态决策
  - **最小权限原则**：只授予完成任务所需的最小权限集合
  - **权限继承**：Agent 的权限 = 用户权限 ∩ Tool 权限

- **敏感操作拦截**：
  - 危险操作清单：DELETE、DROP、TRUNCATE 等不可逆操作
  - 二次确认机制：高危操作需要人工确认或额外授权
  - 操作窗口限制：某些操作只能在特定时间段执行
  - 影响范围提示：执行前显示影响的数据量或范围

- **沙箱隔离**：
  - 进程级隔离：Tool 在独立进程中执行，崩溃不影响主服务
  - 容器级隔离：使用 Docker/容器技术隔离运行环境
  - 网络隔离：限制 Tool 的网络访问权限（白名单模式）
  - 资源限制：CPU、内存、执行时间上限

- **审计日志**：
  - 记录内容：调用者、Tool 名称、参数、返回值、执行时间、结果状态
  - 敏感信息脱敏：日志中隐藏密码、密钥等敏感数据
  - 存储策略：保留时长、归档机制、查询接口
  - 异常告警：失败率突增、敏感 Tool 被调用时触发告警

**类比说明**：
- **权限体系 ≈ 公司门禁系统**：不同级别员工能进不同区域
- **沙箱 ≈ 实验室的安全操作间**：危险实验在里面做，出事也隔离在里面
- **审计日志 ≈ 监控摄像头 + 工作记录**：出了问题能追溯，也能发现异常行为

**设计产出**：Tool 安全架构设计图（三层防线）

**主线项目对接**（V5 → 设计权限网关）：
- 设计权限模型（RBAC/ABAC）
- 设计敏感操作清单与拦截策略
- 设计沙箱执行方案
- 设计审计日志系统

### 5.4 多 Agent 协作

**设计主题**：路由模式、协作模式、竞争模式

**主要概念**：

- **多 Agent 架构对比**：

  | 维度 | 中心化路由 | 去中心化协作 |
  |------|-----------|-------------|
  | 架构图 | 一个 Router Agent 分发任务 | 多个 Agent 点对点通信 |
  | 决策位置 | 中央 Router | 各 Agent 自主协商 |
  | 复杂度 | 逻辑集中，易管理 | 分布式，需协议支持 |
  | 扩展性 | Router 可能成为瓶颈 | 水平扩展容易 |
  | 容错性 | Router 单点故障 | 无单点，部分 Agent 故障可继续 |
  | 适用场景 | 任务分类明确、Agent 功能差异大 | 需要深度协作、信息共享频繁 |

- **中心化路由模式**：
  ```
              ┌───────────────┐
              │   Router Agent │ ← 接收所有输入，决策分发
              └───────┬───────┘
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
  ┌─────────┐   ┌─────────┐   ┌─────────┐
  │ Agent A │   │ Agent B │   │ Agent C │
  │(客服类) │   │(技术类) │   │(销售类) │
  └─────────┘   └─────────┘   └─────────┘
  ```
  - Router 负责：意图识别、Agent 选择、结果汇总
  - 优点：逻辑清晰、易于管控、可解释性强
  - 缺点：Router 复杂度高、新增 Agent 需修改 Router

- **去中心化协作模式**：
  ```
  ┌─────────┐      ┌─────────┐      ┌─────────┐
  │ Agent A │←────→│ Agent B │←────→│ Agent C │
  │(订单)   │      │(库存)   │      │(物流)   │
  └─────────┘      └─────────┘      └─────────┘
       ↑                              ↑
       └────────── 可互相调用 ────────────┘
  ```
  - Agent 之间可直接通信，协商任务分配
  - 优点：灵活、无单点、更接近团队协作
  - 缺点：调试困难、可能出现循环依赖

- **任务分配策略**：
  - **能力匹配**：根据 Agent 能力标签匹配任务
  - **负载均衡**：优先分配给当前空闲的 Agent
  - **优先级队列**：高优先级任务插队，或分配给高性能 Agent
  - **失败转移**：Agent 故障时自动转派给其他 Agent

- **冲突解决机制**：
  - **仲裁者模式**：出现冲突时由专门的 Arbiter Agent 裁决
  - **投票机制**：多个 Agent 给出方案，投票或加权选择
  - **优先级规则**：预定义规则（如客户满意度优先、成本优先）
  - **人工介入**：无法自动解决时转人工处理

**类比说明**：
- **中心化路由 ≈ 公司前台转接**：打进来的电话由前台判断转给哪个部门
- **去中心化协作 ≈ 项目组内部协作**：成员之间直接沟通，共同推进项目
- **冲突解决 ≈ 跨部门争议升级**：先内部协商，解决不了找上级，再不行找 CEO

## 学习建议

- **Agent 是 AI 系统的"大脑"**，理解 ReAct 循环是设计 Agent 的基础
- 不要盲目追求 Agent，很多场景用固定 Workflow 更可靠、更可控
- Tool 设计要关注**边界和安全**，Agent 能做的事情越多，风险也越大
- 多 Agent 架构没有银弹，选择中心化还是去中心化取决于**业务场景和团队能力**
- Vibe Coding：用 AI 辅助生成 Tool Schema 和多 Agent 架构草图，自己评审合理性
