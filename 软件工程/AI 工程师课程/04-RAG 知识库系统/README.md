## 章节目录

### 3.1 RAG 全景

**设计主题**：理解 RAG 在 AI 技术栈中的定位

**主要概念**：
- **三种路径对比**：
  | 方式 | 何时使用 | 优缺点 |
  |------|---------|--------|
  | 纯 Prompt | 常识问题、简单问答 | 快而便宜，但无法用私有数据 |
  | RAG | 需要结合私有权数据 | 灵活、可更新，但依赖检索质量 |
  | Fine-tuning | 特定风格/格式、领域特定词汇 | 改变模型行为，但训练/成本高 |
- **RAG Pipeline 四阶段**：
  ```
  索引 (Indexing) → 检索 (Retrieval) → 增强 (Augmentation) → 生成 (Generation)
  ```
- **何时选 RAG**：
  - 知识更新频繁 → Fine-tuning 跟不上
  - 需要引用溯源 → Fine-tuning 是黑盒
  - 数据量大且分散 → 不适合全放进 Prompt

**类比说明**：
- Prompt：开卷考试，只带一本书进考场
  - 快但受限于"带什么"
- RAG：带个图书馆管理员进考场，随时查
  - 灵活但依赖"管理员查找速度"
- Fine-tuning：把知识刻进模型里
  - 永久改变但"改不了"
- **RAG ≈ 数据库查询 + 智能组装**
- **Fine-tuning ≈ 重新编译代码**（贵且不可逆）
- 你设计系统的决策树

**设计产出**：技术选型决策树（Prompt → RAG/Fine-tuning 如何选择）

### 3.2 索引设计

**设计主题**：如何让文档"可被智能检索"

**主要概念**：
- **文档解析**：
  - 格式处理：PDF/Word/HTML/Markdown → 纯文本
  - 结构化提取：表格、代码块、图片说明
  - 元信息提取：作者、日期、来源、权限标签
- **Chunk 策略**：
  | 策略 | 描述 | 适用场景 | 优缺点 |
  |------|------|---------|--------|
  | 固定字符数 | 每 N 个字符切一块 | 通用文档 | 简单但可能切断句子 |
  | 按段落分割 | 按段落/章节切分 | 结构化文档 | 语义完整，但段可能太长 |
  | 语义分割 | 按语义边界切分 | 关键文档 | 精准但计算成本高 |
  | 递归分割 | 先大后小，多级切割 | 复杂文档 | 兼顾粒度与层级 |
- **Chunk 大小选择**：
  - 太小：上下文信息不足 → 检索结果碎片化
  - 太大：检索精度下降 → Token 浪费
  - 经验值：500-1500 tokens/Chunk（因场景而异）
- **Overlap 设置**：
  - Chunk 间重叠 10-20%：避免边界信息丢失
  - 代价：增加存储和检索量
- **Embedding 时机**：
  - 何时 Embedding：解析后立即 Embedding → 入库
  - Embedding 模型选择：维度（768/1024/1536）、领域适配、成本
- **向量数据库选择**：
  - 嵌入式：Chroma（开发/小型）
  - 专用：Pinecone（SaaS，简单）
  - 开源：Milvus（大规模）
  - 集成：PGVector（PostgreSQL 扩展，已有 PG 时优选）

**主线项目对接**（V4 → 设计文档处理 Pipeline）：
- 设计文档解析器（支持哪些格式）
- 设计 Chunk 策略（大小、分割方式、Overlap）
- 设计 Embedding 模型选择决策
- 设计向量数据库选型

**设计产出**：
1. 文档处理 Pipeline 架构图
2. Chunk 策略决策表
3. Embedding 选型对比表

### 3.3 检索策略

**设计主题**：如何让 AI"找到对的知识"

**主要概念**：
- **向量检索**（语义相似）：
  - 原理：Query 转向量 → 相似度匹配
  - 优点：理解语义意图
  - 缺点：专有名词/数字可能匹配不准
- **关键词检索**（BM25/TF-IDF）：
  - 原理：关键词匹配 → 相关度排序
  - 优点：专有名词精准
  - 缺点：不理解语义
  - 适用场景：技术文档、API 文档、操作指南
- **混合检索**（Hybrid）：
  - 向量 + 关键词结果融合
  - 融合策略：加权排序、RRF（Reciprocal Rank Fusion）
- **HyDE（假设文档嵌入）**：
  - 原理：Query → LLM 生成"假设回答" → Embedding → 检索"假设回答"
  - 优点：Query 与文档语义鸿沟
  - 缺点：增加一次 LLM 调用（延迟 + 成本）
- **重排序（Rerank）**：
  - 原理：粗排后，用更精准的模型对 Top K 重排
  - 适用：对精度要求高的场景
  - 代价：增加计算开销

**检索策略对比矩阵**：
| 策略 | 精度 | 延迟 | 成本 | 适用场景 |
|------|------|------|------|---------|
| 纯向量 | ★★★☆ | ~50ms | 低 | 通用问答 |
| 纯关键词 | ★★☆☆ | ~20ms | 极低 | 精确匹配场景 |
| 混合检索 | ★★★★ | ~80ms | 中 | 知识密集型 |
| HyDE | ★★★★ | ~2s | 高 | 语义差距大 |
| 重排序 | ★★★★★ | +50 ms | 中 | 精度优先 |

**主线项目对接**（V4 → 设计检索架构）：
- 选择检索策略（混合 + 重排序？）
- 设计检索质量评估指标

**设计产出**：检索策略对比表（5 种方式 × 3 个维度）

### 3.4 增强与生成

**设计主题**：检索结果 → 增强 Prompt → 生成回答

**主要概念**：
- **Prompt 增强策略**：
  - 拼接方式：系统 Prompt + 检索结果 + 用户问题
  - 引用标注：回答中标注出处（"根据文档 X"）
  - 冲突处理：多篇文档信息冲突时如何处理？
- **幻觉抑制**：
  - 强制引用：要求 AI 必须引用检索内容，未知时回答"不确定"
  - 回答后验：AI 回答后再检查是否与检索一致
  - 置信度标注：回答附带置信度（但 AI 不自带置信度！需要额外机制）
- **模板设计**：
  ```
  你是客服助手。请根据以下知识来回答用户问题：
  
  ## 相关知识
  [检索结果 1]
  [检索结果 2]
  ...
  
  ## 规则
  - 必须引用检索结果
  - 如果检索结果无法回答问题，请说"我暂时无法回答"
  - 不要编造信息
  - 用简洁的语言回答
  
  ## 用户问题
  [用户问题]
  
  ## 回答
  ```

**主线项目对接**（V4 → 设计 Prompt 增强模板）：
- 设计 RAG Prompt 模板
- 设计引用标注方案
- 设计幻觉抑制策略

**设计产出**：RAG Prompt 模板 + 幻觉抑制方案

### 3.5 知识库系统设计

**设计主题**：从 Pipeline 到完整系统

**主要概念**：文档 → 检索 → 评估 → 更新 的闭环
- **数据源接入**：
  - 支持哪些数据源
  - 接入方式（API/S3/数据库/Webhook）
  - 增量更新策略（增量 vs 全量）
- **增量更新**：
  - 监控文件变更 → 触发重索引
  - 定时全量索引（兜底）
  - 版本管理：旧文档如何清理？
- **质量评估**：
  - 检索质量（命中率、Top-K 准确率）
  - 生成质量（相关性、准确性、有用性）
  - 端到端评估
- **系统架构**：
  ```
  ┌──────┐ ┌──────┐       ┌──────────┐       ┌──────────┐
  │ 数据源│→│ 处理 │→[向量库]→│ 检索服务 │→│ 增强层 │→[LLM]
  │ (文件) │  Pipeline │       │          │       │        │
  └──────┘ └──────┘       └──────────┘       └──────────┘
                           ←──────────────────────────────┘
                           用户反馈
  ```

**主线项目对接**（V4 → 设计知识库系统全架构）：
- 设计数据源接入方案
- 设计增量更新机制
- 设计质量评估流程
- 设计完整知识库系统架构图
